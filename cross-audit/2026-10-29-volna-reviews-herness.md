## F-1 (HIGH) — гейты есть, но их не запускает ни один внешний триггер: `.github/` отсутствует

**Воспроизведение.**

```
$ ls -d .github 2>/dev/null || echo "папки .github НЕТ"
папки .github НЕТ
$ ls .github/workflows 2>/dev/null || echo "workflow'ов НЕТ"
workflow'ов НЕТ
```

`AGENTS.md` правило 2 говорит: «**Публикация — только после гейтов.** `python bin/hs.py gates` должен быть
зелёным». Это верно для того, кто помнит его запустить. Для push, для PR и для внешнего участника гейта нет:
ни один workflow не вызывает `hs.py gates`, потому что workflow'ов нет вовсе.

**Следствие.** Все девять групп проверок могут сломаться в любой момент, и единственный способ узнать —
чей-то локальный запуск. В семействе это единственный репозиторий в таком положении: у `lexspec` в CI пять
guard'ов и три негативных контроля, у `flowguard-spec` — десять шагов, у `VecDHT` — свой набор.

**Починка.** Один `.github/workflows/guards.yml` из трёх шагов:

```yaml
- run: python bin/hs.py gates
- run: python bin/hs.py selftest
- run: python tests/run_all.py     # см. F-2
```

Цена — один файл. Эффект — «зелёное» перестаёт означать «у кого-то локально было зелёное».

## F-2 (MEDIUM) — `PRINCIPLES.md` обещает негативный тест на каждый из 25 принципов; ни одна строка не называет тест

**Обещание** (`docs/PRINCIPLES.md`, шапка):

```
Каждый принцип записан тремя полями: что запрещает, чем принуждается в харнессе,
как проверить, что принуждение работает (негативный тест).
Принцип без третьего поля — декорация.
```

**Что в дереве.**

```
$ python - <<'PY'
import re, pathlib
t = pathlib.Path("docs/PRINCIPLES.md").read_text(encoding="utf-8")
rows = re.findall(r"^\|\s*(P\d+)\s*\|", t, re.M)
tests = sorted(p.name for p in pathlib.Path("tests").glob("test_*.py"))
print("принципов:", len(rows))
print("строк со ссылкой на файл теста:", len([r for r in re.findall(r"^\|.*$", t, re.M) if "tests/" in r or ".py" in r]))
print("файлов тестов:", len(tests))
print("упомянуты в PRINCIPLES:", len([x for x in tests if x in t]))
PY
принципов: 25
строк со ссылкой на файл теста: 0
файлов тестов: 12
упомянуты в PRINCIPLES: 0
```

Третий столбец заполнен **описаниями**, а не ссылками: «убрать команду из записи → публикация падает»,
«посадить нарушение → гейт обязан упасть». Прочитать можно, выполнить — нельзя: не сказано, какой файл и
какая функция это делают.

**Смягчающее обстоятельство, которое я проверил:** часть этих проверок действительно исполняется — `gates`
ловит секреты, утверждения, ссылки, критерии, отказы, процедуры, формулировки и README, а `selftest` прогоняет
негативные тесты. То есть принуждение существует. Не существует **связи** между строкой таблицы и тестом,
который её держит: 25 обещаний и 12 файлов живут в разных местах, и ни одно не указывает на другое.

**Починка.** В третьем столбце — имя файла и функции (`tests/test_budget.py::test_...`), а не описание.
Тогда `lab/check-principles.py` может проверить, что каждая ссылка существует, и упасть на принципе без неё.
Это ровно тот гейт, который документ уже обещает.

## F-3 (LOW) — тесты не собираются раннером: `unittest discover` находит ноль

```
$ python -m unittest discover -s tests -q; echo $?
Ran 0 tests in 0.000s
NO TESTS RAN
5
$ head -4 tests/test_audit.py
"""Тесты аудита: заметка без воспроизводящего случая не является находкой.

Запуск: python tests/test_audit.py
"""
```

Тесты — самостоятельные скрипты с `sys.exit`. Это работает, и `bin/hs.py selftest` их уже вызывает. Но
`unittest discover` находит **0** и печатает «NO TESTS RAN» — то есть наивный CI-шаг будет зелёным и пустым.
Новый тест не подхватится сам: списка нет, `selftest` перечисляет файлы вручную.

**Починка.** `tests/run_all.py`, который обходит `tests/test_*.py`, запускает каждый и суммирует коды возврата,
плюс проверка «найдено не меньше N файлов» — иначе удалённый тест исчезает молча.

## Что я прогнал и **не** нашёл проблем

- `bin/hs.py gates` — девять групп, все `[ok]`, exit 0;
- `bin/hs.py selftest` — негативные тесты инструмента, все `[ok]`, включая «реестр критериев отбивает строку
  без способа установления»;
- все 12 тестов в `tests/` проходят при прямом запуске;
- разделение `core/` (библиотека) и `bin/` (инструменты) честное: тесты импортируют `core`, то есть проверяют
  поведение, а не CLI;
- `CLAIMS.md`, `NOT-CLAIMED.md`, `LEGAL.md` — границы вынесены отдельными файлами, а не абзацем в README;
- `portfolio.json`, `procedures.json`, `profiles.json`, `classes.json` — конфигурация вне кода, тесты её
  читают, а не дублируют.
