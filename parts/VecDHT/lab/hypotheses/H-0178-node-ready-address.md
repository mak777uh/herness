## Боль

Одна фраза: узел слушает на всех интерфейсах, а объявляет себя на loopback — и вторая машина,
получившая этот адрес, идёт на свой собственный loopback и не находит узел.

Если не закрыть, двухмашинный сценарий `lab/two-hosts.sh remote` проходит только потому, что
адрес машины 1 подставляется в командной строке руками (`M1`). Скрипт, который взял бы адрес из
`NODE_READY` — то есть ровно так, как велит README («узел 2 получает адрес M1») — получил бы
`127.0.0.1` и упал бы на «no shard answered» после 30-секундного таймаута.

## Что измерено до правки (2026-11-10, машина boxes.dev `vecdht`)

```
$ ss -ulnp | grep 7771
UNCONN 0  0  0.0.0.0:7771  0.0.0.0:*  users:(("vecdht-cli",pid=200725,fd=8),("vecdht-cli",pid=200725,fd=7))

$ grep NODE_READY /tmp/vd-cer/node0.log
NODE_READY listen=/ip4/127.0.0.1/udp/7771/quic-v1 peer=12D3KooWEKyPsvgm7g8vyRA59466ph3t9VLxEUFzNqTXHJdfY2Wq ...
```

Сокет слушает `0.0.0.0`, а объявлен `127.0.0.1`. Это не гипотеза, а замер: два факта из двух
разных инструментов на одном и том же процессе.

## Где причина

`crates/vecdht-net/src/service.rs:732` — `SwarmEvent::NewListenAddr` пушит адрес в
`listen_addrs` в порядке прихода событий, без фильтра:

```rust
SwarmEvent::NewListenAddr { address, .. } => {
    if self.role == Role::Relay {
        self.swarm.add_external_address(address.clone());
    }
    self.listen_addrs.push(address)
}
```

`crates/vecdht-cli/src/node_cmd.rs:347` берёт **первый** адрес из `listen_addrs()` и печатает его
как адрес узла. При `--listen 0.0.0.0` libp2p отдаёт несколько событий (по одному на интерфейс),
и порядок не гарантирован.

## Зачем это нужно

Условие 3 v1 — «один сценарий на разных машинах, воспроизводимый командой из README». README
требует подставить LAN-адрес машины 1. Пока узел объявляет loopback, эта инструкция не работает
без ручной подстановки, а значит сценарий не воспроизводится командой.

## Порог (объявляется до приёмочного прогона)

Заморожен в `lab/expectations/e0178.tsv` пре-регистрационным коммитом.

- **подтверждение:** все факты таблицы совпали, `WORST_RC=0`, второй прогон `STABLE=1`;
- **опровержение:** любой факт таблицы разошёлся;
- **неопределённость:** прогон не запустился (нет тулчейна, нет машины) — это `UNKNOWN`, а не «ок».

Ключевые факты, которые таблица фиксирует:

| факт | что значит |
|---|---|
| `PRE_FIX_WILDCARD_LOOPBACK` | на пине `NODE_READY` при `0.0.0.0` содержит `127.0.0.1` — дефект есть |
| `POST_FIX_WILDCARD_LOOPBACK` | после правки не содержит — дефект закрыт |
| `POST_FIX_LOOPBACK_KEPT` | при `--listen 127.0.0.1` loopback **остался** — отрицательный контроль правки |
| `LISTEN_TEST_RC` | новый тест зелёный |
| `SELFCHECK_OK` | `HOSTS_OK=1` не сломан |
| `REMOTE_OK` | `HOSTS_REMOTE_OK=1` не сломан |
| `TRANSPORT_RC` | 10 тестов транспорта зелёные |
| `WIRE_TOUCHED` | wire не тронут |
| `SPEC_TOUCHED` | спека не тронута (правка — объявление адреса, не контракт) |

## Чего эта карточка не доказывает

- что узел **достижим** снаружи: фильтр убирает ложное объявление, но не открывает NAT;
- что `0.0.0.0` в `listen_addrs` вообще не нужен — у него есть законный потребитель (relay,
  `E-0145`), поэтому фильтр применяется к тому, что печатает CLI, а не к внутреннему списку;
- что двухмашинный сценарий пройден: он остаётся заблокированным платформой (boxes.dev не даёт
  UDP между машинами), и это записано отдельно.
