# herness — харнесс для автономной работы

Харнесс нужен для одного: **чтобы агент работал сам, долго и с пользой** — часами и сутками, доводя
задачи до результата, который человеку не нужно перепроверять руками.

Границы правды — не цель, а **метод внутри этой задачи**. Он выбран не из любви к строгости:
без проверяемого свидетельства автономная работа деградирует в правдоподобный шум, и чем дольше
агент работает, тем дороже каждая ошибка. На короткой задаче «объявил готово, а не готово»
раздражает; на суточной — обнуляет весь результат. А доверие человека — ресурс: если результат
перепроверяют вручную, автономии нет, есть дорогой черновик.

## Что уже работает

Свой контур, собранный с нуля, без обёрток вокруг чужого агента:

- **своё ядро** Linux 6.18.60 (`core-rs/kernel/`): `tinyconfig`, без модулей и SMP, с
  пространствами имён, cgroups, Landlock и ужесточениями;
- **комната**: ядро грузится в QEMU, `init` — свой бинарь на Rust. Внутри нет shell и coreutils;
  `init` сам монтирует `dev`, `proc`, `sys`, проверяет возможности и ведёт журнал;
- **цикл** (`core-rs/src/loopmod.rs`): модель отвечает одной строкой — `TOOL <имя> <аргумент>`,
  `DONE <итог>` или `BLOCKED <почему>`; цикл разбирает ответ, исполняет инструмент и пишет событие
  в журнал. У прогона есть бюджет по шагам, времени и деньгам;
- **инструменты**: `search` (со сводкой «в каких файлах сколько совпадений»), `list`,
  `read <файл> [строка]` (с продолжением), `write` внутри рабочего каталога, `seal`, `netprobe`;
  все ограничены каталогом, выдача — по критерию;
- **мост наружу** (`bin/bridge.py`) — единственное место, где живёт ключ провайдера; комната
  говорит с ним plain HTTP, TLS и ключ остаются на хосте;
- **три слоя проверки**: форма (порядок событий), опора (ответ должен делить с журналом конкретное
  слово — цифру, путь, id), приёмка (`bin/accept.py`: критерий объявлен до прогона, лежит на хосте
  и проверяет вынесенный из комнаты журнал);
- **продолжение после обрыва**: журнал читается до первой невалидной записи, состояние
  восстанавливается, прогон продолжается с того же места; нечитаемый хвост отрезается с записью об
  этом (ADR-0051);
- **метрики собственной работы** (`bin/judge_metrics.py`): ложное «готово», `pass@1`, `pass^2`,
  цена принятого результата; задачи берутся из явного индекса прогонов (`runs/index.json`), а не
  угадываются по имени файла;
- **29 гейтов** (`bin/hs.py gates`), и у **каждого есть проба**: во временную копию подкладывается
  реалистичный дефект и гейт обязан его заметить (`bin/gate_probe.py`, 30 проб из 30). Пятнадцать
  быстрых проб гоняются при каждом запуске гейтов;
- **комната собирается по манифесту** (`lab/room.json` + `bin/build_room.py`) и сверяется с
  репозиторием до прогона: устаревший образ больше не выглядит как провал модели (F-0035);
- **задачи берутся из собственной истории** (`bin/history_tasks.py`, `baseline_history*.py`,
  `chain_task.py`): утверждения, отказы, журналы, коммиты, решения — с машинными ключами.

Короткая формула изменилась за последние дни. Раньше было «проверяет хорошо, работает плохо»:
половина прогонов заканчивалась молчанием. Сейчас **все семь серий задач проходят**, а причина

Что дало сдвиг (каждое — с замером, а не с верой):

| что | было | стало |
|---|---|---|
| петля по информации (тот же вызов + тот же результат) | 84 % прогонов без исхода | механизм в цикле, застой останавливает прогон с причиной |

| правило «собери ответ из нескольких результатов» | цепочка не решалась | решена за 6 шагов из 20 |
| поиск | регистрозависимый, окно 160 символов | регистронезависимый, окно сдвигается к совпадению |
| пробы гейтов | 2 из 28 | 30 из 30 |

## Что это не

- **Не работающий продукт.** Нет релиза и нет выполненного внешнего задания.
- **Не доказательство, что «плоскость свидетельств» — единственно верное ядро.** Это выбранная
  предпосылка (ADR-0029), и она оправдана целью, а не сама собой.
- **Не «умнее».** Разница не в правильности ответов, а в том, что остаётся, чем проверить, и что
  сказано о границах.
- **Не полная изоляция.** Нет shell, инструменты не выходят из каталога, фильтр syscall ставится,
  если ядро умеет, и об этом честно пишется в журнал. Это не защита от целевого обхода.
- **Не «задача решена».** Приёмка проверяет объявленные условия; если критерий неполон, PASS этого
  не покажет.

Границы — `NOT-CLAIMED.md`; отброшенное — `docs/eliminations.md`; отказы — `lab/failures/`.

## Как устроено

```
ядро 6.18.60 ──> init (Rust) ──> цикл ──> инструменты (search/list/read/write/seal)
                    │              │
                    │              └─ журнал HSJ1: запись с CRC, границы коммита, хвост не чинится
                    └─ песочница: namespaces, Landlock, seccomp (если ядро умеет)
                                   │
   хост: мост (ключ, TLS) <── plain HTTP ── комната
         приёмка (accept/) <── журнал, вынесенный на диск
         метрики (judge_metrics) ← те же журналы
```

## Структура

```
bin/                гейты и проверки (hs.py), мост, приёмка, метрики, доказательства
core-rs/            ядро, init, цикл, песочница, модели; сборка и прогоны в QEMU
accept/             критерии приёмки (в комнату не попадают)
docs/               ADR, журнал решений, обзор сверху, реестр исключённого
lab/                гипотезы, отказы, склад решений (adoptions.json), правила автономии
research/           склады источников и данных, артефакты прогонов
CLAIMS.md           реестр утверждений: тип свидетельства, команда проверки, границы
NOT-CLAIMED.md      что сознательно не утверждаем
```

## Быстрый старт

```
python bin/hs.py gates          # 27 гейтов: секреты, утверждения, ссылки, автономия, решения
python bin/hs.py selftest       # негативные тесты самого инструмента
python bin/judge_metrics.py     # ложное «готово», pass@1, pass^2, цена принятого
python bin/silence_report.py    # почему прогон закончился без заявления
python bin/check_autonomy.py --paths CITATION.cff   # должен дать exit 1
python bin/check_adoptions.py --self-test           # 5 отказов на 5 подложенных дефектов
python bin/gate_probe.py                            # пробы всех гейтов: подложить дефект и потребовать находки
python bin/readme_numbers.py                        # числа README против прибора (--fix пересобрать)
python bin/build_room.py --check                    # комната совпадает с манифестом
python bin/accept.py accept/room-claims-statistics-v3.json <журнал.bin>
```


## Как встроено исследование источников

Чтение не связано с решением — значит, бесполезно. Поэтому цикл из шести шагов, и **каждый шаг
оставляет артефакт**:

1. **Склад** — источник попадает в `research/REFS-INDEX.md`, `DATA-LINKS.md` или
   `HARNESSES-INDEX.md` в тот же день, со статусом `[Ч]` читал / `[А]` только описание /
   `[?]` не открывал.
2. **Вопрос, а не тема** — «как у них решён выход из тупика», а не «посмотрим, что есть».
3. **Разбор** — `research/<NAME>-REVIEW.md`: что механизм делает, какая цена, где доверенная
   граница и **что у них слабее нас**.
4. **Решение** — строка в `lab/adoptions.json` (и `docs/CATALOG.md`): берём / не берём / отложить,
   с причиной.
5. **Гипотеза** — в `lab/registry.json`, с ожидаемым исходом и отрицательным контролем.
6. **Внедрение и проверка** — код, тест, прогон; нет эффекта → пишется отказ (`F-0033`, `F-0034`,
   `C-0215`).

Правило исполняется гейтом **«решения»**: механизм нельзя внедрить, если в складе нет строки с
источником и отрицательным контролем. Гейт проверен отрицательным контролем самого себя
(`--self-test`: пять подложенных дефектов → пять отказов). Это защита от «правил по памяти» —
случая, когда описанного механизма в источнике не оказывается.

Текущий склад: 45 источников литературы, 38 ссылок на данные, 9 харнессов; 7 решений
(5 внедрено, 1 отклонено, 1 отложено).

## Куда движемся

Порядок выведен из цели, а не из интереса:

1. **Опора через ссылку** — если в ответе есть `файл:строка`, проверять, что в этой строке
   результата есть предмет вопроса. Третий случай одного класса (F-0037, F-0060, F-0068):
   модель ссылается на источник по-своему, а приёмка сверяет слова.
2. **Три режима** — план, автономное выполнение, долгосрочная цель (`docs/MODE-SPEC.md`,
   ждёт утверждения владельца).
3. **Запуск без человека** — закладка на источник вместо окна времени, журнал против повторов,
   «нечитаемо» как отдельный исход (F-07 в `research/INSIGHTS.md`).
4. **Свои инструменты и сеть** — агент пишет себе инструменты (F-05) и сам ищет в сети (F-06);
   обе требуют решения, где живёт исполнение кода.
5. **Программный вызов инструментов** — один шаг вместо десятка вызовов; здесь понадобится
   внешний разбор (F-04).

Список идей и их статусы — `research/INSIGHTS.md`; каждое решение — `lab/adoptions.json`.

## Три закона этого репозитория

1. **Число без команды — не результат.** У каждой цифры рядом команда и артефакт.
2. **Отрицательный результат остаётся.** `docs/eliminations.md`, `lab/failures/`, отклонённые
   решения в складе — не свалка.
3. **Каждый отчёт содержит раздел «что это не доказывает».**

Подробнее — `AGENTS.md`. Реестр утверждений — `CLAIMS.md`. Границы — `NOT-CLAIMED.md`.

**О названии.** `herness` — от «her» и «harness»: то, что впрягает в работу не вообще, а под
конкретного человека, с его границами.
