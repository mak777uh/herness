# herness — прибор границ истины

Харнесс нужен не для того, чтобы «быстрее писать код». Он нужен, чтобы **точнее очерчивать
границы истины**: какое утверждение чем подтверждено, где кончается проверенное и начинается
предположение, что именно мы не утверждаем.

Отсюда главное следствие: выход харнесса — не строчки кода, а **утверждения с типом
свидетельства** и явными границами. Код — побочный продукт.

## Что уже работает

Это не набор плагинов поверх чужого агента. Сейчас в репозитории свой, собранный с нуля контур:

- **своё ядро** Linux 6.18.60 (`core-rs/kernel/`), собрано из `tinyconfig` под одну задачу: без
  модулей, без SMP, с включёнными пространствами имён, cgroups, Landlock и ужесточениями;
- **комната**: система грузится этим ядром в QEMU, `init` — свой бинарь на Rust, а не shell.
  Внутри нет ни shell, ни coreutils: `init` сам монтирует `dev`, `proc`, `sys`, проверяет
  возможности, считает стоимость запуска процесса и ведёт журнал;
- **цикл** — в комнате (`core-rs/src/loopmod.rs`): модель отвечает одной строкой `TOOL <имя>
  <аргумент>` или `DONE <итог>`, цикл разбирает ответ, исполняет инструмент и пишет событие в
  журнал; у прогона есть бюджет по шагам, времени и деньгам;
- **инструменты** — свои, без внешних программ: `search`, `list`, `read` (с продолжением чтения),
  `write` внутри рабочего каталога, `seal` (запускает сам себя), `netprobe`; все ограничены
  рабочим каталогом;
- **мост наружу** (`bin/bridge.py`) — единственное место, где живёт ключ провайдера; комната
  говорит с ним plain HTTP, TLS и ключ остаются на хосте;
- **три слоя проверки**: форма (порядок событий), опора (ответ должен делить с журналом
  конкретное слово — цифру, путь, id), приёмка (`bin/accept.py`: критерий объявлен до прогона,
  лежит на хосте и проверяет вынесенный из комнаты журнал);
- **слой истины**: `CLAIMS.md` (164 утверждения с типом свидетельства и командой проверки),
  `NOT-CLAIMED.md`, гейты, отказы в `lab/failures/`, артефакты прогонов в `research/outputs/`.

Живой прогон выглядит так: задача уходит в комнату файлом, модель ищет и читает файлы
инструментами, после цикла журнал копируется на диск, хост монтирует образ и прогоняет критерий.
Последний измеренный прогон задачи «найди в `CLAIMS.md` утверждение типа `statistics`» дал PASS
за 2 шага и верный ответ `C-0021`; до него семь прогонов той же задачи дали FAIL с конкретными
причинами — серия записана в `research/outputs/live-runs.txt`.

## Что это не

- **Не работающий продукт.** Нет релиза, нет опубликованного бинаря, нет ни одного выполненного
  внешнего задания владельца. Это прибор и его проверки.
- **Не доказательство, что «плоскость свидетельств» — верное ядро.** Это выбранная предпосылка
  (ADR-0029).
- **Не харнесс, который «умнее».** Разница не в правильности ответов, а в том, что остаётся, чем
  проверить, и что сказано о границах.
- **Не полная изоляция.** Комната ограничена: нет shell, нет модулей ядра, инструменты не выходят
  из рабочего каталога, фильтр системных вызовов ставится, если ядро это умеет — и об этом
  честно пишется в журнал (`[песочница: фильтра нет, ядро без seccomp]`). Но это не защита от
  целенаправленного обхода и не доказательство безопасности.
- **Не «доказано, что задача решена».** Приёмка проверяет объявленные условия. Если критерий
  неполон, пройденный критерий этого не покажет: в прогоне PASS проверялась форма ответа (id вида
  `C-0123` и опора в журнале), а не то, что найденное утверждение действительно нужного типа.

Подробные границы — `NOT-CLAIMED.md`; отброшенные варианты — `docs/eliminations.md`; отказы —
`lab/failures/`.

## Как устроено

```
ядро 6.18.60 ──> init (Rust) ──> цикл ──> инструменты (search/list/read/write/seal)
                    │              │
                    │              └─ журнал HSJ1: запись с CRC, границы коммита, хвост не чинится
                    └─ песочница: namespaces, Landlock, seccomp (если ядро умеет)
                                   │
   хост: мост (ключ провайдера, TLS) <── plain HTTP ── комната
         приёмка (критерий в accept/) <── журнал, вынесенный на диск
```

## Структура

```
bin/                инструменты хоста: гейты и проверки (hs.py), мост, приёмка, доказательства
core-rs/            ядро, init, цикл, песочница, модели; сборка ядра и прогоны в QEMU
accept/             критерии приёмки: что считается выполненным (в комнату не попадают)
docs/               решения (ADR) и реестр исключённого
lab/                гипотезы, эксперименты, отказы, рецензии
research/outputs/   артефакты прогонов: то, на что ссылаются утверждения
CLAIMS.md           реестр утверждений: тип свидетельства, команда проверки, границы
NOT-CLAIMED.md      что мы сознательно не утверждаем
runs/               рабочие журналы прогонов (в git не едет)
```

## Быстрый старт

```
python bin/hs.py gates          # гейты: секреты, утверждения, ссылки, покрытие и другие
python bin/hs.py selftest       # негативные тесты самого инструмента
python bin/hs.py lab            # где мы сейчас и что дальше
python bin/accept.py accept/room-claims-statistics-v3.json <журнал.bin>   # приёмка прогона
```

Прогон в своём ядре (Windows + QEMU):

```
pwsh core-rs/run.ps1                       # собрать, загрузить, проверить ожидания
pwsh core-rs/accept-run.ps1 -Mode loop     # прогон с диском и приёмкой на хосте
pwsh core-rs/accept-run.ps1 -Mode loop-bridge -Kernel vmlinuz-own-net -Net -Task "..."
```

## Где смотреть доказательства

- `CLAIMS.md` — каждое утверждение с типом и командой; число без команды не считается результатом.
- `research/outputs/` — артефакты: живые прогоны, замеры ядра, отказы инструментов.
- `docs/ADR-*.md` — почему сделано так, включая цену и отвергнутые варианты.
- `lab/failures/` — что сломалось на самом деле и как это нашли; отказ — первоклассный документ.

## Принципы

- [docs/PRINCIPLES.md](docs/PRINCIPLES.md) — 25 принципов портфеля: что запрещают, чем
  принуждаются, каким негативным тестом проверяются.
- `refs` — репозитории как постоянный справочник: ключевые документы синхронизируются в
  `refs-cache/` с дайджестами, поиск идёт локально и воспроизводимо.

## Как мы выбираем

Заимствования проверяются на соответствие задаче, а не на репутацию: [docs/FIT-CHECK.md](docs/FIT-CHECK.md).
Где мы сейчас — `docs/CYCLE.md` и `lab/registry.json`.

## Что это за софт

Единица продукта — не задача, а **граница**: что человек готов делать, с кем и на каких условиях.
Полное определение — [docs/PRODUCT.md](docs/PRODUCT.md).

## Куда это ведёт

Дальняя цель — [docs/VISION.md](docs/VISION.md): узлы, которые договариваются о правилах и
объявляют **свои** границы заранее, а взаимодействие опирается на проверяемые утверждения.

## Три закона этого репозитория

1. **Число без команды — не результат.** Любая цифра в доке имеет рядом команду и артефакт.
2. **Отрицательный результат остаётся.** `docs/eliminations.md` и `lab/failures/` — не свалка.
3. **Каждый отчёт содержит раздел «что это не доказывает».**

Подробнее — `AGENTS.md`. Реестр утверждений — `CLAIMS.md`. Границы — `NOT-CLAIMED.md`.

**О названии.** `herness` — от «her» и «harness»: то, что впрягает в работу не вообще, а под
конкретного человека, с его границами. На слух остаётся прежнее «harness», поэтому старое имя не
потеряно.
