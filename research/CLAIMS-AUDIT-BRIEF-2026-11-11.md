# Бриф внешнего claims-аудита — 11.11.2026

Один самодостаточный блок для вставки во внешний исследовательский интерфейс. Контекст нейтральный,
без наших вердиктов и без подсказок «где искать». Задача — независимая проверка реестра утверждений
по коду и свидетельствам. Формат находок строгий; каждая — с локальным фальсификатором.

Снимок репозитория для аудитора: `claims-audit-snapshot-2026-11-11.tar.gz` (рядом). Что в нём и что
вырезано — см. `SNAPSHOT-MANIFEST.txt` внутри. Снимок отражает рабочее дерево; наши verdict-файлы
(план аудита, карточки отказов, реестр экспериментов, NOT-CLAIMED, ADR/решения, статусы) вырезаны
намеренно, чтобы не задавать готовых выводов.

##BEGIN ВСТАВКИ

Ты — независимый аудитор реестра утверждений. Ниже описан продукт, формат реестра и механизм его
проверки. Твоя задача — найти, где утверждение **не поддержано** своим свидетельством или кодом, а не
согласиться с реестром. Приоритет: воспроизводимые улики (файл:строка, вывод команды), не мнения.
Не додумывай. Если свидетельства не хватает — скажи прямо. Без патчей, без оценок стиля.

### Контекст продукта (нейтральные факты)

Система — «харнесс»: изолированная среда для LLM-агента с формальным слоем истины.
- **Ядро**: ~3000 строк Rust (`core-rs/src`): политика доступа, посредник инструментов, append-only
  журнал событий, рабочий цикл. Заголовок записи журнала: len(u32)+seq(u64)+crc(u32)+kind(u8);
  «crc» — усечённый SHA-256 (4 байта).
- **Хост**: Python 3.13 (`bin/`): приёмка прогонов, гейты, извлечение журнала из образа, сетевой
  инструмент с SSRF-фильтром (`bin/net_policy.py`, `bin/net.py`).
- **Доказательства**: Lean 4 (`proofs/`, чистый core, `lake-manifest.json` packages: []), toolchain
  v4.36.0-rc2. Доказаны свойства модели политики/посредника/моста.
- **Комната**: QEMU на Windows-хосте, гость Linux без шелла; образ raw ext4.
- **Измерения**: приёмка задач агентом (PASS/FAIL/UNKNOWN), серии прогонов, метрики.

### Формат реестра `CLAIMS.md`

Таблица, 7 колонок: `id | утверждение | тип | команда | артефакт | дата | ожидание`.
- **тип** задаёт предельную силу формулировки. Пять типов:
  - `proof` — машинно-проверенное доказательство → «доказано для указанной формализации»;
  - `test` — воспроизводимый прогон с оракулом → «на этом входе получен этот результат»;
  - `statistics` — измерение с бюджетом и разбросом → «p50/p95 такие-то на таком-то железе»;
  - `observation` — единичное наблюдение → «наблюдали один раз при таких условиях»;
  - `judgment` — суждение владельца → «считаем разумным, не проверено».
  Формулировка сильнее типа — дефект.
- **команда** — как воспроизвести свидетельство.
- **артефакт** — файл или каталог прогона, где лежит свидетельство.
- **ожидание** — регулярное выражение, которому обязан соответствовать вывод/артефакт. Пустая
  ячейка = «сверяется только код возврата».

### Механизм проверки (как он устроен, без оценок)

`bin/check_artifacts.py C-XXXX`: читает строку реестра, берёт колонку «артефакт» и колонку
«ожидание», ищет регулярное выражение ожидания в тексте артефакта (файл целиком или все
`.txt/.jsonl/.json/.md/.log/.sql` файлы каталога). Выход 1, если не нашлось.
Свойства механизма, которые тебе важно учитывать:
1. Он **не перезапускает команду** — только ищет ожидание в уже лежащем артефакте.
2. Он сверяет **ожидание ↔ артефакт**, но **не** сверяет **текст утверждения ↔ артефакт** и **не**
   сверяет **команда ↔ артефакт** (производит ли команда именно этот артефакт).
3. Артефакт может быть старше кода/утверждения (дата в колонке «дата» vs текущее состояние кода).
4. Регулярное выражение может совпасть с артефактом по иной причине, чем задумано (например, число
   из другого среза/знаменателя).

### Что проверить (классы дефектов)

Для каждой строки реестра (или репрезентативной выборки, если строк много — укажи, какой) проверь:
- **A. Сила формулировки vs тип**: текст утверждает больше, чем разрешает тип (например, `observation`
  со словом «доказано»/«всегда»; `judgment` подан как измерение; `test` на одном входе обобщён на все).
- **B. Текст ↔ артефакт**: текст описывает один срез/знаменатель/условие, а артефакт содержит другой
  (например, текст про подвыборку, артефакт про полную выборку; текст «0 ложных», артефакт «2 ложных»).
- **C. Команда ↔ артефакт**: указанная команда не производит этот артефакт / не проверяет то, что
  заявлено (команда ищет ожидание в файле, но не воспроизводит измерение).
- **D. Устаревание**: артефакт/дата старше изменения кода, на который ссылается утверждение; число
  могло измениться с тех пор.
- **E. Число без команды**: в тексте есть величина, для которой нет воспроизводимой команды/артефакта.
- **F. Ложное совпадение ожидания**: регулярное выражение ожидания совпадает с артефактом по неверной
  причине (другой срез, другое поле, подстрока).
- **G. Ссылка в пустоту**: артефакт/команда/файл отсутствует в снимке (отметь «не предоставлено», не
  выдумывай содержимое).

### Формат ответа (строго)

На каждую находку — одна запись:
`№ | id утверждения | класс (A–G) | улика (файл:строка или вывод команды) | что это НЕ доказывает | локальный фальсификатор (команда/шаг, которым находку можно опровергнуть) | уверенность (высокая/средняя/низкая)`

В конце — три раздела:
- **«Не проверено / не предоставлено»** — какие утверждения/артефакты остались без проверки и почему.
- **«Противоречия»** — где улики расходятся между собой.
- **«Выборка»** — если проверял не всё: сколько строк проверено, по какому принципу отобраны.

Не предлагай исправлений и не выноси итоговых оценок «реестр хороший/плохой». Только находки с
уликами. Если для проверки критически не хватает данных — **одним** сообщением перечисли, что именно
нужно (не более 5 пунктов), без промежуточных отчётов.

## Заметки для владельца (не для вставки)

- Бриф намеренно **не называет** конкретных подозрительных строк: аудитор должен найти их сам, без
  наших вердиктов (дисциплина «внешней модели — одна инструкция без наших вердиктов»).
- Известные нам расхождения (например, текст↔артефакт у одного утверждения о MuSiQue) в бриф не
  внесены — это и есть проверка, найдёт ли их независимый аудитор. Возврат сверять по коду, не
  принимать на веру.
- Снимок вырезает наш verdict-слой; измерительные артефакты (`research/outputs/`) оставлены — это
  свидетельства, без которых проверка невозможна. Если аудитор сообщит «артефакт не предоставлен»
  для строки, чей артефакт мы вырезали, — это ожидаемо, не дефект реестра.
- Возврат аудитора ложится в реестр находок только после локальной проверки каждой строки
  (закон «число без команды — не результат»).
