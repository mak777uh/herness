# Журнал харнесса: формат и что уже проверено (31.10.2026)

Реализация: `core-rs/src/journal.rs`. Решения взяты из P20, а не из вкуса.

## Формат

```
файл:  "HSJ1" | version u32
запись: len u32 | seq u64 | crc u32 | kind u8 | payload[len]
kind: 1 = данные, 2 = коммит
```

Почему так (что подсказал разбор WAL/Kafka/etcd):

| решение | откуда |
|---|---|
| заголовок с magic и версией | SQLite WAL (magic + version), Firecracker (magic + версия формата) |
| длина записи в заголовке | Kafka (длина+CRC), etcd (длина 56 бит) |
| CRC на запись | Kafka CRC-32C, etcd цепочечный CRC, SQLite накопительная сумма |
| **отдельная запись-коммит** | SQLite: границу задаёт только кадр с `nTruncate ≠ 0`; «запись есть» ≠ «подтверждена» |
| остановка на первой невалидной записи | SQLite `walIndexRecover`, Kafka recovery |
| карантин вместо автопочинки | наша практика (`verify_journal`), подтверждена etcd `Repair` (лечит только `ErrUnexpectedEOF`) |

## Что проверено

**Тесты (5/5, `cargo test --lib`):**
- append + коммит + чтение;
- **оборванный хвост**: обрезали файл внутри записи → валидный префикс = 1 запись, хвост обнаружен,
  карантин создан, **сам журнал не изменён** (починки нет);
- **порча**: испорчен последний байт записи → чтение останавливается, запись не считается валидной;
- **плохой magic** → отчёт «нет заголовка»;
- **граница коммита**: три записи без коммита дают `committed = 0`.

**В реальной системе (QEMU, своё ядро 6.18.60):**
```
журнал: записей 4, коммитов 1, хвост 0 байт, статус ок
```

## Чего пока нет

1. **Диск.** Журнал писался в `/journal.bin` внутри initramfs (это RAM). `fsync` там ничего не значит.
   Настоящая проверка долговечности — ext4 на virtio-blk, и это следующий шаг.
2. **Инъекция обрыва в реальной системе.** Юнит-тест режет файл руками; опыт Q4 требует убить ВМ
   посреди записи и посмотреть, что найдётся при следующем старте.
3. **Политика пакета.** `maybe_sync(n)` есть, но замеров «N записей или T мс» на реальном диске нет.
4. **Каталог.** `fsync` каталога после `rename` не реализован — пригодится, когда появится публикация
   файлов состояния.

## Следующий опыт (Q1 + Q3 + Q4 сразу)

Прицепить диск: `qemu -drive file=journal.img,format=raw,if=virtio`, в init — смонтировать ext4, писать
журнал туда, затем убить ВМ по таймеру посреди записи и при следующем старте проверить:

- найден ли оборванный хвост;
- сколько записей потеряно при `fsync` на каждую против пакета;
- сколько событий в секунду даёт каждый режим.
