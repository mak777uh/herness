# P32 — разбор: конвейер доверия для инструментов агента

**Дата:** 07.11.2026. **Материал:** четыре ответа на задание P32 (три независимых прохода + один
структурированный). **Правило:** чужие числа — вторичны; в `CLAIMS.md` идут только наши измерения.

## 1. Главный результат: нашёлся источник «96,8 %»

В прошлом разборе (P31) число «96,8 % синтезированных инструментов с нулевым конформансом» стояло
**без источника**. Теперь источник есть, и он подтверждается дословной цитатой из таблицы:

**EvolveTool-Bench, arXiv 2604.00392v2** («Beyond Task Completion: A Verification-vs.-Conformance
Gap in Tool-Evolving Agents»).

| протокол | инструментов | средний C | средний R | C = 0 |
|---|---|---|---|---|
| One-Shot | 119 | 0.000 | 0.518 | 100 % |
| ToolMaker-style | 19 | 0.000 | 0.526 | 100 % |
| CREATOR-style | 84 | 0.049 | 0.536 | 91,7 % |
| **всего** | **222** | **0.018** | **0.525** | **96,8 %** |

Что это значит **точно**: инструмент исполняется без ошибок (R ≈ 0,52), но на отложенных входах
даёт **неверный ответ** (C = 0). Это не «падает», а «врёт уверенно». Ручные эталоны проходят все
16 наборов с C = 1.00.

**Границы, которые надо держать в голове:** одна модель (Claude Haiku 4.5), три seed, 8 сессий;
авторы сами пишут, что это пилот, а не приговор протоколам.

## 3. Что не измерено (в план как факт не идёт)

- **Wasm внутри минимальной ВМ** — прямых замеров нет; есть Wasmer вне браузера (5–10×),
  WaSC (старт 15 мс, WASI-путь 3,2×), но это другие конфигурации;
- **Starlark против Wasm** — сопоставимых чисел нет; starlark-go прямо пишет, что память потока
  не ограничивается;
- **поиск по контракту против поиска по имени** — не измерено; CRAFT показывает обратное:
  удаление **имени функции** из поиска роняет точность на 6,6 п.п.;
- **польза canary и хешей среды** — механизм описан, чисел нет;
- **композиция A∘B против создания нового** — не измерено;
- **сеть: выгода на принятый результат** — не измерено; измерены только риски (AgentDojo: 97 задач,
  629 кейсов; фильтр инструментов снижает ASR до 7,5 %);
- **прямое сравнение «инструмент против правила протокола»** — не найдено ни в одном ответе.

## 4. Что противоречит нашим планам

**CRAFT (ICLR 2024):** рост набора инструментов 0 → 261 → 337 → 525 **повышает** точность, а
удаление имени функции из поиска роняет её на 6,6 п.п. То есть «большая библиотека плоха» —
не универсально, а **поиск по контракту вместо имени — не подтверждён**.

Это прямо спорит с нашим F-12 (pre-flight по контракту). Вывод: **имя инструмента оставить в
поиске**, контракт добавить как второй канал, а не замена.

## 5. Что берём в план (три механизма, с отрицательным контролем)

| механизм | источник | отрицательный контроль |
|---|---|---|
| **отложенный конформанс до повторного использования** | EvolveTool-Bench (96,8 %), ToolMaker (12/15) | инструмент, захардкодивший пример, и константа-заглушка обязаны провалить новые входы; ручной эталон — пройти |
| **отказ как протокол** | ImpossibleBench (обход 54 % → 9 % при опции отказа), METR (30,4 %) | невыполнимая задача: «готово» на ней означает обход |
| **протухание по событию, не по календарю** | Maven (треть релизов ломает), BreakGuard (27/89, ~$0,90) | подменить зависимость на идентичную — отзыва быть не должно; подложить изменение поведения без изменения сигнатуры — должен быть |

## 6. Порядок, который я предлагаю

Совпадает с P31, но с поправкой из CRAFT:

1. реестр инструментов append-only с хешем среды;
2. pre-flight: поиск по **имени и контракту** (не только контракту);
3. canary + `stale` на существующих инструментах;
4. ограниченный рабочий набор и архив;
5. **только потом** синтез.

## 7. Границы этого разбора

Все четыре ответа — обзоры литературы, а не наши замеры. Наши числа (pass@1 0.71, pass^2 0.49,
ложных «готово» 0.03, 70 отказов, 2 правила протокола) — единственное, что проверено исполнением.
Чужое число становится фактом только после того, как мы воспроизвели его у себя.
