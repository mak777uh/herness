# Что берём из `chaitin/MonkeyCode`: разбор

**Дата:** 08.11.2026. **Источник:** `chaitin/MonkeyCode`, лицензия AGPL-3.0.

**Прочитано:** `README.md`, `README.monkeycode.md`, `monkeyai/README.md`,
`monkeyai/backend/README.md` — целиком.

**Не прочитано:** исходный код (`internal/*`, `admin/*`, `frontend/*`), OpenAPI-контракты,
`design/*.md`. Выводы ниже — **по документации**, а не по коду. Где документ утверждает
поведение, которое я не проверял в коде, это помечено.

**Что это за проект (важно).** Репозиторий переименован: сейчас это «百智办公 · MonkeyAI» —
корпоративная AI-платформа для офиса (PPT, документы, таблицы, дизайн) с управлением
командой, биллингом и приватным развёртыванием. Прежний MonkeyCode (AI-платформа для
разработки) сохранён отдельным описанием `README.monkeycode.md`. Одно репозиторий, два
продукта, общее ядро.

**Почему это вообще интересно нам.** Это не харнесс и не про верификацию. Это чужой опыт
про **честный учёт того, что нельзя знать заранее** — стоимость вызова, успех доставки,
целостность артефакта. Ровно та же задача, что у нас с тремя исходами и ценой успеха.

---

## Что забираем: четыре механизма

### 1. Неизвестное не выдаётся за известное (главное)

У них платный вызов модели может закончиться так, что **стоимость неизвестна**: нет usage,
оборвался ответ, не пришёл идентификатор. Правило: такой вызов **нельзя списать по оценке**.
Он уходит в «待核查» (ожидает проверки), а не в «списано по расчёту».

Дословно из их документа: *«上下文上界错误、缺失用量或实际费用超出预留都会转待核查，
不能按估值扣款»* — ошибка границы контекста, отсутствие usage или превышение резерва
переводятся в ожидание проверки, **списывать по оценке нельзя**.

Это в точности наш §2, только у нас три исхода проверки, а у них — три исхода расчёта.
**Забираем формулировку**: оценка не становится фактом от того, что другого числа нет.

**Чем у нас проверяется:** `bin/accept.py` (вердикт `UNKNOWN` при отсутствии инструмента),
`bin/check_room_verdict.py` (пустой ответ не PASS). Механизм есть; **не хватает правила**
«оценка стоимости прогона не пишется как расход» — см. ниже, чего не хватает.

### 2. Идемпотентность платного действия

У них: `Idempotency-Key` — повторный запрос возвращает **исходный** идентификатор транзакции
и `409`, а не выполняет действие второй раз. Плюс `X-Billing-Transaction-ID` связывает ответ
с реальной транзакцией.

Для нас это прямо про `AGENTS.md` §1 (деньги) и §12 (порог до прогона): **повтор прогона
не должен тратить деньги второй раз молча**. Сейчас у нас журнал `transfers.jsonl` есть, а
ключа идемпотентности на прогон — нет.

**Забираем:** у прогона появляется `run_id`, и повторная запись расхода с тем же `run_id`
не создаёт вторую запись, а возвращает первую. Цена — одна колонка в журнале и проверка
при записи.

### 3. Неизменяемые артефакты и версии с ETag

У них каждый ресурс (настройки, модели, правила, навыки, эксперты, коннекторы) отдаётся
отдельным эндпоинтом со **своим SHA-256 и ETag/304**. Навык проверяется по размеру и
SHA-256 перед выдачей; повреждённый пакет **отклоняется**, а не отдаётся.

Для нас: это то же, что наша опора (`--anchor`), но применённое к **выдаче** ресурса, а не
к проверке утверждения. Полезная мысль: **версия ресурса считается на стороне того, кто
его хранит**, а не того, кто его просит.

**Забираем частично:** у нас уже есть `evidence/` с отпечатками. Нового механизма не нужно;
нужно правило — при выдаче файлов комнате (образ `share.img`) сверять отпечаток, а не только
число файлов. Сейчас `build_room.py --check` сравнивает **количество**, а не содержимое.

### 4. Снапшот вместо живой ссылки

У них дизайн-ресурсы сохраняются **неизменяемым снапшотом**, старые снапшоты остаются;
удаление из хранилища запрещено в транзакции записи, чтобы не сломать бэкап или идущую
загрузку.

Для нас: это ровно наш принцип «опровергнутое не удаляется, а переезжает» (`CLAIMS.md` →
`docs/eliminations.md`). Подтверждение, что принцип рабочий, — но **нового брать нечего**.

## Чего НЕ берём и почему

**Архитектуру.** Go + PostgreSQL + sqlc + миграции + RustFS + Nginx — это стек
корпоративного веб-продукта. Наш харнесс — Rust-ядро и комната с собственным ядром. Копировать
их структуру значило бы подменить нашу задачу их задачей.

**Биллинг.** У них сложная система: группы, квоты, период в шанхайском часовом поясе,
резерв и подтверждение, кошелёк. Нам нужен один журнал и одна формула
`CostPerVerifiedSuccess`. Их модель решает другую задачу — учёт для команды людей.

**Код.** Лицензия **AGPL-3.0**: использование, изменение и распространение обязывают
раскрывать исходники производной работы по той же лицензии. Для нас это неприемлемо —
наш репозиторий публикуется на своих условиях. **Код не копировать, брать только идеи.**

**Их «AI 并行开发边界»** (границы параллельной разработки агентами: один бизнес-каталог на
задачу, общие точки меняются сериализованно) — идея хорошая и знакомая нам по правилу
«один вопрос — одно изменение». Нового нет.

## Чего не хватает у нас (найдено этим разбором, проверено)

Три пункта; каждый проверен командой, а не взглядом:

| что | проверка | результат |
|---|---|---|
| расход прогона без ключа идемпотентности | `transfers.jsonl`: 149 строк, у каждой есть `tx`, но **ни у одной нет `run_id`** | подтверждено |
| `build_room.py --check` сравнивает число файлов, а не содержимое | `bin/build_room.py:91-97` — `count_image` против `count_host`, хешей нет | подтверждено |
| оценка стоимости не отделена от факта | журнал прогона: `step 1, потрачено 0.00003291` — одно число без пометки «оценка» | подтверждено |

**Почему это дефекты, а не придирки.**

1. **Повтор прогона может записать деньги дважды.** `tx` — это идентификатор транзакции в
   сети, он уникален постфактум. Но если агент повторит запись расхода за тот же прогон,
   проверки «это уже записано» нет: ключа прогона в журнале не существует.
2. **Образ комнаты может разойтись по содержимому.** `--check` скажет «совпадает», если число
   файлов то же. Подменённый файл при неизменном количестве пройдёт проверку — это тихий
   пропуск, то есть UNKNOWN, выданный за PASS.
3. **«Потрачено» без пометки — это факт по виду и оценка по сути.** У нас §5 требует
   `CostPerVerifiedSuccess` из **всех расходов**; число, полученное оценкой, в знаменатель
   такого показателя идти не должно без пометки.

## Границы этого разбора

- Выводы **по документации**, код не читал. Утверждения вида «у них реализовано так» —
  это их собственное описание, не моя проверка.
- Репозиторий **переименован и сменил продукт**; старый MonkeyCode — в отдельном файле.
  В справочнике лежит под `chaitin/MonkeyCode`.
- Лицензия AGPL-3.0 — **код не берём**, только идеи.
- Числа (звёзды, активность) не проверял: GitHub API из этого окружения отдаёт HTML вместо
  JSON, то есть хост блокируется — это UNKNOWN, а не «проект мёртв».
