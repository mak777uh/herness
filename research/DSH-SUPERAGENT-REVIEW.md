# Разбор: deepseek-ai/dsh-superagent-prototype

**Источник:** https://github.com/deepseek-ai/dsh-superagent-prototype (MIT, TypeScript, бандл для
DeepSeek Harness). Добавлен в справочник: `python bin/hs.py refs add <url>` → `refs-cache/`.
**Что прочитано:** README, `docs/003-execution.md`. Остальные документы (000 philosophy, 001 domain,
002 authorization, 004 prompts, 005 panel, 006 deployment, 007 architecture, 008 cookbook) не
читаны — это граница разбора, а не полнота.

## Как устроено

Агент на один GitHub-репозиторий. Слушает GitHub и (опционально) Feishu → из разрешённого
обращения открывает **Ticket** → заводит отдельную сессию `worker-<id>` и каталог → работает →
отвечает в исходной ветке обсуждения (обычно pull request) → панель показывает, где нужен человек.

Три вещи, которые стоит разобрать отдельно.

**1. Стадия Ticket — это «чего он ждёт», а не «что он делает».** Таблица стадий читается сверху
вниз, первое совпадение выигрывает: `person / delivery`, `person / answer`, `person / review`,
`person / blocked|failed`, `working / queued`, `idle`, `working`. Стадия вычисляется из последнего
Report + пришедших Input, а не хранится отдельным полем, — поэтому перезапуск её не теряет.

**2. Report — типизированный исход, а не свободный текст.** Словарь: `ready`, `blocked`, `failed`,
`dropped`, `waiting`. «Awaiting review» — это `ready` с pull request; «Nothing to do» — `dropped`.
Именно типы, а не разбор фраз, двигают стадию.

**3. Работа, влияющая на мир, сначала записывается, потом делается.** Реlea, доставка Input, запуск
Assignment — всё хранится до выполнения; отказ повторяется с удвоением паузы (2 с → минута);
ошибкой системы считается только три отказа подряд. При перезапуске Assignment получает
**recovery note**: проверить каталог, историю git и GitHub, прежде чем повторять внешнее действие.

## Что взять себе (по возрастанию цены)

1. **Типизированный исход вместо свободного текста.** У нас `DONE <итог>` — и всё. Стоит добавить
   `BLOCKED <вопрос>` и `NO-WORK <почему>`: тогда «нужен человек» станет состоянием, а не текстом,
   и приёмка сможет отличать «не смог» от «нечего делать». Цена: словарь в `parse_step` + строки в
   журнале + условие в критерии.
2. **Recovery note при продолжении.** У нас есть «продолжение: шагов N…», но нет требования
   проверить сделанное до повторения. Одна строка в подсказке при resume — прямо из их документа.
3. **Стадия из журнала, а не из переменной.** У нас статус собирается в трёх местах
   (`Outcome.status`, `accept.status()`, строки прогона). Их приём «первое совпавшее условие» даёт
   один вывод из одного источника.
4. **Человек не встаёт в очередь.** У них есть дополнительный слот для сообщения человека: новая
   работа не может заблокировать продолжение уже начатого. Нам это понадобится, если появится
   интерактив.

## Чего не брать

- **Слияние по подсказке.** Auto-merge у них решается текстом промпта, хост не имеет логики
  слияния; в документе честно написано: «These instructions govern the agent, not GitHub's merge
  rules». Это тот самый случай, который мы отвергли: суждение вместо механизма.
- **«Обёртки задают умолчания, а не границу».** У них worker работает без подтверждений от имени
  OS-пользователя оператора и может запустить программу по абсолютному пути — и это написано
  прямым текстом. У нас граница другая (своё ядро, нет shell, инструменты в рабочем каталоге),
  и менять её на «удобство» не надо.

## Что это меняет у нас

Ничего в архитектуре; две вещи в очереди: типизированный исход и recovery note. Обе — дешёвые и
проверяемые, и обе про то же, зачем проект: чтобы «готово» было состоянием с условиями, а не словом.
