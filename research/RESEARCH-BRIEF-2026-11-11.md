### Контекст продукта (нейтральные факты)

Система — «харнесс»: изолированная среда для LLM-агента с формальным слоем истины.
- **Ядро**: ~3000 строк Rust (`core-rs`): политика доступа, посредник инструментов, append-only журнал событий, рабочий цикл. Журнал: заголовок len(u32)+seq(u64)+crc(u32)+kind(u8); «crc» — усечённый SHA-256 (4 байта); kind дописывается после хеша. В коде записи нет fsync.
- **Комната**: QEMU 11.1.0 на Windows-хосте, гость Linux без шелла/coreutils. Образ raw, `-drive file=...,format=raw,if=virtio` (параметр `cache=` не задан). ВМ завершается жёстко (TerminateProcess). Сеть: `-netdev user,restrict=on,guestfwd=tcp:10.0.2.15:PORT-cmd:python relay.py` — единственный канал к хостовому мосту; на Windows-сборке канал не поднимается (Connection refused, 5 вариантов), без `restrict=on` работает.
- **Хост**: Python 3.13 (`bin/`): приёмка прогонов, гейты, извлечение журнала из образа через WSL (`e2fsck -fy` + `mount -o loop`). Инструмент `net` ходит только к мосту; SSRF-фильтр проверяет схему/credentials/локальные имена/порты/классы IP/каждый редирект; DNS этой машины возвращает 198.19.x для всех доменов (перехват), в фильтре есть исключение для 198.18.0.0/15 (RFC 2544); пиннинга адреса сокета нет.
- **Доказательства**: Lean 4 (`proofs/`, чистый core, `lake-manifest.json` packages: []), toolchain v4.36.0-rc2 в WSL. Доказаны свойства модели политики/посредника/моста; соответствие модели и Rust-кода проверяется только тестами и сверкой. Два модуля объявляют тип `Effect` в корневом пространстве имён → агрегат `Proofs` не собирается. В WSL также установлен mathlib (в составе другого проекта).
- **Измерения**: приёмка задач агентом. Одна задача даёт PASS/FAIL в разных прогонах при одном критерии. Режим отказа — молчание (агент не заявляет результат), не ложное «готово» (false_completion_rate=0 на 20 журналах). Серии: new10 9/10; MuSiQue нестабильно. Флак проверяется 3 повторами. Есть скрипт `durability.ps1`: две политики (fsync на коммит vs пакет), убийство ВМ, чтение после.
- **Видение владельца**: формально доказанные отношения между потоками и границами → части взаимозаменяемы, даже ядро можно заменить, сохранив работоспособность. «Пулы законов» для отношений человек↔человек↔сервис; мосты не могут соединиться, если противоречат пулу (в модели есть `Effect.deny` и `Effect.duty`). VecDHT — сеть, где узлы находят друг друга по смыслу; развитие в «интернет, принадлежащий людям», коллективный p2p-хостинг. Сейчас VecDHT — служба обнаружения пиров, не транспорт.

### Вопросы (по убыванию цены ошибки)

**1. QEMU: cache-режим, fsync и жёсткое убийство ВМ на Windows.**
Контекст: `-drive ...if=virtio` без `cache=`; ВМ убивается TerminateProcess; в журнале гостя нет fsync; наблюдаются оборванные хвосты журнала и нестабильный вердикт задачи (FAIL 190s vs PASS 4 шага); есть `durability.ps1`.
Вопросы: (a) какой cache-режим у `-drive` по умолчанию и что он гарантирует при flush/FUA гостя; (b) что теряется при жёстком убийстве процесса QEMU на Windows при `cache=writeback/writethrough/none` и разных политиках fsync гостя; (c) проходит ли virtio-blk flush гостя к хостовому fsync на Windows-хосте; (d) какой режим рекомендован для экспериментов crash-consistency; (e) известные баги QEMU Windows с virtio-blk flush.
Разблокирует: протокол долговечности, диагноз флака, формат журнала.
Источники: QEMU docs (block drivers, cache modes), qemu-devel, virtio spec (flush/FUA), MS docs (TerminateProcess, FlushFileBuffers).

**2. Верификация реального Rust и взаимозаменяемость частей.**
Контекст: ядро ~3k строк Rust; Lean-модели доказаны, соответствие модели и кода — только тесты; видение: доказанные отношения → заменяемое ядро.
Вопросы: (a) инструменты верификации/трансляции реального Rust — Aeneas (Rust→Lean/Coq), hax (Rust→F*/Coq/SSProve), Creusot (Rust→Why3), Verus, Kani: зрелость, поддержка Lean 4, объём усилий на ~3k строк, какие свойства доказуемы (memory safety, функциональная корректность, refinement); (b) архитектурный паттерн «spec↔impl refinement + заменяемые компоненты»: как seL4, CompCert, CertiKOS, Fiat-Crypto организуют доказательство соответствия и замену частей; assume-guarantee, interface automata, refinement calculus — что применимо; (c) прецеденты «доказанно заменяемого ядра» в реальных системах.
Разблокирует: выбор пути моста Lean→C→Rust vs трансляция Rust→Lean; ADR о верификации ядра; дорожная карта видения.
Источники: GitHub/доки проектов, статьи POPL/PLDI/CAV/ITP, seL4/CompCert docs.

**3. QEMU Windows: единственный канал хост↔гость.**
Контекст: `guestfwd=tcp:...-cmd:python relay.py` на QEMU 11.1.0 Windows не поднимает канал; без `restrict=on` работает; комната должна не иметь выхода наружу, кроме моста.
Вопросы: (a) известные проблемы `guestfwd`/`-cmd` на Windows-сборках QEMU, статус в 11.x; (b) альтернативные единственные каналы на Windows без админ-прав: `hostfwd` (обратное направление: хост→гость), virtio-serial/virtconsole, vsock (поддержка Windows?), 9p/virtfs, qemu-guest-agent, SMB; (c) что совместимо с `restrict=on`; (d) рекомендуемая схема «одного канала» для изолированной комнаты.
Разблокирует: этап изоляции комнаты, архитектура канала.
Источники: QEMU docs (net, guestfwd, hostfwd, virtio-serial, vsock, 9p), qemu issue tracker, Windows build notes.

**4. SSRF: канонический фильтр, DNS-rebinding, исключение перехвата.**
Контекст: Python-хост; фильтр проверяет схему/credentials/имена/порты/классы IP/редиректы; DNS возвращает 198.19.x; исключение для 198.18.0.0/15; пиннинга сокета нет.
Вопросы: (a) канонический дизайн SSRF-фильтра (порядок проверок, классы IP, IPv6-mapped/transition, десятичные/octal/hex IP, 0.0.0.0, [::], URL-parser differentials, цепочки редиректов); (b) DNS-rebinding: как правильно пиннить резолв в Python (stdlib urllib/socket, requests/urllib3, httpx, pycurl RESOLVE) — готовые библиотеки/паттерны; (c) безопасное оформление исключения для DNS-перехвата в RFC2544-диапазоне: как отличить литеральный URL от результата резолва, чтобы не открыть обход; (d) известные обходы фильтров с per-redirect проверкой.
Разблокирует: hardening net-инструмента, негативные тесты.
Источники: OWASP SSRF, PortSwigger research, RFC 2544/6890, urllib3/httpx docs, CVE/writeups rebinding.

**5. Чтение грязного ext4 без модификации оригинала.**
Контекст: журнал извлекается из raw-образа ext4 через WSL; сейчас `e2fsck -fy` + `mount -o loop`; ВМ убита жёстко → ext4 «грязная»; нужно читать, не меняя оригинал и не получая устаревшие данные.
Вопросы: (a) `debugfs -R "dump"` на грязной ext4 — читает ли без модификации, видит ли незакоммиченные транзакции журнала; (b) `mount -o ro,noload` на грязной ext4 — риск устаревших данных, какие именно; (c) e2fsck на копии vs оригинал — гарантия неизменности оригинала; (d) чистый экспорт из гостя до убийства: fsfreeze + qemu-guest-agent, 9p/virtio-fs, sync + отдельный канал; (e) форензик-best-practice чтения грязного ext4 без записи (software write-blocker).
Разблокирует: read-only приёмка, текст ADR.
Источники: ext4 kernel docs, e2fsprogs/debugfs man, qemu-guest-agent docs, forensic write-blocking literature.

**6. Статистика нестабильных вердиктов агента.**
Контекст: одна задача PASS/FAIL в разных прогонах; режим отказа — молчание; флак проверяется 3 повторами; серии new10 9/10, MuSiQue нестабильно.
Вопросы: (a) сколько прогонов нужно для устойчивого вердикта и как считать доверительный интервал (pass@k unbiased estimator — HumanEval/Codex; биномиальные CI; sequential testing / SPRT для флаки-тестов); (b) литература по flaky-test detection и root-cause (deterministic replay, seed control); (c) метрики ложного завершения/молчания в agent-eval (SWE-bench, tau-bench, AgentBench, METR) — как измеряют; (d) достаточно ли 3 повторов и какой протокол рекомендован.
Разблокирует: протокол измерений стабильности, переносимость вердиктов.
Источники: HumanEval paper (pass@k), flaky-test surveys (ICSE/FSE), agent benchmark docs, METR methodology.

**7. Lean 4 CI без mathlib и конвенции имён.**
Контекст: `proofs/` чистый core Lean (packages: []), rc2 в WSL; корневой конфликт `Effect`; скрипты зовут Windows lake.exe (Windows-elan нет); в CI Lean проверяется по артефакту, не вживую.
Вопросы: (a) best practice Lean 4 CI на GitHub Actions без mathlib: установка elan/toolchain, кэш .lake, готовые actions; (b) пиннить rc2 или ждать stable — риски rc-тулчейна для доказательств; (c) конвенции пространств имён / module system Lean 4 (public/import all), чтобы избежать корневых конфликтов; (d) гейт `#print axioms` в CI; (e) если позже понадобится mathlib — `lake exe cache get` в CI, стоимость.
Разблокирует: оживление Lean-контура, ADR namespaces, CI job.
Источники: Lean 4 docs (module system, lake), leanprover GitHub, mathlib CI docs, elan.

**8. Prior art видения: пулы законов и смысловая сеть.**
Контекст: (a) «пулы законов», мосты не соединяются при противоречии; в модели `Effect.deny` и `Effect.duty`; (b) VecDHT — обнаружение пиров по смыслу, развитие в user-owned p2p-хостинг; сейчас не транспорт.
Вопросы: (a) capability-based security (ocap, seL4 capabilities), macaroons/biscuit (аттенуация, contextual caveats), policy composition (XACML combining algorithms, Cedar, OPA/Rego, Zanzibar) — что формализует «пулы законов и непротиворечивые мосты»; (b) деонтическая логика в access control: конфликт duty vs deny, obligation conflicts — существующие формализации; (c) semantic/vector peer discovery: академические и проектные прецеденты (semantic overlay networks, embedding-based routing, vector DHT); (d) user-owned p2p hosting/сети: IPFS/Filecoin, Hypercore/Holepunch/Keet, Freenet/Hyphanet, GNUnet, Nostr — модели владения/управления, что переиспользуемо; (e) что в видении genuinely ново vs изобретение велосипеда.
Разблокирует: дизайн nomos, дорожная карта VecDHT, ADR о заимствованиях.
Источники: ocap literature (Mark Miller), seL4 docs, macaroons/biscuit specs, XACML/Cedar/OPA docs, deontic logic in security papers, DHT/overlay surveys, доки проектов.
