# PRIOR-ART — маршрутизация задач: что уже решено проверяемо

Дата: 29.10.2026. Источники: GitHub API (поиск), README в справочнике (`hs refs`).

## Что нашлось

| работа | что делает | что даёт нам |
|---|---|---|
| **NVIDIA-NeMo/Switchyard** (Rust, ~3.5k★) | маршрутизирует трафик LLM-приложений между моделями и провайдерами, сохраняя совместимость с OpenAI/Anthropic API | готовый слой, если понадобится несколько провайдеров; подтверждает, что маршрутизация — инфраструктурная задача, а не исследовательская |
| **withmartian/routerbench** | бенчмарк систем маршрутизации между моделями | методика: качество против цены, сравнение с оракулом |
| **ynulihao/LLMRouterBench** (ACL'26 Findings) | большой бенчмарк и единый фреймворк маршрутизации | методика оценки на многих моделях и задачах |
| **MilkThink-Lab/RouterEval** | бенчмарк маршрутизации по задачам | наборы задач и метрики |
| **primitive-bench/primitive-bench** | «маркетплейс проверяемых исходов»: задача → фиксированная цена → маршрутизация по инструментам → возврат, если исход не доставлен | ближайший аналог нашей идеи: подтверждает связку «задача → инструменты → исход», но коммерческую |

## Что это меняет у нас

1. **Методика уже есть.** Не нужно изобретать, как мерить маршрутизацию: берём схему
   «качество против цены, сравнение с оракулом и с константной стратегией». Наша константа —
   «всегда L1».
2. **Наш результат читается в их терминах.** 6,9 % отличий правил от «всегда L1» — это оценка
   выигрыша роутера над константой на нашем распределении. В литературе это и есть вопрос
   «сколько даёт роутер поверх лучшей константной политики».
3. **Никто не маршрутизирует *уровень обвязки*.** Все найденные работы выбирают модель, провайдера
   или инструмент. Наш слой — L0/L1/L2 для собственной работы — не покрыт. Это не значит «мы
   первые»: это значит, что готового бенчмарка под наш вопрос нет, и его придётся собрать самим.

## Что можно переиспользовать напрямую

- **Оракул как верхняя граница**: для каждой задачи — лучший уровень, если бы мы знали заранее.
- **Cost-quality кривая**: не одно число, а зависимость качества от цены; сравнение роутера с
  константами (L0, L1, L2).
- **Разделение «роутер vs политика»**: роутер выбирает, политика исполняет — у нас это `plan` и цикл.

## Где мы расходимся с их постановкой

| они | мы |
|---|---|
| выбор модели/провайдера/инструмента | выбор уровня обвязки и набора инструментов |
| качество = правильный ответ | качество = корректный исход **плюс** сохранившиеся свидетельства и границы |
| цена = токены/деньги | цена = шаги, время, риск ложного вывода |
| оракул недоступен | оракул тоже недоступен, поэтому и нужен эксперимент на типах |

## Вывод для решения

Классификатор — последний шаг, а не первый. Сначала: методика из RouterBench, константа «всегда L1»,
оракул на выборке и только затем модель, если она обгонит константу на этой выборке.

## Что это не доказывает

Что их методики переносятся на «уровень обвязки». Что метрики качества совместимы: у нас в качество
входят границы, у них — правильность ответа.
