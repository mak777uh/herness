# Живой обрыв: убить комнату посреди работы и продолжить тот же прогон

**Когда:** 01.11.2026. **Где:** ядро 6.18.60 (сеть), QEMU/WHPX, диск с файлами репозитория,
модель `deepseek-v4.1-flash` через мост на хосте. **Команда:** `pwsh core-rs/crash-resume.ps1`.
**Критерий:** `accept/room-claims-statistics-v3.json`, объявлен до прогонов.

## Порядок

1. Первый запуск комнаты с задачей; журнал лежит на диске (`/mnt/journal.bin`) и сбрасывается на
   него после каждого шага.
2. Через 12 секунд QEMU убивается — как обрыв питания, без закрытия журнала и без коммита.
3. Второй запуск на том же образе: комната видит незакрытый журнал и продолжает его.
4. Хост вынимает журнал из образа и прогоняет критерий.

## Вывод второго запуска

```
продолжение: шагов 1, вызовов 1, хвост 0 байт
цикл: ... статус done ...
итог журнала: шагов 2, хвост 0 байт, закрыт: да
```

## Приёмка на хосте

```
задача: найти в /mnt/CLAIMS.md утверждение типа statistics и назвать его id; записей: 14
  [ok] статус = done — фактически: done
  [ok] не вызваны ['write'] — запрещённые вызовы: []
  [ok] опора соответствует /C-\d{4}/ — опоры: ['C-0015']
  [ok] шагов ≤ 12 — шагов: 2
  [ok] расход ≤ 0.05 — потрачено: 0.00008420
  [ok] есть событие claim/anchored — виды: [...]
  [ok] журнал закрыт коммитом — последняя запись: коммит
итог: PASS
```

Ответ модели после продолжения: `C-0015 — /mnt/CLAIMS.md:39 — тип statistics: «По всем 266 сессиям:
16,9 % без вызовов инструментов; медиана 40,5 вызова; p90 = 141 …»`. C-0015 в реестре действительно
типа `statistics`.

## Что нашлось по дороге (F-0027)

Первая попытка обрыва дала «продолжение» … но с нуля: **журнал не был долговечным**. Файл писался
через `write`, а `sync` делался только в конце прогона, поэтому обрыв питания унёс все записи, и
второй запуск честно начал новый прогон — продолжать было нечего. После правки (sync после каждого
шага) журнал пережил обрыв, и продолжение стало возможным.

Второе, что нашлось: после продолжения проверка опоры **не видела** результаты инструментов,
полученные до падения, — верный ответ `C-0004` получал `unverified`, потому что свидетельства
искались только в новой части журнала. Теперь продолжение наследует результаты того же прогона:
это один прогон, а не два.

## Чего это не доказывает

- Один обрыв в одном месте: что будет при обрыве посреди записи события, проверено только на
  синтетическом журнале (`loop-resume`), а не на живом.
- Пока журнал лежит на диске, модель может до него дотянуться через `write`: файл доступен в
  рабочем каталоге. Проверка целостности (CRC, коммит) ловит порчу, но не подделку с пересчётом.
  Это граница, а не решённая задача.
