Причина вердикта: две блокирующие находки. Disposable-копия допускает tracked-ignored файлы, а cleanup при устойчивой ошибке заменяет первичное исключение. Зелёные focused/regression suites не покрывают эти комбинации.

[F1] HIGH / BLOCKER — tracked-ignored force-added файлы попадают в disposable copy
Файлы:
- bin/hs.py:193-219, особенно 201-204 (enumerator);
- bin/hs.py:222-249 (disposable_copy);
- bin/gate_probe.py:114-138, особенно 131-138 (probe sandbox).
Связанный тестовый пробел: tests/test_gates_w11.py:374-432.

Нарушение критерия:
Требование исключает из disposable copy ignored/force-added секретные зоны. Команда
    git ls-files -c -o --exclude-standard -z
объединяет cached/tracked и untracked nonignored файлы. --exclude-standard не удаляет cached-файл, который игнорируется, но был force-added. Дополнительный denylist покрывает только фиксированные имена/каталоги; произвольный ignored путь вне него проходит.

Воспроизводимый контрпример (выполнен изолированно, synthetic marker, не реальный секрет):
1. Создать temp git repo.
2. В .gitignore записать lab/private/.
3. Создать lab/private/secret.txt с маркером SYNTHETIC-IGNORED-SECRET.
4. Выполнить git add -f lab/private/secret.txt.
5. Вызвать hs.disposable_files(root), hs.disposable_copy(root) и gate_probe.sandbox(root).
Фактический вывод:
    enumerator_contains_ignored= True
    disposable_copy_contains_ignored= True
    probe_sandbox_contains_ignored= True
lab/private входит в COPY gate_probe, поэтому дефект затрагивает и claims-disposable, и probe sandbox.

Дополнительное read-only свидетельство на текущем repo (содержимое файлов не читалось):
    git ls-files -ci --exclude-standard -z -> 814 tracked-ignored путей, все под lab;
    hs.disposable_files(root) -> 4727 путей;
    tracked_ignored_admitted -> 814 из 814.
Примеры допущенных путей: lab/h2/A/run-1/CYCLE.md, P16-RESULTS.md, P17-RESULTS.md, P18-RESULTS.md, SELF-WORK.md.

Почему focused suite зелёный:
Тест force-add только .secrets/forced.txt и .env, которые отсекает denylist. Произвольный ignored force-added путь lab/private/secret.txt не проверяется.

Минимальный fix:
- Отдельно fail-closed получить git ls-files -ci --exclude-standard -z; при OSError/timeout/nonzero бросать MissingData.
- Вычесть этот набор из allowed set перед копированием.
- Добавить focused regression с force-added lab/private/secret.txt (или другим ignored путём под COPY) и проверить отсутствие файла в hs.disposable_copy и gate_probe.sandbox.
- Сохранить существующие symlink/junction и denylist проверки.

[F2] HIGH / BLOCKER — cleanup маскирует первичную ошибку
Файлы:
- bin/gate_probe.py:675-697, особенно 695-697 (cleanup в finally);
- bin/gate_probe.py:130-167, особенно 165-167 (cleanup в except);
- bin/hs.py:1477-1484 (та же схема в gate_claims_run);
- bin/hs.py:239-249 (та же схема в disposable_copy).

Нарушение критерия:
Bounded retry корректен сам по себе: после deadline устойчивый WinError 32 остаётся ошибкой. Но remove_disposable() вызывается из finally/except без сохранения активного первичного исключения. Если cleanup тоже падает, Python выбрасывает cleanup error вместо исходной ошибки gate/inject/copy/git init. Это прямым образом нарушает требование «retry не маскирует первичную ошибку».

Воспроизводимый контрпример (выполнен на изолированных monkeypatch-объектах, без запуска bin/gate_probe.py и без его lock/temp dirs):
A. sandbox:
- shutil.copy2 бросает RuntimeError("PRIMARY-COPY");
- shutil.rmtree устойчиво бросает PermissionError с winerror=32;
- monotonic возвращает 0.0, затем 4.0 (deadline уже истёк);
- вызов gate_probe.sandbox(root).
Ожидалось: PRIMARY-COPY. Фактически:
    sandbox_exception_type= PermissionError
    message= [WinError 32] persistent sharing violation
B. _run_selected:
- fake sandbox возвращает temp-каталог;
- gate бросает RuntimeError("PRIMARY-GATE");
- cleanup устойчиво бросает тот же PermissionError.
Ожидалось: PRIMARY-GATE. Фактически:
    selected_exception_type= PermissionError
    message= [WinError 32] persistent sharing violation

Почему focused suite зелёный:
tests/test_gates_w11.py:600-711 отдельно проверяет RuntimeError при успешном cleanup и persistent lock при отсутствии первичной ошибки. Комбинация «первичная ошибка + ошибка cleanup» не проверяется.

Минимальный fix:
- Во всех трёх путях сохранять первичное BaseException, выполнять cleanup, но при cleanup failure повторно выбрасывать primary; добавить к нему note/контекст с cleanup error.
- Не превращать cleanup failure в успех и не терять исходный тип/сообщение.
- Добавить combined negative control: PRIMARY-GATE/PRIMARY-COPY + persistent WinError 32; assert первичного типа/сообщения и наличия cleanup note.
- Применить одинаковую схему к gate_probe.sandbox, gate_probe._run_selected, hs.disposable_copy и hs.gate_claims_run.
