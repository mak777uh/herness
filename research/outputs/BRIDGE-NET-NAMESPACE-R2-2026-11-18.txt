BRIDGE-NET-NAMESPACE-R2 — нерабочий unshare отвергается 503
Дата: 2026-11-18
Пре-регистрация: lab/prereg/BRIDGE-NET-NAMESPACE-R2.json
Команда: python tests/test_bridge_net_namespace.py (Windows делегирует в WSL Ubuntu)
Окружение: Windows + WSL2 Ubuntu, uid 0; unshare 2.41.3; только loopback.

Зачем
-----
Решение владельца A (C-0328) запускает /v1/net под unshare -U -p -f --mount-proc.
Отсутствие unshare даёт 503. Но наличие файла не значит, что user namespace
разрешён: на Ubuntu 24.04 с apparmor_restrict_unprivileged_userns и на CI-раннере
unshare падает с EPERM. Тогда net.py не исполняется (изоляция не запускается),
но ответ был 200 с error — не явный отказ. CI run 44301185581 показал красный
C-0324 после включения namespace; полный вывод теста в логе не детализирован.

Изменение
---------
bin/bridge.py: Bridge.unshare_works(unshare) — одноразовая проба
`unshare -U -p -f --mount-proc <python> -c pass` с allowlist-окружением и
таймаутом 15 с; результат кэшируется в Bridge._unshare_ok. Если проба не прошла,
net_command возвращает пустую команду и причину, обработчик отвечает 503 до
запуска net.py. Проверка наличия файла осталась отдельной веткой.

tests/test_bridge_key_isolation.py: на Linux в PATH моста подставляется shim
`unshare`, который исполняет команду без namespace. Предмет этого теста —
наследование окружения; namespace проверяет test_bridge_net_namespace.py.
Это делает C-0324 независимым от доступности user namespace на раннере.

Регрессия C-0324:
- Windows: ВЕРДИКТ PASS — дочерний процесс /v1/net не получает ключ из окружения.
- WSL (с shim launcher'а): тот же PASS; вхождения канарейки во всех каналах 0.

Что это НЕ доказывает
---------------------
- Windows не покрыт: там unshare не используется, остаётся отдельный канал
  чтения окружения процесса (H-0010).
- Проба кэшируется: если условия изменятся после первого запроса, повторной
  проверки нет.
- PID-namespace не изолирует файловую систему, сеть и token-файл; путь
  скрывается из /proc, но файл по известному пути доступен.
- WSL-прогон под uid 0; успех под root не гарантия для обычного uid.
- Это не K9, не активация и не approval: настоящий owner-ключ не создавался,
  active пуст, K9_proven не выдавался.
