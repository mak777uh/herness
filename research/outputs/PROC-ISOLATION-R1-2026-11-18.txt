# PROC-ISOLATION-R1 — остаток /proc и PID-namespace

Дата: 2026-11-18; test-only; настоящие ключи и токены не читались.
Пре-регистрация: `lab/prereg/PROC-ISOLATION-R1.json`.
Мост и комната не менялись: `bin/bridge.py` — protected/needs_owner, этот срез только измеряет.

## Вопрос

`BRIDGE-KEY-ISOLATION-R1` закрыл наследование `os.environ` в `/v1/net`, но на Linux
остаётся `/proc/<ppid>/environ`: дочерний процесс того же uid читает **стартовое**
окружение родителя, включая `HS_BRIDGE_KEY`. Allowlist окружения этого не закрывает.
Второй вопрос: скрывает ли родителя PID-namespace `unshare -U -p -f --mount-proc`.

## Команда

```text
python bin/proc_isolation.py
```

На Windows скрипт делегирует в WSL Ubuntu; внутри WSL работает `--run-arms`.
Родитель запускается с синтетической канарейкой в стартовом окружении, оба ребёнка —
с allowlist-окружением без канарейки. Ребёнок ищет `HS_BRIDGE_KEY=<канарейка>` в
`/proc/<ppid>/environ` и во всём `/proc`; печатаются только булевы результаты.

## Окружение

```text
uid=0(root) gid=0(root) groups=0(root)
unshare from util-linux 2.41.3
6.6.114.1-microsoft-standard-WSL2
```

## Вывод

```text
плечо A (без изоляции):
PROBE_RAN=1
FOUND=1
FOUND_ANY=1
плечо B (unshare -U -p -f --mount-proc):
PROBE_RAN=1
FOUND=0
FOUND_ANY=0
[ok] A: probe выполнился
[ok] A: канарейка видна напрямую в /proc родителя (остаток воспроизведён)
[ok] A: канарейка видна при поиске по всему /proc
[ok] B: probe выполнился в namespace
[ok] B: родитель не виден напрямую
[ok] B: канарейка не видна при поиске по всему /proc
провалов: 0
ВЕРДИКТ: PASS — same-uid /proc видит env; PID-namespace скрывает родителя
```

## Что это значит

1. Остаток `BRIDGE-KEY-ISOLATION-R1` подтверждён: allowlist окружения не мешает
   ребёнку того же uid прочитать стартовое окружение моста через `/proc`. Это не
   регрессия фикса — фикс закрывает наследование, а не чтение чужого `/proc`.
2. `unshare -U -p -f --mount-proc` убирает родителя из `/proc` ребёнка: и прямой
   путь, и поиск по всему `/proc` дают 0. Это рабочий строительный блок для
   Linux-ветки моста, если владелец разрешит менять `bin/bridge.py`.

## Что это НЕ доказывает

- Прогон в WSL идёт под `uid=0(root)`. На обычном uid `unshare -U` может требовать
  разрешённых user namespaces; тогда плечо B честно упадёт, а не станет «зелёным».
- Это не изменение моста: `/v1/net` по-прежнему запускает `net.py` без namespace.
  Интеграция — расширение поверхности `bin/bridge.py`, а это `needs_owner`.
- PID-namespace не изолирует файловую систему, сеть и токен-файл; побег через
  смонтированные пути, `ptrace` соседей и другие каналы не проверялся.
- Windows-путь не проверялся; `unshare` — Linux-only. Для Windows нужен отдельный
  механизм (job object/AppContainer/отдельный uid), это другой срез.
- Это не K9-доказательство композиции и не разрешение комнате доверять внешним
  данным. Метка `[external_untrusted]` остаётся текстовой.
- Настоящий owner-ключ не создавался, admission не подписан, `active` пуст,
  `K9_proven` не выдан.
