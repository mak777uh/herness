[F3] HIGH / BLOCKER — root-aware loaders исполняют stale .pyc и допускают false green
Файлы:
- bin/hs.py:133-145, особенно 134-145;
- bin/gen_capabilities.py:48-59 (та же схема для core/tools.py).

Суть:
load_gate_module() читает source bytes и включает их digest в имя модуля, но затем вызывает spec.loader.exec_module(). sys.dont_write_bytecode=True запрещает запись .pyc, но не чтение уже существующего .pyc. SourceFileLoader может исполнить старый bytecode, если timestamp и size исходника совпадают с метаданными .pyc. Уникальное имя модуля этого не предотвращает: cache path зависит от source path, а не от имени модуля. Аналогичная проблема есть в gen_capabilities.build().

Нарушение критерия:
Sealed dual_root/stopping_rule запрещает cached-code подмену и любой cross-root false verdict. Докстринг bin/hs.py:121-125 прямо обещает, что повторный вызов после правки не получает cached старый код. Это обещание текущим кодом не выполняется. Baseline gate_compile создавал .pyc, поэтому сценарий реалистичен при обновлении checkout, а не только теоретический.

Воспроизведение (выполнено в temp, без правки репозитория):
1. Создать temp root с bin/gate_docs.py:
       def main(root):
           return 0
2. Установить фиксированный mtime 1700000000 и явно создать py_compile-кэш.
3. Заменить source на same-size вариант:
       def main(root):
           return 1
4. Восстановить тот же mtime.
5. Вызвать hs.load_gate_module(root, "bin/gate_docs.py") и hs.gate_docs(root).

Фактический вывод:
    STALE_GATE_PYC_CONTROL {"source_main_rc": 1, "executed_main_rc": 0,
                            "gate_problems": [], "false_green": true}

Дополнительный минимальный контроль с VALUE=1 -> VALUE=2 дал executed_value=1 при source_value=2.

Почему focused/evidence зелёные:
- В текущем дереве __pycache__ и .pyc отсутствуют.
- Прогоны выполняются с -B/PYTHONDONTWRITEBYTECODE=1.
- Hostile-cache control проверяет sys.modules, но не timestamp-valid .pyc.
- Clean selftest копирует hs-core и не моделирует stale bytecode.

Минимальный fix:
- В обоих loader-путях исполнять compile(data, str(path), "exec") в уже созданном module object, а не SourceFileLoader.get_code(); либо использовать loader, который всегда компилирует прочитанные source bytes и никогда не читает .pyc.
- Добавить focused negative control: same-size source edit + сохранённый mtime + timestamp-valid .pyc; gate обязан увидеть новую версию и вернуть RED.

[F4] HIGH / BLOCKER — обычный CLI gates падает на отсутствующем hs-core из-за разных MissingData
Файлы:
- bin/hs.py:34 (MissingData вызывающего модуля);
- bin/hs.py:1649-1655, особенно 1651-1655;
- bin/binary_version.py:57-61;
- cmd_gates catch: bin/hs.py:2002-2013.

Суть:
При запуске `python bin/hs.py` класс MissingData определяется в __main__. root-aware binary_version.problems() при отсутствии hs-core импортирует `from bin.hs import MissingData` и бросает отдельный bin.hs.MissingData. except MissingData в gate_rust() ловит только __main__.MissingData, поэтому исключение пролетает мимо и обрывает весь gate-loop. В свежем script context без ранее импортированного package bin тот же deferred import может дать ModuleNotFoundError: No module named 'bin'.

Нарушение критерия:
Обычные gates должны завершаться штатным verdict/ summary; N/A/unknown не должны превращаться в PASS, но и явно предусмотренная ветка «сборка неполная» не должна обрывать CLI traceback. Это также остаток root/dependency-cache проблемы: уникальное имя главного validator-модуля не делает транзитивный import bin.hs тем же модулем/тем же классом исключения.

Воспроизведение (выполнено на disposable copy candidate):
1. Создать hs.disposable_copy(ROOT).
2. Скопировать только свежие core-rs/target/release/deps/hs_core-* артефакты; hs-core/hs-core.exe не копировать.
3. Инициализировать git worktree.
4. Выполнить:
       python <copy>/bin/hs.py gates --root <copy> --circuit a --profile full

Фактический вывод:
- CLI_GATE_RC=1.
- Последние штатные строки заканчиваются на `[ok] требования: 0 проблем`.
- stderr содержит traceback:
       bin/hs.py:1652 in gate_rust
       bin/binary_version.py:61 in problems
       bin.hs.MissingData: нет собранного hs-core: версию формата в бинарнике проверить нечем
- Итогового `[FAIL] rust ...` и общего summary нет.

Ожидалось по коду hs.py:1653-1655: проблема отсутствующего hs-core добавляется к problems и возвращается как обычный gate FAIL (либо корректно классифицируется как N/A), без traceback.

Почему focused/evidence зелёные:
- tests/test_gates_w11.py импортирует `from bin import hs`, поэтому вызывающий и binary_version используют один cached bin.hs.MissingData.
- tests/test_binary_version.py:51-58 проверяет только type(exc).__name__ == "MissingData", но не identity класса и не CLI entrypoint.
- Clean disposable selftest копирует hs-core, поэтому missing-binary ветка не исполняется.
- Real-readonly integration также использует дерево с hs-core.

Минимальный fix:
- Передать класс/factory MissingData из hs.gate_rust() в binary_version.problems(root, missing_data=MissingData), либо вынести общий исключение в отдельный root-independent модуль; не импортировать bin.hs из validator.
- Добавить subprocess negative control именно для `python bin/hs.py ...`: rlib/deps-артефакт свежий, hs-core отсутствует; assert отсутствия traceback и наличия штатного rust verdict/summary.
