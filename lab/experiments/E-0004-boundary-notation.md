# E-0004 — Три способа записать границу: схема, язык политик, мини-DSL

Гипотеза (H-0003): для границ участника отдельная нотация не нужна, если схема и существующий язык
политик дают ту же однозначность и проверяемость дешевле.

## Пре-регистрация (объявлено до прогона)

**Вход:** три реальные границы:

1. **Обмен артефактами:** «отдаю результаты прогона партнёру, если он не публикует их; запрещено
   передавать сырые ключи».
2. **Публикация:** «публикую только то, что прошло гейты; запрещено публиковать до прохождения».
3. **Трата:** «оплата проверки до $50 без подтверждения; выше — только с явным согласием».

**Три нотации:**
- A. JSON/YAML-схема + проверка кодом;
- B. существующий язык политик (Cedar или Rego — на выбор исполнителя, обосновать);
- C. мини-DSL: свой синтаксис, парсер ≤200 строк, проверяльщик.

**Метрики:**
1. время написания трёх границ (минуты, медиана из 3 попыток);
2. число мест, где второй читатель понял иначе (неоднозначности);
3. решаемость: может ли проверка ответить «в рамках / вне рамок» без человека (да/нет на каждую);
4. цена тулчейна: новые зависимости, шаги сборки, редакторская поддержка;
5. качество диагностики: понятно ли, почему отказ.

**Порог (объявлен сейчас):** DSL оправдан, если он даёт **меньше неоднозначностей** и **не больше
шагов** до проверяемого ответа, при цене тулчейна не выше, чем у B. Иначе — остаёмся на A или B, а
DSL считается отброшенным с записью в `docs/eliminations.md`.

## Команда

```
python bin/hs.py run "E-0004: три нотации для трёх границ"
```

не вынесен.

## Что это не доказывает

- Что три границы представляют все будущие.
- Что второй читатель не предвзят.
- Что DSL не выиграет при росте числа границ (эффект масштаба не проверяется тремя случаями).
