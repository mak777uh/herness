id: F-0084
date: 11.11.2026
title: guestfwd в QEMU 11.1.0 на Windows принимается, но канал не поднимается — restrict=on отрезал бы мост
what: попытка закрыть гостю выход наружу через `restrict=on` + `guestfwd` дала пять разных отказов, и ни один вариант не поднял канал к мосту. QEMU отвергает адрес хоста в поле guestfwd, принимает гостевой адрес и пустой, но гость в обоих случаях получает `Connection refused (os error 111)`. Команда `.cmd` не стартует вовсе (CreateProcess не исполняет скрипты), `.exe` собранный PyInstaller — тоже не даёт канала. При этом на ХОСТЕ порт 8790 занят мостом (netstat: ESTABLISHED), то есть QEMU на гостевом адресе ничего не слушает.
class: tooling-gap
principle: параметр, который принимается без ошибки, не обязан работать; «принят» и «работает» — разные исходы, и различает их только прогон
detect: запустить QEMU с restrict=on и guestfwd, поднять гостя и посмотреть, соединяется ли цикл с мостом; отдельно проверить netstat на хосте — слушает ли QEMU гостевой адрес
test: пять вариантов синтаксиса (10.0.2.2 / пустой адрес / 10.0.2.15; .cmd / .exe). Все дают Connection refused у гостя. Журнал комнаты: `step/error мост недоступен (10.0.2.15:8790): Connection refused (os error 111)`
symptom: прогон с -NetRestrict даёт 0 шагов и статус done-без-опоры; гость не может дотянуться до моста, хотя QEMU не сказал ни слова об ошибке
cause: guestfwd в QEMU на Windows не поднимает канал; функция Unix-ориентированная, и её поведение на этой платформе не документировано как рабочее
fix: не исправлено. `-NetRestrict` теперь отказывает с названной причиной, а не молча ломает прогон. Вторая стена отложена: первая (политика Rust + SSRF-фильтр + openat2) стоит и проверена отдельно
caught_by: прогон lab/workspace-verify и accept-run с -NetRestrict: 0 шагов, журнал говорит Connection refused на 10.0.2.15:8790
