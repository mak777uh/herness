# Теоретическое приближение: безопасный MCP-мост от магазина к покупателям

**Что это.** Не предложение и не продукт. **Исследование**: как мог бы выглядеть безопасный мост
между магазином и агентами покупателей, если исходить из того же подхода, что в `herness` —
сначала границы, потом удобство.

**Зачем.** Если начнутся массовые атаки на веб-версии магазинов, у бизнеса должен быть план
«как существовать дальше». Этот документ описывает один из возможных.

---

## 1. Постановка

### Что меняется

Покупатель перестаёт ходить на сайт. Он говорит своему агенту: «найди мне дрель до 8000 рублей,
чтобы была в наличии и доставка завтра». Агент идёт к магазину — **не в браузере, а по протоколу**.

### Что это даёт магазину

| | веб-версия | MCP-мост |
|---|---|---|
| **что исполняется у покупателя** | браузер, JS, десятки библиотек | **агент в изолированной среде** |
| **что исполняется у магазина** | весь фронт, CMS, плагины | **только бэкенд и мост** |
| **персональные данные** | проходят через магазин | **остаются у покупателя** |
| **кто платит за модель** | магазин | **покупатель** |
| **поверхность атаки** | огромная | **несколько функций** |

### Что это НЕ решает

- **Мост — это тоже код**, и он тоже может быть дырявым.
- **Бэкенд магазина остаётся** — если он дырявый, мост не поможет.
- **Агент покупателя — недоверенная сторона.** Он может быть враждебным.

**Главный принцип:** мост не должен доверять агенту. Агент не должен доверять мосту. Обе стороны
проверяют друг друга.

---

## 2. Устройство моста

### Слои

```
┌──────────────────────────────────────────────────────────┐
│  АГЕНТ ПОКУПАТЕЛЯ (на машине покупателя)                 │
│  в изолированной комнате, как в herness                  │
└──────────────────────┬───────────────────────────────────┘
                       │  MCP-протокол (JSON-RPC поверх HTTPS)
                       │  подписанные запросы
                       ▼
┌──────────────────────────────────────────────────────────┐
│  МОСТ МАГАЗИНА (маленький сервис, отдельно от бэкенда)   │
│                                                          │
│  1. проверка подписи и квоты                             │
│  2. политика: что этому агенту разрешено                 │
│  3. вызов бэкенда по закрытому списку операций           │
│  4. ответ — только разрешённые поля                      │
│  5. журнал append-only                                   │
└──────────────────────┬───────────────────────────────────┘
                       │  внутренняя сеть, без выхода наружу
                       ▼
┌──────────────────────────────────────────────────────────┐
│  БЭКЕНД МАГАЗИНА (каталог, цены, наличие, заказы)        │
└──────────────────────────────────────────────────────────┘
```

### Почему мост отдельно от бэкенда

**Причина:** если мост скомпрометирован, бэкенд не должен пасть. Мост — это **тонкая прослойка**,
которая знает только разрешённые операции.

**Цена:** ещё один сервис, который надо держать.

---

## 3. Инструменты моста

**Не «API магазина»**, а **закрытый список из шести-восьми функций**, как в `herness`:

| инструмент | что делает | замыкание |
|---|---|---|
| `search_products` | ищет товары по тексту и фильтрам | чтение каталога, 200 мс, 8 КБ |
| `get_product` | карточка товара по id | чтение каталога, 100 мс, 4 КБ |
| `check_stock` | наличие и срок доставки | чтение склада, 100 мс, 1 КБ |
| `get_price` | цена с учётом скидок | чтение цен, 100 мс, 1 КБ |
| `place_order` | создать заказ | **запись**, 500 мс, 1 КБ |
| `order_status` | статус заказа | чтение заказов, 100 мс, 1 КБ |

**Почему именно так:** у каждой функции объявлено замыкание — что читает, что пишет, сколько
времени, сколько памяти, сколько байт выдаёт. Всё, что не объявлено, — запрещено.

**Чего в списке нет и не должно быть:**

- произвольный SQL;
- произвольный HTTP;
- загрузка файлов;
- исполнение кода;
- доступ к другим покупателям.

---

## 4. Политика: что разрешено агенту

### Три уровня доверия

| уровень | кто | что может |
|---|---|---|
| **анонимный** | любой агент | поиск, карточки, цены, наличие |
| **идентифицированный** | агент с подписью покупателя | + создание заказа, статус |
| **доверенный** | агент с историей | + отслеживание, возвраты |

### Правила

```
allow agent search_products  catalog:**
allow agent get_product      catalog:**
allow agent check_stock      stock:**
allow agent get_price        price:**
deny  agent place_order      order:**          # только идентифицированному
deny  agent read_other       customer:*        # никогда
```

**Правило приоритета:** запрет сильнее разрешения. Что не разрешено — запрещено.

### Что доказуемо

**Как в `herness`:** политика — это данные, и её можно проверить формально.

| теорема | утверждение |
|---|---|
| запрет сильнее разрешения | если есть `deny`, отказ независимо от `allow` |
| нет неявных разрешений | что не разрешено — запрещено |
| анонимный не создаёт заказ | у анонимного нет правила `allow place_order` |

**Доказательство в Lean** — как сделано для `herness`, шесть теорем.

---

## 5. Что мост обязан гарантировать

| свойство | как проверяется |
|---|---|
| **адрес только один** | мост ходит только на внутренний бэкенд; адрес задан при запуске |
| **токен не выходит** | ключи читаются из файла, не попадают в ответ и лог |
| **тело ограничено** | размер запроса и ответа ограничен |
| **ответ не переписывается** | мост возвращает данные бэкенда как есть |
| **каждая операция записана** | журнал append-only с CRC |
| **квота на агента** | число запросов в минуту ограничено |

**Граница:** это свойства, которые надо **доказать**, а не объявить. В `herness` мы доказали
политику, но мост пока проверен только поиском по коду. Для магазина это надо закрыть.

---

## 6. Идентификация покупателя

### Что нужно

**Мост должен знать, чей это агент**, иначе любой может создать заказ от чужого имени.

### Как

**Подписанный запрос:**

```
запрос = { tool, args, nonce, timestamp }
подпись = sign(приватный_ключ_покупателя, sha256(запрос))
```

**Покупатель регистрирует публичный ключ** при первом обращении (или при привязке к аккаунту).

**Мост проверяет:**
- подпись верна;
- `nonce` не повторялся (защита от повтора);
- `timestamp` не старше N секунд (защита от отложенной атаки).

### Что это НЕ решает

- **Кража ключа** — если ключ украден, мост не отличит.
- **Социальная инженерия** — если покупателя обманули, подпись будет настоящей.

**Это не аутентификация человека, а аутентификация агента.**

---

## 7. Сценарий «дикого интернета»

### Если начнутся массовые атаки

**Временная мера, которая сохраняет бизнес:**

| шаг | что | почему |
|---|---|---|
| 1 | **сервер магазина отключить от сети** | чтобы остановить атаку |
| 2 | **веб-версию убрать** | она и есть главная поверхность атаки |
| 3 | **оставить только MCP-мост** через отдельный шлюз | маленькая поверхность, легче защитить |
| 4 | **мост держать за шлюзом** с ограничением по IP, квоте, подписи | сузить до одного канала |
| 5 | **бэкенд оставить во внутренней сети** | он не виден снаружи |

### Что это даёт

- **бизнес продолжает работать** для покупателей с агентами;
- **поверхность атаки сужается** с «весь фронт» до «несколько функций»;
- **данные покупателей не проходят через магазин**;
- **можно спокойно чинить веб-версию**, пока работает мост.

### Что это стоит

- **теряются покупатели без агентов** — их придётся научить или временно потерять;
- **надо быстро сделать мост** — а это не неделя;
- **нагрузка на поддержку** — вопросы «почему сайт не работает».

### Чего это НЕ решает

- **Мост тоже может быть дырявым.** Он меньше, но не неуязвим.
- **Бэкенд остаётся** — если он дырявый, мост не спасёт.
- **Это не «безопасный интернет»**, а **временная мера выживания**.

## 8. Порядок внедрения, если бы это делалось

| шаг | что | сколько |
|---|---|---|
| 1 | **описать инструменты** и их замыкания | дни |
| 2 | **написать мост** как тонкую прослойку | недели |
| 3 | **доказать политику** в Lean | недели |
| 4 | **сверить код с моделью** | недели |
| 5 | **прогнать с реальными агентами** на тестовом каталоге | месяцы |
| 6 | **открыть анонимный доступ** (поиск, карточки) | после 5 |
| 7 | **открыть заказы** (с подписью) | после 6 |

**Не начинать с заказов.** Начать с того, что ничего не меняет: поиск, карточки, наличие.

---

## 9. Что взять из `herness` как есть

| механизм | зачем магазину |
|---|---|
| **закрытый список инструментов** | вместо «API на всё» — шесть функций |
| **замыкание на каждый инструмент** | видно, что он может, и что не может |
| **политика как данные** | можно проверить формально |
| **посредник: решение принимает политика** | одна точка, а не разбросанные проверки |
| **журнал append-only** | свидетельство для разбора инцидентов |
| **коды отказа** | «не прошло» становится инструкцией |
| **три исхода: PASS / FAIL / UNKNOWN** | тихий пропуск не считается успехом |

## 10. Что НЕ брать

| механизм | почему |
|---|---|
| **своё ядро и QEMU** | это для агента у покупателя, а не для моста магазина |
| **формальная верификация всего** | недели работы; начать с политики |
| **полная изоляция** | мосту нужен доступ к бэкенду |

---

## 11. Честная граница

**Это теоретическое приближение.** Оно не проверено на реальном магазине, не согласовано с
юристами, не оценено по стоимости.

**Что в нём можно утверждать:**
- подход **уменьшает поверхность атаки** — это следует из устройства, а не из замеров;
- подход **позволяет доказать часть свойств формально** — это проверено на `herness`;
- подход **не решает всех проблем** — мост и бэкенд остаются.

**Что нельзя утверждать:**
- что это **безопасно** — не проверено;
- что это **дешевле** — не считали;
- что покупатели **примут** — не спрашивали;
- что это **спасёт** при массовой атаке — неизвестно.

**Ценность документа — в форме вопроса:** «если делать безопасный мост, то как он устроен и где
его границы». Ответ на этот вопрос лучше, чем его отсутствие.
