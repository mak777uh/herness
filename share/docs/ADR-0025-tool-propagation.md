# ADR-0025 — Инструмент переезжает между классами, но по одному

Дата: 29.10.2026. Статус: предложено. Дополняет ADR-0020 (профили) и ADR-0023 (кристаллизация).

## Идея

Инструмент, доказавший выигрыш в одном классе задач, не должен оставаться там навсегда: если
соседний класс делает похожие действия, инструмент, вероятно, поможет и ему.

Но «вероятно» — не основание. Инструмент переезжает **по одному классу за раз**, каждый переезд —
пробный период с замером.

## Состояния пары «инструмент × класс»

```
отсутствует → кандидат → пробный → активный → выведенный
                 │           │          │
                 │           └─ провал → возврат в «отсутствует» + запись в lab/failures
                 └─ нет замера → не переходит дальше
```

Переход в `активный` — только по измеренному выигрышу в этом классе, а не по аналогии.

## Близость классов

Считается по **словарю действий**: у класса есть набор действий (read, run, report…), близость —
мера пересечения (Жаккар). Инструмент, работающий с действием `run`, естественно соседствует с
классами, где `run` есть.

Порог по умолчанию — 0.5. Инструмент из «уточнения» (T-0007, действие `answer`) не переезжает никуда:
пересечения нет.

## Правила

| правило | формулировка |
|---|---|
| R1 | переезд только при измеренном выигрыше в исходном классе (≥20 %) |
| R2 | только в соседний класс (близость ≥0.5) |
| R3 | по одному классу за раз: второй переезд — после завершения первого |
| R4 | пробный период обязателен; без замера статус не меняется |
| R5 | провал в пробе — возврат и запись в `lab/failures/`, а не «ещё попробуем» |
| R6 | инструмент, не использованный N недель, выводится (`retired`) |

## Зачем «постепенно», а не сразу

1. **Инерция универсализации.** Инструмент, объявленный универсальным, перестаёт проверяться — и
   через месяц им пользуются там, где он не работает.
2. **Разные классы — разные издержки.** `hs py` в сборке экономит шаги, а в публикации может
   добавить ритуал, которого там не было.
3. **Обратимость.** Один переезд легко откатить; десять одновременно — уже миграция.

## Как это работает механически

```
python bin/hs.py spread
```

Читает `classes.json` (классы и действия) и `tools.json` (что где уже работает), считает близость и
печатает предложения: `инструмент: класс_откуда → класс_куда (выигрыш, близость)`.

Предложение — **не решение**. Решение — запись в `tools.json` со статусом `trial` и замером.

## Метрики

| величина | что показывает |
|---|---|
| классов на инструмент | степень универсализации |
| доля переездов, закончившихся провалом | качество переноса |
| время от `trial` до `active` | скорость проверки |
| регрессии в целевом классе | цена переезда |

## Риски

1. **Ложная близость:** пересечение слов-действий не означает сходства задач.
2. **Выигрыш не переносится:** 33 % в сборке ничего не говорят о публикации.
3. **Раздувание профилей:** чем больше инструментов в классе, тем выше риск перегрузки (4–10 — предел).

## Что это не доказывает

Что близость по действиям отражает реальное сходство. Что перенос выигрыша вообще возможен между
классами. Что порог 0.5 верен — это гипотеза.
