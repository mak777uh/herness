# ADR-0008 — Связь между узлами: идентичность, рендеву, транспорт, очередь

Дата: 29.10.2026. Статус: предложено. Дополняет ADR-0007.

## Задача

Несколько собственных узлов обмениваются сообщениями и артефактами. Сети между ними нестабильны:
соединения могут не устанавливаться, внешние адреса меняются, часть протоколов может не проходить.

## Пять слоёв, связанных контрактом

```
1. Идентичность     Ed25519-ключ узла; адрес = отпечаток ключа. Аккаунтов нет.
2. Рендеву          VecDHT: «кто умеет X» / «кто держит запись Y». Находит пира, не двигает данные.
3. Транспорт        сменный: релей → TLS → прикладные протоколы → оверлей → носитель.
4. Очередь          durable outbox: сообщение живёт, пока не подтверждено (at-least-once + dedupe).
5. Содержимое       контентная адресация: артефакты и сообщения адресуются хешем, не потоком.
```

Правило: слои связаны только контрактом. Замена транспорта не меняет ни рендеву, ни очередь, ни
формат сообщения.

## Про VecDHT: что он даёт и чего не даёт

Факты из `README.md` VecDHT (кэш справочника, 29.10.2026):

| факт | значение |
|---|---|
| что это | p2p семантическая рендеву-сеть: узел публикует намерение (эмбеддинг + подписанный текст) |
| устройство | Kademlia, 64 шарда, подпись + PoW, admission-политика, denylist и отзыв ключей |
| записи | контентно-адресуемые: узел показывает, что ему отдали; третья сторона может проверить |
| зрелость | «≈85 % готовности» (оценка); тег и бинарник не выпущены |
| измерено | 192 холодных resolve: p95 = 117…257 мс |
| границы | padding не реализован — это не сеть анонимности |

Отсюда: VecDHT **не является** транспортом для сообщений и **не является** средством сокрытия
адреса. Это служба обнаружения.

## Варианты транспорта

| вариант | свойства | когда применяется | ограничение |
|---|---|---|---|
| прямой HTTPS | минимальная задержка | базовая связь | зависит от сети и NAT |
| релей у владельца | фиксированный адрес входа | основная схема | адрес релея виден |
| прикладные протоколы (TLS/QUIC) | выше устойчивость к потерям | нестабильные сети | требует настройки на обеих сторонах |
| onion-сервис | входящее соединение без проброса портов | узел за NAT | задержка в секундах |
| оверлей (VecDHT/libp2p) | адресация без постоянного адреса | поиск пира | медленнее; нужен bootstrap |
| носитель (USB/QR) | не требует сети | полная недоступность сети | ручной перенос |

## Bootstrap — узкое место

Любая оверлей-схема начинается с точки входа. Если точка входа недоступна, сеть не поднимается.
Поэтому источников входа несколько и они разной природы: вшитый список, обмен пирами, DNS TXT,
QR-код, физический носитель.

## Что делаем сейчас

| сейчас | зачем это транспортный слой |
|---|---|
| конверт сообщения (подпись, id, run_id, seq, lease) | один формат для всех транспортов |
| durable outbox с подтверждениями | непрерывность при обрыве (A15) |
| идентичность = ключ | нет миграции аккаунтов при смене транспорта |
| интерфейс `Transport.send(envelope)` | добавление транспорта — новый класс, не правка ядра |
| контентная адресация артефактов | большие данные не идут через медленный канал |

## Границы

- Ни один транспорт не гарантирует установление соединения: свойства сети меняются.
- Сокрытия адреса нет: узел виден так же, как при обычном проксировании.
- Задержка оверлея — сотни миллисекунд на поиск, доставка через посредников — секунды.
- Оверлей без участников не работает: сеть из одного узла ничего не решает.

## Что это не доказывает

Что VecDHT выдержит нагрузку вне тестового стенда. Что оверлей даст приемлемую скорость для
интерактивной работы. Что связка «рендеву + outbox» не создаёт петель доставки.
