# ADR-0023 — Повтор как сигнал кристаллизации: из вызова модели в код

Дата: 29.10.2026. Статус: предложено. Дополняет ADR-0015 (конвейер инструментов).

## Наблюдение

Из журналов: **22 % всех вызовов инструментов — повтор той же команды** в той же сессии
(C-0015). Часть повторов законна, но сам факт говорит о другом: агент заново «решает» задачу,
решение которой уже известно.

## Принцип

**Повторяющаяся последовательность — кандидат в код, а не повод ещё раз вызвать модель.**

Если одна и та же связка «условие → команда → проверка» встречается N раз, она перестаёт быть
решением и становится **процедурой**. Процедуру исполняет софт: детерминированно, дешево, без модели.

```
наблюдение → повтор (≥N) → процедура → тест → расписание → модель больше не нужна
```

## Порог

| признак | порог для кристаллизации |
|---|---|
| одинаковых команд в сессии | ≥3 |
| одинаковая связка команд в разных сессиях | ≥5 |
| связка с ветвлением по результату | ≥10 (сложнее, риск ошибки выше) |

Порог — гипотеза, а не измерение. Меняется только с замером (P9: гейт не ослабляется).

## Что можно и что нельзя кристаллизовать

| можно | нельзя |
|---|---|
| сбор фактов с известным форматом (счётчики, списки, сверки) | задачи, где нужен выбор между вариантами |
| проверки с детерминированным ответом | оценка «достаточно ли хорошо» |
| подготовка среды (создать, скопировать, развернуть) | формулировки и решения о границах |
| выгрузка и нормализация данных | всё, где ответ зависит от смысла запроса |

Правило: **кристаллизуется только то, что имеет детерминированную проверку.** Если проверка
требует суждения, процедура станет источником ложной уверенности — хуже, чем вызов модели.

## Куда попадает процедура

1. **Заметка** с примером входа и ожидаемого выхода (в `lab/notes/`).
2. **Скрипт** в `bin/` с `--selftest`: он обязан падать на посаженном нарушении.
3. **Принцип** в `AGENTS.md`: агент обязан использовать процедуру, а не повторять команды.
4. **Расписание** — если у процедуры есть регулярность.

## Что это меняет в цикле

- Перед шагом агент смотрит: есть ли процедура под эту задачу (`hs plan` / справочник).
- `hs step` отмечает повтор — сигнал, что процедуры ещё нет.
- Отчёт показывает долю повторов: она должна падать. Это метрика кристаллизации.

## Метрика

| величина | что показывает |
|---|---|
| доля повторов в прогоне | сколько ещё не кристаллизовано |
| число процедур с `--selftest` | прочность кристаллизации |
| шагов на задачу | должна падать при росте процедур |

## Риски

1. **Кристаллизация суждения.** Процедура начнёт отвечать там, где нужен человек.
2. **Застывание.** Процедура переживает причину, по которой появилась; нужна дата и условие пересмотра.
3. **Ложная экономия.** Процедура дешевле вызова модели, но дороже в поддержке; порог должен учитывать частоту.

## Что это не доказывает

Что 22 % повторов действительно кристаллизуемы: часть из них — законные повторные проверки.
Что порог 3/5/10 верен. Что процедуры не начнут выдавать устаревший ответ.

## Первый кандидат: `cd` в начале команды

Подсчёт по всем сессиям: **19 372 команды из 44 507 (43,5 %) начинаются с `cd`**. Это не работа, а
настройка каталога, повторяемая в каждом вызове.

Поэтому в `hs step` добавлена нормализация: ведущий `cd <dir>;` перехватывается, каталог
применяется к шагу, в журнале ставится `cwd_normalized: true`. Модель больше не обязана писать
`cd` — это первая процедура, выведенная из наблюдения, а не из плана.

## Второй кандидат: преамбула Python

Подсчёт: **14 729** команд вызывают venv-интерпретатор, **2 164** задают `PYTHONIOENCODING`,
**1 048** — `ErrorActionPreference`. Суммарно это уже сравнимо с `cd`: фиксированная обёртка,
повторяемая в каждом запуске.

Процедура: `hs py <файл>` или `hs py --code "<код>"` — сам выбирает интерпретатор проекта, ставит
UTF-8, возвращает код возврата. Модель больше не пишет преамбулу.

## Итог по двум процедурам

| процедура | что заменяет | масштаб |
|---|---|---|
| `cd` → `cwd_normalized` | ведущий `cd` в команде | 19 386 |
| `hs py` | `$py=...; $env:PYTHONIOENCODING=...` | 14 729 |

Вместе — около 34 тысяч вызовов, где повтор заменим кодом. Это не «оптимизация на глаз», а
измеренный адрес.

**Проверено на практике (E-0011):** одна и та же задача — прогнать 8 наборов тестов — потребовала
12 команд без процедур и 8 с ними (−33 %), при одинаковом результате и без четырёх шагов разведки.


## Автоматизация и надёжность: петля, а не разовый аудит

Обнаружение повторов перестало быть ручным скриптом: `python bin/hs.py repeats --sessions --limit 40`
печатает кандидатов по порогам, `hs procs` показывает реестр процедур из `procedures.json`.

Петля:

```
журналы → hs repeats (кандидаты) → процедура → selftest → реестр (procedures.json)
        → автоматический запуск по расписанию → журналы → снова repeats
```

### Что нашлось на первых 25 крупных сессиях

25 182 вызова, 189 кандидатов. Верхние — не разрозненные команды, а **циклы ожидания**:

| повторов | что |
|---|---|
| 202 | `cd repo; python scripts/library_wake.py --check; git log…` |
| 91 | `library_wake.py --wait --timeout 3600 …` |
| 74 | проверка «замков» и времени каждые несколько секунд |

Это важнее, чем экономия шагов: агент **опрашивал** среду вместо того, чтобы ждать события. Такая
процедура кристаллизуется не в батч-скрипт, а в примитив ожидания (событие, а не поллинг).

### Правила надёжности

1. У каждой процедуры есть `selftest` — команда, которая падает, если процедура сломалась.
2. `status` процедуры: `candidate` → `active` → `retired`; перевод только по замеру.
3. Процедура, которая не использовалась N недель, уходит в `retired` — иначе реестр гниёт.
4. Ошибка процедуры пишется в `lab/failures/`, как любой другой отказ.

### Замер, который решает

Доля повторов в новых прогонах должна падать. Если она не падает после добавления процедуры —
процедура не соответствует реальной работе, и её надо пересмотреть, а не защищать.
