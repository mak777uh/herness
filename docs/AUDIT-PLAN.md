## 2. Оценка по принципам

**Закон 1 «число без команды — не результат» — выполняется, но есть перекос.**
218 утверждений с командой и артефактом. Однако **число утверждений само по себе ничего не
доказывает**: значительная часть — учёт (сколько задач, какие файлы), а не знание. Метрика покрытия
1.00 измеряет дисциплину ведения реестра, а не истинность. Риск: «218 утверждений» читается как
«много сделано»; это подмена.

**Закон 2 «отрицательный результат остаётся» — выполняется лучше всех.**
33 отказа, отклонённая запись в складе решений (A-0006), отклонённые варианты в `eliminations.md`.
Это сильная часть работы.

**Закон 3 «каждый отчёт содержит что это не доказывает» — выполняется частично.**
В README и обзоре есть, в артефактах `research/outputs/*` — как правило нет.

**Главный системный риск: 25 из 27 гейтов проверены только успехом.**
Сегодня дважды выяснилось, что гейт открыт: «автономия» срабатывала на собственном описании,
а правило «перед механизмом — поиск по складу» вообще не было гейтом. Гейт без отрицательного
контроля — это украшение: он выглядит работающим и не проверен.

**Второй риск: измерения держатся на догадке о именах.**
`bin/judge_metrics.py` определяет задачу по префиксу имени журнала. Это работает, но это
соглашение в голове, а не данные: переименование журнала молча выкинет прогон из метрик.

**Третий риск: узкая база измерения.**
77 журналов, но фактически 5 семейств задач (P27 короткие, MuSiQue, отказ, два контрольных).
`pass^k` при k≥3 почти нигде нет, поэтому «надёжность» измерена слабо.

**Четвёртый: отказы не связаны с защитой от повторения.** У 33 отказов нет поля «каким гейтом
закрыт». Мы знаем, что ошибка была, но не знаем, что она не повторится.

## 3. План изменений (по приоритету, с критерием приёмки)

### P0 — то, без чего остальное ненадёжно

**P0.1. Отрицательный контроль для всех гейтов.**
Общий инструмент `bin/gate_probe.py`: для гейта создаёт временную копию состояния, ломает условие
(секрет в файле, утверждение без команды, ADR вне карты глубин, защищённый путь в индексе) и требует
ненулевой код. Начинаем с пяти самых рискованных: секреты, утверждения, ссылки, глубины, харнессы.
*Приёмка:* ≥5 гейтов имеют записанный отказ; отчёт `research/outputs/gate-probes.txt`.
*Почему первым:* гейт — это то, что защищает все остальные выводы.

**P0.2. `runs/index.json` — журнал как данные.**
Для каждого журнала: путь, задача, критерий, вердикт, число шагов, расход. `judge_metrics.py`
читает индекс, а не угадывает по имени.
*Приёмка:* набор метрик не меняется при переименовании журнала; индекс генерируется командой.

**P0.3. Вес утверждений.**
Поле `weight: core|support` в `CLAIMS.md` (или отдельный список). Core — то, на чём стоит продукт
(журнал, хост, приёмка, метрики, отказ). Support — учёт.
*Приёмка:* гейт печатает «core: N, support: M» и падает, если core < 20; в README указывается
**core**, а не общее число.

### P1 — эффективность и надёжность

**P1.1. Связь «отказ → гейт».**
В `lab/failures/F-*.md` поле `caught_by` (гейт или тест). Метрика `repeat_protection` = доля
отказов с защитой.
*Приёмка:* ≥ половины отказов имеют `caught_by` и проверены пробой из P0.1.

**P1.2. `pass^k` при k≥3** на 4 задачах, где уже есть по 3–4 прогона; отчёт с интервалом.
*Приёмка:* число в артефакте, а не «примерно».

**P1.3. Длинная работа:** пять обрывов подряд в одной задаче + бюджет кампании.
*Приёмка:* выживание 5/5, потеря работы ≤ 1 шаг на обрыв.

### P2 — гигиена и перенос идей

- 4 артефакта без ссылок: либо сослаться, либо удалить (иначе склад раздувается);
- 14 маркеров XXX/TODO: разобрать, каждый — либо задача, либо удаление;
- `prior_art` в складе решений (последнее звено правила «сначала справочник»);
- hooks на хосте, `clarify` — после P1, не раньше.

## 4. Чего НЕ делаем (сознательно)

- не добавляем многоагентность и не гонимся за внешними бенчмарками с браузером;
- не ставим LLM-судью в вердикт;
- не наращиваем число утверждений «для покрытия»: лучше 60 core, чем 400 учётных;
- не публикуем наружу.

## 5. Что этот аудит не доказывает

- что найденные 33 отказа — все; скорее всего часть дефектов не проявилась на наших 5 семействах
  задач;
- что гейты после P0.1 станут надёжными: проба проверяет реакцию на **известный** дефект, а не на
  неизвестный;
- что план оптимален: он выведен из текущих чисел и может измениться после P0.2, когда измерения
  перестанут зависеть от имён.
