## 2. Q11 — где живёт полная семантика карточки

Полная проверка карточки (все preconditions/postconditions, лимиты, примеры) — на **promoter**,
на хосте, до допуска. В runtime остаётся тонкий слой: проверка admission, exact-byte привязка
к бинарнику/карточке/политике, проверка класса данных (K6) и жёсткого K4. Runtime не
пересчитывает всю карточку и не «дообъясняет» её: если байты не совпали с допущенными —
`K11_ADMISSION_REQUIRED`.

Почему: две полные реализации одной семантики (promoter и runtime) расходятся, и тогда
непонятно, какая из них закон. Тонкий runtime можно проверить на точное совпадение байтов,
полную семантику — на хосте, где есть ключ и реестр.

Что это не доказывает: что promoter реализован или что runtime не пропускает запрещённое
действие. Это доказывают тесты этапов 6–7, а не этот выбор.

## 3. Q12 — S02: поток, счётчики и границы

Замораживается в [`lab/prereg/HEAD-SLICE-R1.json`](../lab/prereg/HEAD-SLICE-R1.json) как `s02`:

| поле | правило |
|---|---|
| `CHUNK` | 4096 байт на `read()`; цикл не читает больше `max_bytes_read` |
| `bytes_read` | сумма байт **выданных** строк; конец последней выданной строки |
| `bytes_received` | сколько байт получено из `read()`; только диагностика в evidence, не в выводе |
| EOF | только `read() == 0`; отсутствие строки — не доказательство EOF |
| `truncated` | `true` при line/byte/output limit; `false` только при доказанном EOF |
| `cap < первой строки` | `K4_RESOURCE_LIMIT` (ни одной полной строки не помещается) |
| output overflow | `stop_reason=output_cap`, исход `ok`, не `K4` |
| CR | сохраняется как байт; строки делятся по `\n`, CR не срезается |
| UTF-8 | проверяется только для выданных строк; ошибка — `S12_ENCODING` |
| частичная строка | никогда не выдаётся: либо строка целиком, либо остановка |

Почему: `bytes_read`, посчитанный «по файлу», врёт при остановке; `truncated=false` при
недоказанном EOF — ложный зелёный; `output_cap` — это штатная остановка вывода, а не
превышение K4.

Что это не доказывает: что реализация соблюдает таблицу. Это доказывает `HEAD-SLICE-R1`
с восемью критическими контролями и тремя повторами.

## 4. Q13 — комната

WSL2 + KVM, QEMU `-M microvm`, ровно один `-accel kvm`, без NIC, диска, host mounts,
9p/virtiofs. Fallback на WHPX/TCG запрещён: TCG — симуляция, не граница безопасности.
`KVM_RUN` доказывается двумя независимыми способами: QMP `query-kvm`
(`present=true, enabled=true`) и счётчик tracepoint `kvm:kvm_entry` > 0 во время загрузки.
Отрицательный контроль: тот же запуск без доступа к `/dev/kvm` обязан отказать, а не
тихо уйти в TCG.

Почему: без `KVM_RUN` нельзя утверждать, что гость исполнялся на аппаратной границе.

Что это не доказывает: что гость не имеет сети — это доказывается конфигурацией QEMU и
отсутствием устройств, а не наличием KVM.

## 5. Q14 — наблюдение эффектов

seccomp в режиме TRACE + ptrace в госте. Разрешено утверждать только
`observed_in_guest` и `enforced_by_kernel`. Запрещено `observed_independent` и
`K9_proven`: наблюдатель живёт в той же комнате, что и наблюдаемый код, и не является
независимым оракулом.

Что это не доказывает: отсутствие эффекта за пределами наблюдаемых syscall. Пропуск
наблюдения — не «чисто», а N/A.

## 6. Q15 — ключ

Один operational Ed25519 ключ + offline backup. Восстановление — только через отзыв и
поднятие `min_epoch`; backup **не** получает права подписывать admission. Формат подписи —
raw Ed25519 (RFC 8032) с доменным префиксом `herness-admission-v1`, отдельно от JCS-байтов.

Церемония создания настоящего ключа — за владельцем. Агент создаёт только эфемерные
test-only ключи для self-test и среза.

## 7. Q16 — пилот генератора

Один шаблон `file_read_stream`: 20 спецификаций (12 допустимых + 8 граничных), 24 мутанта
(16 критических + 8 функциональных), 3 повтора. Пороги и held-out хеши фиксируются до
запуска. Пилот запускается **только после** зелёного ручного `head`. Авто-approval нет,
`K9_proven` нет; результат — инженерный scorecard, не статистическое доказательство.

## 8. Q17 — порядок отказов и словарь v3

Порядок проверок в runtime: `K11` → `S1` → `S6` → `K6_SECRET_EGRESS` →
`K6_DATA_CLASS_UNKNOWN` → объектные ошибки (`S10`/`S11`) → `K4` → `S12`.

Словарь v3 аддитивен, старые коды не переименовываются:

| код | что означает | что делать |
|---|---|---|
| `S10_NOT_FOUND` | объект объявлен, но его нет | создать объект или отказать |
| `S11_NOT_REGULAR` | объект не regular file (каталог, устройство, FIFO) | отказать, не открывать как файл |
| `S12_ENCODING` | выданные байты не являются допустимым UTF-8 | отказать, не выдавать содержимое |
| `S13_TOOL_INACTIVE` | инструмент не активен по derived authority | не запускать; нужен admission и право запуска |
| `S14_ALREADY_EXISTS` | create-new не может перезаписать существующий объект | выбрать новый путь или отказать |

`output_cap` — не отказ, а штатная остановка. `S14` не переиспользует `S1`/`S6`.

## 9. Q18 и F04 — реестр и две оси статуса

Реестр замораживается: `registry.jsonl` — genesis-снимок, дальнейшие изменения — только
события в `lab/tools/registry.events.jsonl` с `prev`/`seq`/JCS/хешами. `active` не хранится:
он производный от событий и текущего evidence. Все шесть legacy-инструментов (`search`,
`list`, `read`, `write`, `seal`, `netprobe`) — `quarantined`; `search` — rejected;
`net` — отдельный bridge path вне реестра.

Две независимые оси:

| ось | значения | где хранится |
|---|---|---|
| подпись | `not_admitted → owner_signed` | admission-манифест |
| право запуска | `admitted_inactive → activated` | производное от событий и evidence |

`activated` не хранится и не подставляется: без текущего evidence инструмент не запускается.
`K9_proven` не выдаётся.

## 10. A01 и AUDIT — admission и порядок аудита

Admission: JCS (RFC 8785, подмножество без float), detached подпись, exact-byte binding
card/source/binary/fixture/policy/room. Promoter — на хосте. На Linux запуск только через
memfd + `F_SEAL` + `fexecve`/`execveat`; на Windows — только проверка и хранение, запуск
отказом. `seal`/`netprobe` вне v0.

Порядок аудита до среза: policy (`!`, единый источник) → write (`O_EXCL`, `NO_XDEV`,
нормализация) → read/search/list → две карточки `head` → процессы и self-exec →
admission. Каждый патч — с negative control; гейт не ослабляется.

## 11. Что этот документ не решает

- не меняет конституцию и не добавляет прав инструментам;
- не делает `head` активным: он остаётся candidate до настоящего owner-admission;
- не закрывает `HEAD-SLICE-R1` сам по себе: срез закрыт отдельным прогоном E-0030 (PASS);
- не отменяет Q1–Q10 и не переоткрывает принятые решения R5–R7;
- не является публикацией наружу и не разрешает её.
