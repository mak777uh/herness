# ADR-0062 — herness verify: измерять проверяемость чужого README

**Дата:** 15.11.2026. **Статус:** принято. **Связано:** `VERIFY-REPO-R1`, `E-0027`, `C-0306`, `F-0093`.

## Решение

Первый внешний инструмент харнесса — не комната, не ядро и не сеть. Это `bin/verify_repo.py`:
он отвечает на один вопрос о **чужом** репозитории — *какие числа в README можно воспроизвести,
а какие нет*, и печатает отчёт, квитанцию и границу.

## Почему так

1. **Нулевая установка.** Python + stdlib. Не нужны QEMU, WSL, Lean, ключи и модель.
2. **Результат за 30 секунд.** Один прогон — один отчёт; квитанция хранит sha256 прочитанного README.
3. **Не судит истинность.** «Нет команды» ≠ «ложь». Это различие — то же, что между `anchored` и
   `strict` внутри харнесса (ADR-0058).
4. **Не дублирует MethodSeal.** Тот замораживает методологию и запрещает правку; здесь — измерение
   формы утверждения.

## Две меры, а не одна

- **Широкий счёт** — любая строка с числом вне кода, таблиц и бейджей.
- **Строгий счёт** — где у числа есть единица измерения (тесты, звёзды, загрузки, мс, проценты).
- **Доля** считается по строгому счёту и печатается рядом с широким: иначе число льстило бы себе.

## Граница (объявлена в каждом отчёте)

- Читается только `README*`. `docs/`, `CLAIMS.md`, бенчмарки, CI, таблицы, бейджи и код — не читаются.
- Прогон на пяти репозиториях дал 0–3 строки с числами в прозе (строгих 0–1): числа живут в таблицах и бейджах.
  Значит «доля 0.00» — свойство текста, а не приговор проекту.
- Инструмент ничего не запускает из чужого репозитория: только читает файл. Это осознанно:
  запуск чужого кода — отдельное решение с отдельными границами.

## Проверено и отменено: таблицы (VERIFY-REPO-R2)

Гипотеза «в таблицах README чисел больше, чем в прозе» проверена на тех же пяти репозиториях.
Результат — **FAIL**: `table_total = 0` у всех пяти. Числа в этих README живут в бейджах
(счётчики звёзд и загрузок) и в `docs/`, а не в таблицах.

По объявленному в критерии правилу расширение отменено: код читает прозу, как в R1.
Оставлено исправление дефекта, найденного по ходу: числа и единицы теперь ищутся без ссылок
и URL — до него `is%3Aissue` в ссылке давало «%» и цифру, и в markitdown два «табличных»
утверждения были мусором.

Гипотеза возвращается только с образцом: репозиторий, где в README есть числовая таблица.

## Поверхность прибора: пять репозиториев с бенчмарками (VERIFY-REPO-R3)

Гипотеза «в README проектов, которые меряются скоростью, числа стоят рядом с командой» проверена
на пяти README, скачанных с `raw.githubusercontent.com` (без клона).

Результат — **FAIL по объявленным порогам**: ≥3 строгих утверждения у 2 из 5 (simdjson 11, LightGBM 3),
команда рядом — только у duckdb (1 из 5). Повтор совпал.

Но сумма говорит другое: **17 строгих утверждений против 2** на «обычных» README. Поверхность есть
именно там, где проект заявляет скорость: у simdjson 25 строк с числами, 11 строгих — и ни одной
команды воспроизведения в README. Команды живут в `benchmark/`, `docs/` и CI.

Порог не понижен: R3 остаётся FAIL, гипотеза возвращается с новым критерием, если понадобится.
Практический вывод для продукта: прибор измеряет **разрыв между числом и местом его проверки**,
а не «качество README»; для репозиториев с бенчмарками этот разрыв — обычное дело.
