## Контекст проекта (без него ответы будут мимо)

**herness** — харнесс для агентов на трёх уровнях: политика (кто/что/ресурс), посредник (исполняет),
замыкание (ничего не пройдёт мимо). Репозиторий: <https://github.com/mak777uh/herness> (MIT, публичный).
Сейчас: 32 гейта с 34 пробами, 305 утверждений, 8 Lean-модулей, CI из 5 job'ов.

**Ядро и комната:** собственное ядро Linux 6.18 (стены закрыты), QEMU-комната с Rust PID1 без shell,
шесть инструментов (`read`, `list`, `search`, `write`, `seal`, `netprobe`), журнал HSJ2 (CRC кадра +
цепочка событий). Инструменты — capability-хэндлы НЕ используются: каждый инструмент проверяет путь
против объявленного замыкания (`/mnt/**`).

**Доказательства:** `proofs/Proofs/Policy.lean` (6 теорем о посреднике), `proofs/Proofs/Bridge.lean`
(3 теоремы о мосте: адрес из конфигурации, токен не в ответе, ответ не переписывается),
`PartBridge.lean` (5 теорем), три негативных контроля обязаны падать. Тулчейн `v4.36.0-rc2` в WSL.
Три аксиомы: `propext`, `Classical.choice`, `Quot.sound`.

**Что делаем:** карточка инструмента (JSON: входы, выходы, замыкание, отказы, примеры) → генерация
Rust-тела и правил политики → лестница из 8 ступеней → реестр с переиспользованием. Мосты между
частями — та же схема, но с Lean-моделью и доказательством.

**Два раунда уже прошли:** первый — 5 «обычных» README (0–1 строгих чисел), второй — 5 с
бенчмарками (17 строгих, 1 с командой). Третий — два независимых ответа на 29 вопросов.

## E.A. Доказательства

**R2-1. NC с witness: как доказать ожидаемый отказ для наших теорем в Lean 4.36?**
Наш негативный контроль (`BridgeNegative.lean`) сейчас проверяется как «не собирается». Обе
модели первого круга согласны: падение ≠ ложность (таймаут тактики даёт тот же rc≠0). Как
построить **свидетель контрпримера** — `decide` на конкретном входе / SlimCheck / явная лемма
о ложности? Какие шаблоны применимы к нашим теоремам (`(forward cfg req).host = req.wantedHost`)?
*Что решает:* переделка всех негативных контролей.
*Ссылки:* `proofs/Proofs/BridgeNegative.lean`, `bin/lean_wsl.py` (строки 143–152).

**R2-2. Cedar-style DRT для нашего посредника: сколько входов и какой генератор?**
Прецедент Cedar: модель доказана в Lean, Rust сверяется дифференциальным случайным тестированием
на миллионах входов. Наш посредник — `core-rs/src/loopmod.rs` (6 инструментов, 19 правил политики).
Сколько входов нужно, чтобы DRT имел силу? Какой генератор — `cargo-fuzz`, `proptest`, свой?
Каков критерий вердикта («модель и код совпадают на N входах»)?
*Что решает:* заменит `policy_diff.py` (18 фиксированных запросов).
*Ссылки:* `core-rs/src/loopmod.rs`, `lab/tools/policy.json`.

**R2-3. olean-аудит и lean4checker в нашем WSL.**
Урок marfagenez: 35 из 48 файлов не компилировались. Мы сделали `bin/check_lean_imports.py`
(8 модулей, 5 корней). Чего не хватает: (1) `olean`-аудит (счёт .olean == счёт .lean);
(2) `lean4checker` — повторная проверка `.olean` через ядро (для недоверенных AI-доказательств).
Как встроить в наш WSL-прогон (`bin/lean_wsl.py`)? Что считать провалом?
*Ссылки:* `bin/check_lean_imports.py`, `bin/lean_wsl.py`.

**R2-4. Mutation testing для инструментов: цена и целевой mutation score.**
Обе модели первого круга согласны: примеры — минимальная форма, полноту меряет mutation testing
(`cargo-mutants`). Какова цена прогона на шести инструментах (средний размер функции ~50 строк)?
Какой mutation score считать достаточным для признания примеров полными?
*Ссылки:* `core-rs/src/loopmod.rs`, `bin/tool_card.py`.

## E.C. Capability и архитектура

**R2-8. Capability-хэндлы в нашем ядре: применим ли cap-std/WASI-подход?**

по построению). Наша комната — собственное ядро + PID1, не WASI. Применим ли подход: PID1
раздаёт каждому инструменту хэндлы (read-only / write-only / net) вместо проверки пути?
Какие ограничения в собственном ядре?
*Ссылки:* `core-rs/src/loopmod.rs`, `core-rs/src/sandbox.rs`, `docs/DESIGN-0002-tool-generation.md` §2.

**R2-9. Plug-in match для карточек: как проверить «предусловие слабее, постусловие сильнее»?**
Обе модели: заменимость — plug-in match (Zaremski–Wing). Как механически проверить для карточек,
где предусловие = `closure`, постусловие = `outputs`? Есть ли инструмент для JSON-контрактов?
*Ссылки:* `bin/tool_card.py`, `lab/tools/registry.jsonl`.
