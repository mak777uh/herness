# Предложение: харнесс пишет мосты под задачи

**Дата:** 16.11.2026. **Статус:** предложение, не решение. **Основание:** формулировка владельца —
«харнесс пишется от задач»: если задача повторная, берётся готовый мост; если задача идёт дальше —
достраивается новое.

## Что уже есть (не с нуля)

| элемент | где | состояние |
|---|---|---|
| модель моста и его теорем | `proofs/Proofs/Bridge.lean` | адрес только из конфигурации, токен не в ответе, ответ не переписывается |
| мост между частями | `proofs/Proofs/PartBridge.lean` | 5 теорем, обе части в namespace, агрегат собирается (ADR-0061) |
| сборка и аксиомы | `bin/lean_wsl.py` | агрегат `Proofs` обязан собраться; теоремы — только `propext`, `Classical.choice`, `Quot.sound` |
| негативный контроль | `Proofs.Negative`, `Proofs.PartBridgeNegative` | оба обязаны **падать**, иначе проверка пуста |
| сверка Rust с моделью | `bin/policy_diff.py` | 15 из 18 совпадают; три — ограничение модели, не кода |
| прецедент «мост в три языка» | `H-0180` (Lean → C → Rust) | пре-регистрация есть, прогона нет |
| дисциплина | `lab/prereg/`, `CLAIMS.md`, гейты с пробами | 32 гейта, 34 пробы, отрицательный результат остаётся |

То есть **проверять** сгенерированный мост уже есть чем. Нет трёх вещей: контракта моста как
данных, реестра с переиспользованием и самого шага синтеза.

## Что такое мост в этой схеме

Мост — не код, а **обязательство**, у которого есть:

```json
{
  "id": "br-<hash контракта+законов+кода+тулчейна>",
  "from": "cell-a", "to": "cell-b",
  "contract": {
    "inputs":  [{"name": "lines", "type": "seq[str]"}],
    "outputs": [{"name": "count", "type": "nat"}],
    "resources": {"read": ["/mnt/work/**"], "write": [], "net": []}
  },
  "laws": ["output_is_function_of_input", "no_read_outside_root", "no_net"],
  "proof": {"lean": "proofs/Proofs/BridgeGen/<id>.lean", "axioms": ["propext", "Classical.choice", "Quot.sound"]},
  "code": {"rust": "core-rs/src/bridge_gen/<id>.rs", "tests": "core-rs/tests/<id>.rs"},
  "evidence": {"build": "research/outputs/<id>-lean.txt", "diff": "research/outputs/<id>-diff.txt"},
  "toolchain": "leanprover/lean4:v4.36.0-rc2",
  "verdict": "verified"
}
```

Правило: **мост существует, только если его доказательство собирается и его негативный контроль
падает**. Файл без зелёной сборки — не мост, а черновик; он лежит в `lab/` и в реестр не попадает.

## Цикл (7 шагов)

1. **Подпись задачи.** Из задачи выводится сигнатура: что входит, что выходит, какие ресурсы
   нужны, какие законы обязаны держаться. Подпись — хеш; она же ключ поиска.
2. **Поиск в реестре.** Есть мост с той же подписью → шаг 3. Нет → шаг 4.
3. **Переиспользование — с перепроверкой.** Мост не «доверенный», а «проверяемый»: `lake build`
   его модуля, сверка аксиом, `cargo test`, негативный контроль. Зелено → мост отдаётся задаче,
   в журнал пишется `bridge/reuse` с id и хешем доказательства.
4. **Синтез.** Модель пишет три вещи: Lean-модель с законами, доказательство, Rust-реализацию —
   и **негативный контроль** (заведомо ложное утверждение, которое обязано не доказаться).
5. **Верификация.** Агрегат собирается; аксиомы стандартные; негативный контроль падает;
   `policy_diff` показывает совпадение модели и кода на наборе входов. Любой красный — мост
   не регистрируется, в отчёт идёт `BLOCKED` с причиной (а не «не получилось»).
6. **Регистрация.** `id = hash(contract, laws, code, toolchain)`. В реестр попадает только
   `verdict: verified`; всё остальное — в `lab/failures/` как отрицательный результат.
7. **Рост.** Задача, которой нужны два моста, получает композит: его доказательство импортирует
   теоремы частей, а контракт — их контракты. Композит регистрируется так же, с той же проверкой.

## Почему это не превращается в свалку сгенерированного кода

- **Реестр — актив, а не свалка.** Ценность харнесса становится в том, сколько у него
  *проверенных* мостов, а не сколько кода он написал. Это измеримо: число мостов с зелёным
  доказательством и падающим контролем.
- **Переиспользование требует перепроверки.** Доверие к мосту — не «мы его однажды проверили»,
  а «сборка сходится сейчас, на этом тулчейне». Тулчейн входит в id: смена Lean ломает id, а не
  репутацию.
- **Отрицательный контроль обязателен для каждого моста.** Без него доказательство может быть
  пустым (`sorry`, лишняя аксиома) — у нас уже есть случай, когда это ловилось (`F-0080`).

## Что может убить идею (честно)

1. **Доля успешного синтеза.** Если модель не доказывает 8 из 10 мостов, реестр не растёт, а смена
   превращается в перебор. Это надо измерить первым, а не поверить.
2. **Композиция взрывает обязательства.** Два моста — три теоремы; пять — уже трудно. Начинать
   надо с языка законов, который композируется механически (разрешения, происхождение адреса,
   отсутствие сети), а не с произвольных предикатов.
3. **Дрейф кода от модели.** Lean доказывает свойство модели, не Rust. Лечится тем же, чем политика:
   дифференциальной сверкой на наборе входов (`policy_diff`), и это отдельный гейт.
4. **Стоимость.** Синтез дорог; выигрыш только на повторах. Если повторяемость задач ниже ~30 %,
   реестр не окупится.

## Первый срез (одна вертикаль, до любого роста)

**Тип задачи:** «прочитать файл, отфильтровать строки по подстроке, посчитать» — встречается
в наших же сериях и годится как минимальный мост «хост → комната».

**Законы моста (три, проверяемые):**
- `output_is_function_of_input` — результат зависит только от входа;
- `no_read_outside_root` — чтение не выходит за объявленный корень;
- `no_net` — сеть не трогается.

**Прогон:**
1. Синтез один раз: Lean-модель + три теоремы + Rust + негативный контроль.
2. Регистрация моста `br-<hash>`.
3. Вторая задача того же типа: переиспользование, перепроверка, вердикт.
4. Замер: шаги, время, стоимость — с мостом и без; вердикты обязаны совпасть.

**Порог (объявляется до прогона):** синтез даёт зелёное доказательство со стандартными аксиомами
и падающий контроль **с первой или второй попытки**; переиспользование даёт тот же вердикт и
**не больше половины** шагов первого прогона. Если синтез не удался — это тоже результат: тогда
идея остаётся предложением, а не планом.

## Связь с видением

Владелец сформулировал это 07.11.2026 дословно: «сам харнесс дописывает себя только вот такими
строгими штуками… любой внешний код он тоже пишет таким образом» (`docs/VISION-0001-harness-as-cell.md`).
Это предложение — первый инженерный перевод той фразы: не «харнесс пишет код», а «харнесс пишет
обязательство и предъявляет доказательство, иначе код не становится мостом».

## Чего это предложение не решает

- Не отвечает, **как** модель будет искать доказательства (тактики, библиотека лемм).
- Не описывает, как хранить мосты между машинами (реестр локальный; сеть — отдельная тема VecDHT).
- Не говорит, что делать с мостами, у которых законы не выразимы в выбранном языке (например,
  «мост не врёт про время» — это уже про часы, а не про данные).
