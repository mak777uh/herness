# ADR-0047. Контракт провайдера: сессия, обрезание, лимиты

**Статус:** принято 31.10.2026 по трём проходам P24 и двум собственным замерам.

## Что проверено замерами (не по документации)

| факт | число |
|---|---|
| пустой `content` при `max_tokens=24` | `finish_reason=length`, content пуст, reasoning 24 (C-0151) |
| тот же промпт при `max_tokens=800` | `finish_reason=stop`, content есть, reasoning 46 |
| стабильный `x-opencode-session` | второй вызов: `cache_read=512`, input 60, allowance 1,208e-05 (C-0152) |
| новый UUID на каждый запрос | `cache_read=0` всегда, allowance 5,724e-05 |

Отсюда два решения, оба дешёвые и оба — исправление дефектов:

1. **Классификация ответа по `finish_reason` раньше текста.** Пустой `content` при `length` — это
   обрезание (`Reply::Truncated`, статус прогона `truncated`), а не «модель промолчала». Раньше цикл
   называл это ошибкой формата.
2. **Сессия стабильна на процесс.** Мост генерировал новый UUID на каждый запрос — это отключало
   кэш и стоило в 4,7 раза дороже на повторяющихся промптах.

`max_tokens` поднят с 300 до 2000: при 300 рассуждающая модель тратит бюджет на reasoning и вернуть
текст может не успеть (46 reasoning-токенов даже на «ответь одной строкой»).

## Что установлено по документации и осталось непроверенным

- **Лимиты Go — долларовые окна, а не число запросов.** Проходы дают разные числа: $12/$30/$60
  (5 ч / неделя / месяц) и, в другом месте, тарифы $10/$40 с иными окнами. **Расхождение не
  закрыто**; в реестр как факт не идёт.
- **`GET /zen/go/v1/usage`** — по одному из проходов (PR #32913) возвращает остаток по трём окнам.
  Не проверял; если работает, это дешёвый способ узнать лимит до отказа.
- **`allowance`/`list_cost`** — что именно они значат, документировано слабо; мы их **пишем в
  журнал** и не строим на них логику.
- **Коды исчерпания** (402 против 429 против остановки) — расходятся в источниках; фиксируем фактом
  только то, что видели сами: `402` на zen для платной модели, `429` для `-free`, `400
  MissingSessionID` без заголовка.

## Протокол инструментов: не меняем, но изолируем

Измерения есть (arXiv:2607.03953: текстовый/NLT +14,9 п.п. точности и −93 % критических ошибок на
14 моделях; ACL REALM 2026: принудительный текст может **снижать** fidelity у моделей с нативным
tool-calling). Универсального победителя нет, поэтому:

- остаёмся на `TOOL/DONE` — наша модель рассуждающая, и для этого класса измерения за текст;
- но выносим разбор в отдельный слой (`parse_step` → валидатор → исполнение), чтобы нативный
  адаптер можно было добавить, не трогая цикл;
- правило стриминга и частичных вызовов нам пока не нужно: мост не стримит.

## Границы

- Числа лимитов Go в реестр не внесены: источники противоречат друг другу.
- `reasoning_effort` мы не передаём; поведение модели без него — то, что измерено выше.
- Валидатор аргументов инструментов пока один: имя инструмента и разбор строки. Схемы аргументов
  (JSON Schema) нет — это следующий слой, и он нужен независимо от протокола.
