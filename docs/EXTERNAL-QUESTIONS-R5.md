# R5 — от ответов R4 к исполнимому v0

**Дата:** 2026-11-16
**Канон:** [mak777uh/herness](https://github.com/mak777uh/herness), ветка `main`
**Снимок кода и документов:** [`a4bcae5368bcdb4f02e369e7d1e7c69ee1418d09`](https://github.com/mak777uh/herness/tree/a4bcae5368bcdb4f02e369e7d1e7c69ee1418d09)
**Предыдущий круг:** [R4 — 45 вопросов](https://github.com/mak777uh/herness/blob/a4bcae5368bcdb4f02e369e7d1e7c69ee1418d09/docs/EXTERNAL-QUESTIONS-R4.md)
**Этот файл:** 24 вопроса следующего круга: 18 `P0`, 6 `P1`, 0 `P2`.

R4 закрыл P0 на уровне направлений. Две независимые модели сошлись в главном: текущей карточки
недостаточно, генератор нельзя писать до типизированного контракта и двусторонней проверки, а
QEMU-комната, а не WSL, является границей безопасности. R5 не пересказывает R4 и не просит ещё раз
доказать эти направления. Он просит закрыть конкретные развилки и написать минимальные артефакты,
из которых можно начать первую строку кода.

Ответы R4 не опубликованы целиком: они существуют у владельца как два больших текста. Ниже —
сводка, достаточная для ответа на R5. Если для ответа нужна точная формулировка R4, скажите об этом;
не додумывайте её.

## 0. Как читать и как отвечать

### 0.1. Что является хорошим ответом

Хороший ответ на вопрос R5 содержит:

1. **одно выбранное решение**, а не список «можно так или так»;
2. **артефакт**: JSON-схему, таблицу, псевдокод, state machine, manifest или тест-матрицу;
3. **границу применимости**: что этим решением нельзя доказать;
4. **негативный тест**: какой вход обязан быть отклонён;
5. **цену**: сколько это добавляет к v0 и что придётся отложить.

Ответ без артефакта считается мнением. Ответ, который расширяет права инструмента, противоречит
D2 и D8, даже если он удобен.

### 0.2. Шаблон

Для каждого вопроса:

```text
## <ID>
ANSWER: <одно решение в 1–3 предложениях>
CHOSEN: <A / B / синтез; если синтез — что именно взято>
WHY: <почему это проверяемо и совместимо с K1–K11>
ARTIFACT: <схема / псевдокод / таблица / manifest / тесты>
TESTS: <3–7 конкретных проверок, включая негативную>
FAILURE MODE: <как это решение может дать ложную уверенность>
NOT PROVEN: <что остаётся недоказанным>
CONFIDENCE: high / medium / low
```

Если вы считаете посылку вопроса неверной:

```text
CONTRADICTION <ID>: <что именно неверно>
EVIDENCE: <ссылка на файл/строку/тест>
ALTERNATIVE: <чем заменить>
```

Не переписывайте ответ молча.

### 0.3. Приоритеты

- `P0` — без ответа нельзя фиксировать схему, checker или первый вертикальный срез.
- `P1` — нужно для качества v0, но не блокирует первую схему.
- `P2` — в R5 не задаётся; отложено.

### 0.4. Ограничения

- Секреты не попадают в контекст и в git. В примерах — только синтетические canary-значения.
- Ничего не публикуется наружу без явного «да» владельца.
- Гейт не ослабляется, чтобы «стало зелёным». `N/A` не равно `green`.
- В WSL владельца работает другой проект. Нельзя трогать его файлы, глобальные настройки, сеть и
  firewall. Любой эксперимент — только в одноразовом каталоге/клоне.
- Конституцию меняет только владелец. Агент может просить поправку; генератор не меняет
  конституцию, лестницу, реестр, policy, bridge registry и журнал согласований.

## 1. Контекст за один экран

### 1.1. Где проект

`herness` — исследовательский харнес для QEMU-гостя: Rust PID1, Lean-модели, политика `nomos`,
журнал HSJ2, мосты, замыкание и провенанс. Каноническая линия — GitHub `main`; несколько агентов
работают последовательно, поэтому всё важное пушится, а следующий агент обязан понять, где
остановились.

Сейчас в репозитории есть:

- конституция v0 с K1–K11 и юрисдикцией;
- шесть инструментов: `read`, `search`, `list`, `write`, `seal`, `netprobe`;
- контракты, policy, registry, словарь отказов;
- карточка `head` как эталон;
- Rust PID1 с политикой и записью;
- Lean-модель мостов;
- WSL-симуляция политики;
- бумажный замер карточек и R2–R4.

Чего нет:

- генератора инструментов;
- типизированного контракта с эффектами, pre/post/frame;
- двусторонней проверки `card ↔ policy ↔ capability ↔ ceiling`;
- обеспеченных K6, K7, K9, K11;
- полноценного K8 (провенанс есть частично);
- admission-манифеста и реестра допусков;
- `bin/tool_examples.py`, на который ссылается лестница;
- повторного замера `netprobe` после решения K3.

### 1.2. Слои, которые нельзя смешивать

1. **Закон** — K1–K11 и поправки. Закон ограничивает; он не выдаёт разрешение.
2. **Потолок комнаты** — что физически доступно: корни ФС, сеть, время, память, байты выдачи.
3. **Контракт инструмента** — что инструмент обещает: типы, эффекты, pre/post/frame, отказы,
   лимиты, примеры.
4. **Policy** — решение allow/deny для конкретного запроса в конкретной комнате.
5. **Capability** — фактический OS-хэндл, который получил процесс.
6. **Реализация** — код, который можно выбросить и перегенерировать.
7. **Свидетельства** — хеши, журнал, тесты, доказательства, вердикты лестницы.

Карточка не является разрешением. `kind` не является разрешением. Зелёный тест не является
доказательством безопасности. `active` не означает «доверенный».

### 1.3. K1–K11 сжато

| id | закон | что ограничивает |
|---|---|---|
| K1 | `no_read_outside_root` | чтение только внутри корня комнаты |
| K2 | `no_write_outside_root` | запись только внутри рабочего корня |
| K3 | `no_net_except_declared` | прямой выход запрещён; только объявленный мост; adjacent соблюдает K1–K11; downstream — через K9; двойной allowlist |
| K4 | `bounded_resources` | время, память, выдача ограничены |
| K5 | `explicit_refusal` | ошибка — код из словаря; молчание — нарушение |
| K6 | `no_secret_outside_protected_space` | секрет/ключ не пересекает границу; redaction или отказ; неизвестное — отказ |
| K7 | `deterministic_output` | один вход → один выход; порядок/время только с waiver |
| K8 | `provenance` | у active-инструмента есть карточка, хеш и пакет свидетельств |
| K9 | `composition_preserves` | композиция инструментов/мостов сохраняет K1–K11 на защищённой границе |
| K10 | `no_self_modification` | инструмент/генератор не меняет конституцию, лестницу, реестр, policy, bridge registry, журнал согласований |
| K11 | `admission_to_protected_space` | чужой код входит только с явным согласованием, привязанным к хешам и области; до этого — карантин |

### 1.4. Ключевые рамки владельца

Полные D1–D12 — в R4. Здесь только то, что нельзя переспорить без нового аргумента:

- **D1:** канон — GitHub `main`; всё важное пушится; следующий агент должен понять, где остановились.
- **D2:** конституция — закрытый пул законов; инструмент получает поведение внутри K1–K11 и
  потолка комнаты, а не «права на всё».
- **D3:** сеть — только через объявленные мосты; прямой выход запрещён; сеть владельца не
  блокируется.
- **D4:** секреты не выходят за пределы защищённых пространств; неизвестная классификация — отказ.
- **D5:** юрисдикция — первая комната и граница входа в пространство владельца; это не мировое право.
- **D6:** чужое приложение/инструмент/мост/устройство входит только с явным согласованием,
  привязанным к хешам и области; до этого — карантин.
- **D7:** конституцию меняет только владелец; агент может запрашивать изменение.
- **D8:** сгенерированный инструмент судится конституцией, а не словами владельца; пока он не
  верифицирован, он недоверенный, и от него нельзя строить дальнейшую сеть доверия.
- **D9:** цель — понять, как сформировать конституцию и как начать писать от неё инструменты в
  рамках формализации языка; часть задач позже переносится внутрь харнеса.
- **D10:** критерий успеха генератора пока не сформулирован; нужен измеримый критерий.
- **D11:** каждый новый агент полностью отвечает за код и репозиторий и устраняет хвосты
  предыдущего.
- **D12:** секреты не в контекст и не в git; ничего наружу без «да»; гейт не ослабляется; находка
  только с воспроизводимым доказательством.

### 1.5. Что уже измерено и что это не значит

- Бумажный замер шести инструментов: 5 карточек валидны, главное право сохранено у 1/6, точное
  покрытие контракта — 0/6, глаголы — 10/21 (47.6%), типизированные I/O — 0/6. Порог
  `DESIGN-0002 §9` не пройден. Это замер **до** решения K3; `netprobe` нужно перемерить.
- WSL-симуляция: 30 PASS, 0 FAIL, 2 CONTROL, 5 N/A. Это проверка политики, а не граница
  безопасности. Она не защищает ноутбук и не доказывает QEMU-комнату.
- Lean-модель мостов проверяет включение множеств законов; это не семантика трасс и не
  соответствие Rust-коду.
- Зелёная лестница, хеш и proof не создают доверия автоматически.

## 3. Что подтверждено в коде на `a4bcae5`

Это не «находки» в смысле инцидента и не доказанные эксплойты. Это статически прочитанные дефекты
и один воспроизведённый ложный зелёный. Они важны потому, что R5 просит проектировать checker,
который не повторяет эти ошибки.

### 3.1. `card_atoms.py` умеет придумывать право на чтение

Файл: [`bin/card_atoms.py`](https://github.com/mak777uh/herness/blob/a4bcae5368bcdb4f02e369e7d1e7c69ee1418d09/bin/card_atoms.py#L36)

```python
read = list(fs.get("read") or [])
...
for scope in read or ["/mnt/**"]:
```

Если `closure.fs.read` пуст, функция синтезирует право `read` на `/mnt/**`. То есть карточка не
может честно сказать «я не читаю файлы»: пустой список превращается в противоположное утверждение.
Это не просто отсутствие проверки; это неверная декларация эффекта.

### 3.2. `conflicts()` не сравнивает положительные атомы с policy

Файл: [`bin/card_atoms.py`](https://github.com/mak777uh/herness/blob/a4bcae5368bcdb4f02e369e7d1e7c69ee1418d09/bin/card_atoms.py#L122)

```python
denied = {str((a.get("action") or {}).get("verb")) for a in atoms(card) if a.get("negated")}
for rule in mine:
    if rule.get("effect") == "allow" and rule.get("action") in denied:
        out.append("S4_POLICY_CONFLICT...")
```

Проверяются только `allow`-правила против отрицательных атомов. Положительное право карточки,
которое policy запрещает, не сравнивается. Поэтому карточка с синтезированным чтением проходит
`--check`, хотя policy содержит `netprobe-deny-fs` с `deny read file:/mnt/**`.

Воспроизведение на синтетической карточке (не на реальном `netprobe`; его карточки в репозитории
нет):

```json
{
  "id": "netprobe",
  "purpose": "проверить единственный мост",
  "inputs": {"host": "строка"},
  "outputs": {"ok": "флаг"},
  "closure": {
    "fs": {"read": [], "write": []},
    "net": ["10.0.2.2:8790"],
    "time_ms": 100,
    "memory_mb": 4,
    "output_bytes": 256
  },
  "refusals": ["S6_CLOSURE_BREACH"],
  "examples": [{"args": {"host": "10.0.2.2:8790"}, "expect": "ok"}]
}
```

```text
$ python bin/card_atoms.py --derive tmp_netprobe_card.json
... "verb": "read", "object": "file", "scope": "/mnt/**" ...

$ python bin/card_atoms.py --check tmp_netprobe_card.json
[ok] карточка netprobe не противоречит политике (правил у инструмента: 3)
$ echo $?
0
```

Это ложный зелёный: карточка объявила «не читаю», checker увидел «читаю», policy запрещает чтение,
но результат `ok`. Именно такой класс ошибок должен ловить двусторонний checker.

### 3.3. `read` и `search` проверяют путь, а затем открывают его по строке

Файл: [`core-rs/src/loopmod.rs`](https://github.com/mak777uh/herness/blob/a4bcae5368bcdb4f02e369e7d1e7c69ee1418d09/core-rs/src/loopmod.rs#L832)

```rust
let path = resolve_in(name, workspace)?;
let meta = std::fs::metadata(&path).map_err(...)?;
if meta.len() > MAX_FILE { ... }
let text = std::fs::read_to_string(&path).map_err(...)?;
```

`resolve_in` канонизирует путь и проверяет policy, но затем `read_to_string` снова открывает путь по
строке. Между проверкой и открытием путь может быть заменён (rename/symlink swap). Это окно TOCTOU
для чтения. `search` устроен так же: `resolve_in` на строке 643, `read_to_string` на строке 664.
Для записи уже используется `openat2` с `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS`; это хороший
прецедент, но чтение и поиск его не используют.

Это не воспроизведённый эксплойт. Это статически видимое окно, которое требует адверсариального
теста, прежде чем делать выводы.

### 3.4. `head` читает файл целиком

Карточка `head` обещает «вернуть первые N строк файла, не давая прочитать файл целиком». Фактический
`tool_read_in` сначала делает `read_to_string` всего файла, затем считает строки и обрезает вывод.
Если `purpose` — нормативное обещание, то поведение не входит в контракт; если это маркетинг, его
надо убрать или заменить проверяемым `max_bytes_read`. Сейчас это не проверяется.

### 3.5. Мелкие хвосты

- `bin/tool_examples.py` упомянут в лестнице, но в каноническом коммите отсутствует.
- `bin/tool_card.py --render` не печатает `closure.net` (строки 112–128).
- `netprobe` исторически провалил карточку до решения K3; после решения K3 он не перемерен.
- В рабочем дереве есть 27 предсуществующих CRLF-модификаций; их нельзя коммитить как «свои».

### 3.6. Что это не доказывает

- Не доказывает, что QEMU-комната небезопасна: это дефекты checker/чтения, а не побег из QEMU.
- Не доказывает, что `netprobe` реально утёк: карточки нет, синтетическая карточка лишь повторяет
  форму.
- Не доказывает TOCTOU-эксплуатацию: нужен тест с гонкой.
- Не отменяет K1–K11: наоборот, показывает, почему checker и runtime должны быть двусторонними.

#### D02. [P0] Какое формальное ядро принимаем: трассы или монотонное сужение?

**Контекст.** A предлагает семантику допустимых трасс с тремя множествами:

Forbid_parent ⊆ Forbid_child
Must_parent ⊆ Must_child

или убрать возможности. Обе идеи могут быть совместимы, но сейчас это два разных языка. Если
оставить оба, Lean, Rust и checker снова разойдутся.

**Вопрос.** Выберите одно ядро для v0 и покажите, как в нём выражаются K1–K11:

1. Домен семантики: трассы, состояния, pre/post, эффекты или гибрид. Что является «поведением».
2. Точное определение `<=` (refinement / trace inclusion / inclusion of authority sets). Что
   означает «дочерний слой не расширяет».
3. Как выражаются `Allow`, `Forbid`, `Must`; нужны ли все три в v0 или `Must` откладывается.
4. Как выражаются K1–K2 (пути), K3 (мост), K4 (ресурсы), K5 (отказ), K6 (секрет), K7
   (детерминизм), K8 (провенанс), K9 (композиция), K10 (самомодификация), K11 (допуск). Для
   каждого — форма или честное «вне модели v0».
5. Как это ядро связано с Lean-моделью `Cell`/`poolIncluded` и с Rust `policy_allows`: кто эталон,
   кто реализация, как проверяется расхождение.
6. Пример: `head` и `netprobe`, затем композиция `read → seal` или `search → write`. Покажите
   трассу/авторитет и место отказа.
7. Негативный контроль: попытка расширить путь, добавить разрешение, ослабить запрет, отозвать
   допуск. Какой тест обязан покраснеть.
8. Что ядро **не** моделирует (время, конкурентность, side channels, реальный Rust).

**Артефакт:** 1–2 страницы семантики, Lean-сигнатуры, псевдокод Rust-checker, 5 тестов.
**Не доказывать:** что модель соответствует Rust; это отдельное обязательство.

#### D04. [P0] Как владелец утверждает конституцию и поправки без PKI?

1. Что именно подписывается: конституция, amendment manifest, law set, effective date, diff,

10. Что можно честно утверждать, если подпись проверяется только вручную.

**Артефакт:** `amendment-manifest-v1`, verification pseudocode, state machine, 6 тестов.
**Не доказывать:** что подпись = намерение; hash ≠ intent.

10. Что должен уметь v0, чего не должен.

**Артефакт:** план с файлами, командами, acceptance criteria, 2-week/2-month. **P0.**

#### E02. [P1] Какой workflow для нескольких агентов и внешних ответов?

**Контекст.** Канон — GitHub `main`, агенты работают последовательно, есть второй локальный клон,
CRLF-шум, старые ветки. R5-ответы будут новым большим текстом; их надо сохранить так, чтобы
следующий агент не начинал с нуля.

**Вопрос.**

1. Direct push vs PR vs branch protection; что обязательно для docs, что для code.
2. Обязательный handoff: коммит, что сделано, что не сделано, следующий шаг, риски, где лежат
   ответы R5.
3. Protected paths и decision log: какие файлы нельзя менять агенту; кто approves.
4. CI и обязательные гейты; какие проверки блокируют merge.
5. CRLF и лишний diff-шум; как не коммитить чужие изменения; как чистить рабочее дерево.
6. Второй клон и stale branches: merge/archive/delete; что делать с `C:\111\herness`.
7. Как хранить внешние ответы: `docs/` или `research/`, один файл или несколько, как индексировать.
8. Разрешение конфликта двух агентов; кто главный; как откатывать.
9. Что должен оставить агент, если не успел; как не оставить «зелёный» без evidence.
10. Definition of done для docs и для code.

**Артефакт:** workflow + handoff template + protected paths. **P1.**

## 5. Что мы сделаем с ответами

1. Сведём ответы в decision log; конфликтующие ответы не усредняем, а выбираем с обоснованием.
2. Зафиксируем `tool-card-v1`, `LawRecord-v1`, `effect` vocabulary и `admission-manifest-v1`
   как черновики в репозитории.
3. Починим `card_atoms` и добавим двусторонний checker с регрессионным тестом на ложный зелёный.
4. Закроем read/search TOCTOU и `head`; добавим adversarial тесты.
5. Соберём минимальную QEMU-комнату и один вертикальный срез.
6. Только после этого — генератор и экономика.

Ни один ответ R5 не включает инструмент автоматически. Новые capabilities, сеть, секреты и
sandbox-изменения требуют owner approval. AI-ревьюер не заменяет человеческое approval.
