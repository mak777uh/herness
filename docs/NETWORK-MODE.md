# NETWORK-MODE — режим сети и бюджет трафика

Сейчас связь мобильная: медленная, с лимитом и нестабильная. Позже будет хороший Wi-Fi. Это
означает не «ждать Wi-Fi», а **два режима работы** с разными правилами.

## Режимы

| режим | когда | что разрешено |
|---|---|---|
| **mobile** | мобильный интернет, лимит, нестабильность | только необходимое: короткие вызовы модели, малые запросы, локальная работа |
| **full** | Wi-Fi, безлимит | всё: синхронизация справочника, веер вопросов, загрузки |

Переключение — сознательное действие, а не «как получится». Режим пишется в конфиг и виден в `hs facts`.

## Что меняется в mobile

| действие | mobile | full |
|---|---|---|
| вызов модели | только когда без него нельзя, короткий промпт, `max_tokens` мал | свободно |
| справочник `refs sync` | не запускать целиком; только конкретные источники | полный синк |
| веер вопросов по моделям | **отложить** | основной инструмент |
| загрузка файлов, картинок | отложить | можно |
| `git push` | мелкими пачками, после проверки | свободно |
| повторы при ошибке | 1, не 3 | 3 с backoff |

## Почему это не «просто подождать»

Три причины работать сейчас:

1. **Локальные замеры не требуют сети**: E-0002 (язык), тесты, контракты, журнал — всё офлайн.
2. **Элиминационный цикл** и синк справочника — это как раз то, что стоит накапливать и запустить
   пачкой на хорошем канале.
3. **Архитектура не должна зависеть от канала**: офлайн-режим уже заявлен (E7 в ADR-0007); мобильный
   интернет — его проверка в реальных условиях, а не гипотеза.

## Что учитывать в коде

- таймауты короче, повторов меньше — по режиму;
- ответы не тянуть целиком, если нужен только статус;
- каждый сетевой вызов журналируется с числом байт: цена канала должна быть видна, а не угадываться;
- тяжёлые загрузки — отдельной задачей с явным «сколько это стоит».

## Что это не даёт

Гарантии, что «потом будет Wi-Fi»: планировать надо так, чтобы работать и без него.
