# ADR-0007 — Политика выхода в сеть: один шлюз, allowlist, хранение ключей

Дата: 29.10.2026. Статус: принято владельцем. Дополняет ADR-0004.

## Контекст

Узлы работают в сетях с разной доступностью: часть соединений может не устанавливаться, скорость
и потери меняются, внешний адрес узла не всегда постоянен. Одновременно ключи внешних сервисов не
должны находиться на клиентских машинах.

Решение: сервер выполняет роль **шлюза выхода** — единственной точки, через которую узлы
обращаются к внешним сервисам.

```
клиентский узел ──► шлюз ──► маршрут (direct / прокси / релей) ──► внешний сервис
                     │
                     ├─ allowlist доменов и портов
                     ├─ хранение ключей (клиент их не видит)
                     └─ журнал: хост, статус, байты, длительность
```

## Два режима

| режим | для чего | ограничение |
|---|---|---|
| **инструмент** `http_fetch` | вызовы моделей, API, чтение страниц | политика проверяет домен, метод, размер ответа; тело возвращается с дайджестом |
| **туннель** (CONNECT) | пакетные менеджеры и сборщики (`cargo`, `npm`, `pip`, `forge`) | allowlist по хосту и порту; без записи в allowlist — отказ |

Туннель нужен потому, что перечисленные инструменты не работают через вызов функции. Это более
широкий канал, поэтому список доменов для него уже́.

## Инварианты

| id | инвариант | зачем |
|---|---|---|
| E1 | по умолчанию запрещено; разрешения выдаются роли и прогону явно | отсутствие правила не означает разрешение |
| E2 | ключи хранятся только на шлюзе; клиент видит имя и отпечаток | компрометация клиента не даёт доступа к сервисам |
| E3 | каждый выход журналируется: хост, порт, статус, байты, длительность; тела — с дайджестом | утверждение «запрос не уходил» проверяемо |
| E4 | маршрут не меняется молча: смена пути — событие в журнале, а не невидимая подмена | иначе несравнимы результаты прогонов |
| E5 | повторы только для идемпотентных запросов | двойная отправка = двойное действие |
| E6 | аварийный выключатель: одна команда останавливает весь выход | реакция быстрее расследования |
| E7 | офлайн-режим: без сети работа продолжается, результаты досылаются позже | связь может отсутствовать в середине задачи |

## Маршруты

Поддерживаются несколько путей: `direct`, `upstream-proxy`, `relay-via-second-host`.

- маршрут выбирается на старте прогона и фиксируется в записи;
- недоступность маршрута — ошибка с кодом, а не тихий переход на другой;
- переключение — отдельное решение с записью в журнал.

## Следствия

1. Клиент может вообще не иметь доступа к внешним сервисам — ключи и сетевой доступ разделены.
2. Сборки получают параметры прокси от харнесса, а не из ручной настройки машины.
3. Поверхность риска смещается на шлюз: короткоживущие токены, отдельные ключи под сервисы, ротация.
4. Появляется измеримая величина: задержка и потери по маршрутам.

## Границы

- Allowlist не предотвращает выгрузку данных **через разрешённый домен**; для этого нужен отдельный
  детектор, а не список доменов.
- Шлюз не гарантирует доступность внешнего сервиса и не ускоряет его.
- Схема не делает трафик невидимым и не заявляет анонимности: узел виден сервису так же, как при
  любом проксировании.

## Что это не доказывает

Что маршрут через шлюз быстрее локального. Что один шлюз выдержит одновременные вызовы моделей и
сборки. Что allowlist покрывает все нужные домены.
