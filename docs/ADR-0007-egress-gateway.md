# ADR-0007 — Сервер как безопасный канал в сеть

Дата: 29.10.2026. Статус: принято владельцем. Дополняет ADR-0004 и ADR-0006.

## Контекст

Владелец работает из среды, где доступ к внешним сервисам нестабилен или заблокирован. Текущая
схема — локальная цепочка `приложение → 127.0.0.1:2080 (релей) → 127.0.0.1:12334 → интернет` —
известна своей хрупкостью: конфликт за порт, падение релея, зависимость от одного процесса на
рабочей машине.

Одновременно сервер (A15) уже нужен как дублёр для непрерывности. Логично, чтобы он же был
**единственной точкой выхода в сеть**.

## Решение

Сервер становится **шлюзом выхода** с явной политикой. Локальный агент не открывает произвольных
соединений: он просит сервер, а решение «можно/нельзя» принимает политика.

```
локальный агент ──► сервер ──► маршрут (direct / прокси / релей) ──► интернет
                        │
                        ├─ allowlist доменов и портов
                        ├─ хранение ключей (клиент их не видит)
                        └─ журнал: хост, статус, байты, длительность
```

## Два режима, и их нельзя путать

| режим | для чего | как ограничивается |
|---|---|---|
| **Инструмент** `http_fetch` | вызовы моделей, веб, API | политика проверяет домен, метод, размер ответа; тело возвращается с дайджестом |
| **Туннель** (CONNECT-прокси) | пакетные менеджеры, сборщики (`cargo`, `npm`, `pip`, `forge`) | allowlist по хосту и порту; без allowlist — отказ |

Туннель нужен потому, что `cargo` и `npm` не умеют «сходить через инструмент». Но туннель —
более широкая дверь, поэтому для него отдельный, более узкий список доменов.

## Инварианты

| id | инвариант | зачем |
|---|---|---|
| E1 | По умолчанию запрещено; разрешения выдаются роли и прогону явно | «забыли закрыть» не должно означать «открыто» |
| E2 | Ключи живут только на сервере; клиент видит имя ключа и отпечаток | утечка клиента не даёт доступа к моделям |
| E3 | Каждый выход журналируется: хост, порт, статус, байты, длительность; тела — с дайджестом | «мы не ходили туда» проверяемо, а не на слово |
| E4 | Молчаливого изменения доверия нет: падение маршрута не означает «пойти напрямую» без записи в журнал | иначе обход блокировки тихо ломает модель угроз |
| E5 | Повторы только для идемпотентных запросов; неидемпотентные — по явному подтверждению | двойная отправка = двойное действие |
| E6 | Аварийный выключатель: одна команда останавливает весь выход | утечка должна останавливаться быстрее, чем расследуется |
| E7 | Офлайн-режим существует: без сети харнесс работает, а не падает | связь может пропасть в середине работы |

## Маршрутизация и отказоустойчивость

Несколько путей с проверкой здоровья: `direct`, `upstream-proxy`, `relay-via-second-host`.

- маршрут выбирается на старте прогона и **не меняется на ходу** — иначе результаты
  несравнимы между прогонами;
- падение маршрута = ошибка с кодом, а не тихое переключение;
- переключение — отдельное решение с записью в журнал.

## Что это меняет

1. **Вызовы моделей идут через сервер.** Локальный агент может вообще не иметь доступа к
   провайдерам — и это плюс: ключи не покидают сервер.
2. **Сборки требуют настройки прокси.** `cargo`, `npm`, `pip` получают переменные окружения от
   харнесса, а не из ручной настройки машины.
3. **Модель угроз смещается на сервер.** Компромисс сервера = компромисс ключей и трафика.
   Отсюда: короткоживущие токены, отдельные ключи под сервисы, ротация.
4. **Появляется измеряемая величина — стоимость канала:** задержка и потери по маршрутам.

## Чего это не даёт

- Allowlist не мешает утечке **через разрешённый домен** (gist, pastebin, чужой репозиторий).
  Против этого нужен отдельный детектор утечек, а не список доменов.
- Не гарантирует, что маршрут не заблокируют завтра.
- Не делает трафик невидимым: это вопрос оператора, а не архитектуры.

## Что это не доказывает

Что маршрут через сервер быстрее локальной цепочки — не мерили. Что один сервер выдержит
одновременные вызовы моделей и сборки — не мерили.
