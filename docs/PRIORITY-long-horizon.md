# Приоритет: длинные задачи (часы и сутки)

**Дата:** 01.11.2026. **Источник:** прямое указание владельца. **Статус:** приоритет, влияет на
выбор следующих работ.

## Что это значит

Харнесс должен удерживать работу **часами и сутками** без потери смысла, доказательств и денег.
Сейчас все наши прогоны — минуты, поэтому этот приоритет **не проверен ни одним измерением**. Ниже
честно: что уже есть, что для этого не хватает, чем будем мерить.

## Что уже работает в эту сторону

| механизм | что даёт для долгой работы | чем ограничен |
|---|---|---|
| журнал с sync после каждого шага (ADR-0051) | после обрыва работа продолжается с места, а не с нуля | продолжение проверено на обрыве в середине короткой задачи |
| коммиты как границы состояния | видно, что именно считается завершённым | коммит один на прогон |
| бюджеты шагов и денег на прогон | работа не уходит в бесконечность | **бюджет задаётся на прогон, а не на сутки** |
| один и тот же вердикт при повторе (C-0197) | на коротких задачах результат устойчив | на MuSiQue вердикт уже нестабилен (C-0204) |

## Чего не хватает (по существу, а не «улучшить»)

1. **Бюджет времени как измеряемая величина.** Сейчас есть `max_steps` и `max_allowance` на прогон.
   Для суток нужен **общий бюджет на кампанию**: сколько шагов, сколько денег, сколько часов — и
   что делать, когда он кончился (остановиться и сказать, а не тихо оборваться).
2. **Восстановление после многих обрывов.** Проверен один обрыв. Для суток нужен прогон, где
   обрывов пять-десять подряд, и после каждого работа продолжается, а не начинается заново.
3. **Дрейф контекста.** Промпт собирается из задачи, ≤12 строк истории и последнего результата.
   На сотнях шагов модель теряет, что уже сделано. Нужен слой «что уже установлено» (факты с
   якорями), а не только последний результат.
4. **Периодическая проверка промежуточных утверждений.** На длинной работе нужно, чтобы опора
   проверялась не один раз в конце, а на каждом этапе — иначе через сутки выяснится, что первые
   десять шагов ни на чём не стояли.
5. **Стоимость.** Длинная работа = много вызовов. Нужна метрика «цена за принятую задачу» с учётом
   неудачных прогонов, иначе «эффективно» останется словом.

## Чем мерить (что должно появиться)

| метрика | как считается | зачем |
|---|---|---|
| выживание после N обрывов | прогон с N инъекциями обрыва, доля продолженных корректно | заменяет «проверено один раз» |
| потеря работы при обрыве | сколько шагов повторено после восстановления | цена восстановления |
| дрейф «что установлено» | доля утверждений, известных на шаге K, которые модель помнит на шаге K+50 | ловит забывание |
| цена за принятую задачу | расход / число принятых задач, с неудачами в знаменателе | делает «эффективно» числом |
| доля ложных «готово» на длинной задаче | ложные принятия / все принятия | главный риск длинной работы |

## Ближайшие три шага, которые я вижу

1. **Инъекция обрывов N раз** в одну длинную задачу (сейчас `crash-resume.ps1` умеет один обрыв) —
   расширить до N и записать числа.
2. **Бюджет кампании** в критерии: `max_total_allowance`, `max_total_steps`, `max_wall_clock` — с
   остановкой и явным статусом `budget-campaign`, а не молчаливым обрывом.
3. **Слой «установлено»**: список проверенных утверждений с якорями, который попадает в промпт
   вместо части истории.

## Граница

Пока ни одна из этих метрик не измерена, «работает часами» — это **замысел, а не факт**. Первое,
что должно появиться, — число выживания после повторных обрывов; без него всё остальное про
долгую работу будет рассуждением.
