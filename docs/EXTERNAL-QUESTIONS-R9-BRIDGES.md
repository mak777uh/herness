## 0. От владельца — задача этого раунда

> Сейчас ИИ — новая технология, и все подходы меняются. Смотреть из первых принципов и пытаться понять, как это могло бы выглядеть оптимально.

Расшифровка для отвечающего:

- **Не тащите привычные паттерны как данность.** Механизмы appsec 2010-х (ACL, code review, подписи, «песочница = chroot», «доверенный администратор»), привычки Unix и корпоративные практики выводились для среды «много пользователей, код пишет человек». Здесь среда другая: **один владелец, код и инструменты пишет ИИ-модель, внешние сервисы недоверены по определению**. Если классический механизм в этой среде устарел — скажите прямо и предложите замену, не ссылаясь на «так принято».
- **Выводите из модели угроз и свойств среды**, а не из аналогий. Хороший ответ называет: кто противник, какие у него возможности, какое свойство системы делает его неэффективным и сколько это стоит.
- **Оптимально — значит с ценой.** Ответ без цены (время, сложность, TCB, доля провалов) не считается ответом.

## 1. Проект в одном экране

[`herness`](https://github.com/mak777uh/herness) — харнесс, который должен **безопасно генерировать собственные инструменты** и работать в среде, где код пишет ИИ-модель. Состав:

- **первая комната** (room zero) — защищённый корень доверия: конституция K1–K11, ключи, политика, реестр, допуск;
- **инструменты** — сначала native, затем сгенерированные; у каждого карточка (декларация эффектов), но карточка не является доказательством поведения;
- **admission** — подписанное владельцем согласование, привязанное к точным байтам card/source/binary/policy/room;
- **комната** — QEMU/KVM-гость без сети и лишних устройств, с наблюдением за поведением;
- **мосты** — единственный способ выйти наружу; downstream-мост может иметь свои правила, если цепочка доказанно не нарушает конституцию.

Состояние на 23.11.2026: 33 гейта (профиль auto) — 33/33 зелёные; CLAIMS.md ~325 утверждений, anchored 1.00, strict 0.56; CI — 6 job'ов, зелёный; изоляция внешнего помощника `/v1/net` закрыта с трёх сторон (PID-namespace на Linux, low-IL на Windows, Landlock-барьер записи); K9 — модель композиции проверена в Lean (`K9_model_checked`, не `K9_proven`). Точка входа в историю смен — [`docs/WHERE-I-STOPPED.md`](https://github.com/mak777uh/herness/blob/main/docs/WHERE-I-STOPPED.md).

**Что считается успехом v0:** один сгенерированный read-only инструмент проходит card → policy → room → observation → owner admission, и отчёт честно отделяет свидетельство от доказательства. **Что не является успехом:** «модель написала код, он запустился».

## 2. Словарь

| термин | смысл |
|---|---|
| **мост (bridge)** | канал между комнатой и внешним миром; единственный способ «выйти наружу»; downstream-мост может иметь свои правила |
| **adjacent bridge** | мост, соприкасающийся с первой комнатой или пространством владельца; обязан соблюдать K1–K11 |
| **внешнее** | недоверенный помощник за мостом (например, сетевой провайдер); его ответ маркируется |
| **замыкание (closure)** | объявленный набор каналов шага: какие файлы читает/пишет, куда ходит сетью, какие секреты трогает |
| **taint** | метка заражения; в модели K9 пока только два класса: `secret` и `net` |
| **admission** | подписанное владельцем согласование входа чужого кода, привязанное к хешам байтов |
| **гейт** | автоматическая проверка репозитория; гейт не ослабляется, смена порога — отдельный ADR |
| **пре-регистрация** | порог критерия запечатывается до прогона; отрицательный результат остаётся результатом |
| **NC** | not-claimed: явная запись «что это утверждение НЕ доказывает» |
| **K9_model_checked / K9_proven** | модель проверена в Lean / доказано соответствие кода модели |

## 3. Конституция: рамка, которую нельзя молча менять

Полный текст: [`docs/CONSTITUTION-v0-2026-11-16.md`](https://github.com/mak777uh/herness/blob/ce7c64d/docs/CONSTITUTION-v0-2026-11-16.md). Ключевая идея: описывать инструмент надо не разрешениями, а **законами, которым он обязан подчиняться**; владелец утверждает законы, а не каждый инструмент.

Три слоя, которые нельзя смешивать: **потолок возможностей** (что физически доступно: fs/net/time/mem — задаёт комната/ядро), **конституция** (что запрещено при любом поведении — владелец, поправкой), **карточка инструмента** (что делает инструмент — модель/агент). Свобода — только в третьем слое.

| id | закон | смысл в одном предложении | статус |
|---|---|---|---|
| K1 | `no_read_outside_root` | читать только внутри объявленного корня | частично |
| K2 | `no_write_outside_root` | писать только внутри объявленного корня | частично |
| K3 | `no_net_except_declared` | сеть — только через объявленный мост; двойной allowlist: инструмент объявляет мост, мост — адреса; adjacent-мост обязан соблюдать K1–K11; downstream — через K9 | политика решена, реализация частично |
| K4 | `bounded_resources` | время, память, выдача ограничены | частично |
| K5 | `explicit_refusal` | отказ явный, с кодом из словаря; молчание — нарушение | частично |
| K6 | `no_secret_outside_protected_space` | секрет не пересекает границу защищённого пространства; v0 fail-closed | **не обеспечен** |
| K7 | `deterministic_output` | те же входы → тот же вывод | **не проверяется** |
| K8 | `provenance` | у active-инструмента есть карточка, хеш и пакет свидетельств | частично |
| K9 | `composition_preserves` | композиция инструментов и мостов сохраняет K1–K11 на границе первой комнаты; без доказательства — отказ | **не обеспечен** (модель есть, см. §4) |
| K10 | `no_self_modification` | инструмент/генератор не меняет конституцию, лестницу, реестр, policy, bridge registry | частично |
| K11 | `admission_to_protected_space` | чужое приложение/инструмент/мост входит в защищённое пространство только по явному согласованию, привязанному к хешам | **не обеспечен** (код admission есть, owner-подписи нет) |

Юрисдикция: конституция действует на **первую комнату и границу входа в пространство владельца** (например, ноутбук). Мосты дальше могут иметь свои правила, но обязаны не приводить к нарушению конституции на защищённой границе (K9). Сеть хоста и обычная работа владельца этим законом не блокируются — ограничивается сеть **комнаты и её мостов**.

Решения владельца Q1–Q10: [`docs/DECISIONS-R5-2026-11-16.md`](https://github.com/mak777uh/herness/blob/ce7c64d/docs/DECISIONS-R5-2026-11-16.md). R8-развилки Q11–Q18/F04/A01 ещё у владельца: [`docs/R8-SYNTHESIS.md`](https://github.com/mak777uh/herness/blob/main/docs/R8-SYNTHESIS.md).

## 5. Вопросы

### A. Онтология моста

#### A1. Что такое мост из первых принципов?

**Дано.** В репо мост одновременно: HTTP-прокси с allowlist ([`bin/bridge.py`](https://github.com/mak777uh/herness/blob/ce7c64d/bin/bridge.py)), Lean-теорема об адресе/токене/ответе ([`proofs/Proofs/Bridge.lean`](https://github.com/mak777uh/herness/blob/ce7c64d/proofs/Proofs/Bridge.lean)), обязательство с контрактом и законами ([PROPOSAL-0001](https://github.com/mak777uh/herness/blob/ce7c64d/docs/PROPOSAL-0001-task-written-bridges.md)) и строка в чекере цепочек ([`bin/chain.py`](https://github.com/mak777uh/herness/blob/ce7c64d/bin/chain.py)).
**Развилка.** (а) мост = канал с политикой; (б) мост = обязательство (контракт), а код — одна из реализаций; (в) мост = тип данных в формальной модели; (г) мост = протокол взаимодействия, а не сущность.
**Что нужно.** Одно определение из первых принципов (кто участник, кто противник, какое свойство определяет мост), которое объясняет, почему эти четыре представления — одно и то же, и какое из них первично.

#### A2. Правильная ли это аксиома — «мосты единственный способ выйти наружу»?

**Дано.** K3 запрещает прямой сетевой выход из комнаты; сеть — только через объявленный мост ([конституция, K3](https://github.com/mak777uh/herness/blob/ce7c64d/docs/CONSTITUTION-v0-2026-11-16.md)).
**Развилка.** (а) да, единственный канал — правильная аксиома (триангуляция не нужна); (б) нет, нужен второй независимый канал (аудит/наблюдение) или канал «отказов»; (в) мосты должны быть не «выходом», а «входом»: внешнее инициирует, комната отвечает.
**Что нужно.** Ответ из модели угроз: какие атаки устраняет единственность выхода и какие — нет.

#### A3. Должен ли мост быть кодом вообще?

**Дано.** PROPOSAL-0001 предлагает синтезировать мосты (Lean-модель + доказательство + Rust + негативный контроль) под повторяющиеся задачи; владелец 23.11.2026 спросил: не нужен ли для мостов «свой язык», поскольку именно мосты принципиальны и про безопасность.
**Развилка.** (а) мост — всегда сгенерированный код с доказательством; (б) мост — данные (декларативная таблица разрешений) + один крошечный неизменяемый интерпретатор; (в) мост — конфигурация существующих generic-прокси (но тогда generic-прокси — большой TCB).
**Что нужно.** Рекомендация с ценой каждого варианта в среде «ИИ генерирует, владелец не читает код».

#### A4. Минимальный мост v1 — какой?

**Дано.** Первый срез proposal: «прочитать файл → отфильтровать → посчитать» с тремя законами.
**Что нужно.** Из первых принципов: минимальный мост, полезность которого можно измерить за один день, и минимальный набор законов, без которого он не мост. Предложить альтернативный первый срез, если этот неудачен.

### B. Язык обязательств (сердце раунда)

#### B1. Нужен ли мостам свой язык — и в каком смысле «свой»?

**Дано.** Одно и то же обязательство моста существует в трёх рукописных представлениях: Lean-модель ([`Composition.lean`](https://github.com/mak777uh/herness/blob/ce7c64d/proofs/Proofs/Composition.lean)), policy-чекер с JSON-фикстурами ([`bin/chain.py`](https://github.com/mak777uh/herness/blob/ce7c64d/bin/chain.py), [`lab/fixtures/chain/`](https://github.com/mak777uh/herness/tree/ce7c64d/lab/fixtures/chain)) и Rust-исполнение с расхождением 15/18 ([`bin/policy_diff.py`](https://github.com/mak777uh/herness/blob/ce7c64d/bin/policy_diff.py)). Ручная синхронизация трёх представлений уже давала дефекты класса «прибор врёт» (F-0087: формат журнала уехал между исходником и бинарником; CRLF-писатели; сводка тестов печатала «провалов: 0» при красном тесте).
**Развилка.** (а) декларативный формат данных (JSON/JSON-Schema) — один источник, три потребителя; (б) маленький DSL с собственным синтаксисом и парсером; (в) встроить обязательства в общий язык (типы Lean/Rust/WIT-интерфейсы), без отдельного формата; (г) никакой язык — тесты и негативные контроли как единственный источник истины.
**Что нужно.** Выбор из первых принципов с критерием: минимальный TCB, механически проверяемое соответствие, стоимость для одного человека. Явно ответить: где проходит граница между «языком» и «форматом данных» и почему она здесь важна.

#### B2. Как обеспечить, что три потребителя обязательства не разъезжаются?

**Дано.** Три потребителя: Lean-доказательство (семантика), Python-чекер (политика), Rust-мост (исполнение). Расхождение уже наблюдаемо: 15/18 в policy_diff; пять deny-правил policy.json отсутствуют в Rust ([`docs/R8-SYNTHESIS.md`](https://github.com/mak777uh/herness/blob/main/docs/R8-SYNTHESIS.md)).
**Развилка.** (а) генерация: Lean-определения и Rust-код порождаются из одного IR; (б) extraction: Rust извлекается из Lean; (в) конформность: независимые реализации + обязательная дифференциальная сверка на входах и мутантах (текущий путь); (г) один интерпретатор, остальные — проверки.
**Что нужно.** Какое сочетание даёт максимум гарантии на минимум усилий для одного человека; что должно быть гейтом.

#### B3. Какие свойства закона делают его механически компонуемым?

**Дано.** PROPOSAL-0001: «композиция взрывает обязательства — начинать надо с языка законов, который компонируется механически (разрешения, происхождение адреса, отсутствие сети), а не с произвольных предикатов». В K9-модели `comp` складывает замыкания, и T1 доказывает сохранность границы — но только для вырожденной семантики «список каналов».
**Развилка.** (а) законы должны быть монотонными предикатами над каналами (объединение сохраняет); (б) законы должны быть ресурсными наборами (capability sets), композиция = пересечение; (в) законы должны быть «эффектами» с тейнт-алгеброй (объединение taint); (г) композицию нельзя спасать выбором законов — нужен отдельный закон композиции.
**Что нужно.** Формальный критерий «закон композициируем» и минимальный набор законов первого среза, который им удовлетворяет.

#### B4. Как выглядят обязательные негативные контроли для языка обязательств?

**Дано.** Дисциплина репо: доказательство без падающего негативного контроля может быть пустым (F-0080 — ловился случай `sorry`/лишняя аксиома); мутационное тестирование уже применяется (PILOT-GENERATOR: 16/16 + 8/8 мутантов).
**Что нужно.** Список мутантов контракта/закона, которые **обязаны** быть отвергнуты всеми потребителями (чекер, Lean-контрпример, Rust-исполнение): лишний канал, недоказанный downstream, ускользнувший taint, подмена адреса моста, wildcard там, где нужен литерал. Что добавить к этому списку из первых принципов, чтобы мутанты ловили «язык, который нельзя нарушить только потому, что в нём нельзя ничего выразить»?

#### B5. Не превращается ли язык обязательств в новый доверенный код?

**Дано.** Проект целенаправленно сжимает TCB: room — Rust PID1 без shell; парсер формата журнала сверяется с бинарником; пре-регистрации запечатывают пороги.
**Что нужно.** Из первых принципов: какова максимальная сложность семантики языка, при которой его интерпретатор сам доказуем в Lean на одну страницу / проверяем одним property-тестом? Дайте оценку в строках/правилах и критерий «язык перерос себя».

### C. Доверие и допуск

#### C1. Что такое «согласование владельца», когда владелец не читает код?

**Дано.** K11: чужой код входит в защищённое пространство по явному согласованию, привязанному к хешам байтов card/source/binary/policy/room ([конституция](https://github.com/mak777uh/herness/blob/ce7c64d/docs/CONSTITUTION-v0-2026-11-16.md)); admission-код есть, owner-подписи нет ([`docs/OWNER-RUNBOOK-2026-11-17.md`](https://github.com/mak777uh/herness/blob/main/docs/OWNER-RUNBOOK-2026-11-17.md)).
**Развилка.** (а) согласование = подпись байтов (текущий дизайн); (б) согласование = утверждение **семантики** (цель, границы, законы), а байты привязываются reproducible-сборкой; (в) согласование = утверждение доказательства и негативных контролей, а не кода; (г) согласование не нужно для сгенерированных мостов, если гейты зелёные — достаточно журнала.
**Что нужно.** Первопринципный ответ: что именно владелец утверждает своим ключом и какое свойство это даёт, которого нет без подписи.

#### C2. Реестр мостов как актив: правильная ли это экономика?

**Дано.** `id = hash(contract, laws, code, toolchain)`; переиспользование требует перепроверки; смена toolchain ломает id, а не репутацию; при повторяемости задач < ~30 % реестр не окупится ([PROPOSAL-0001](https://github.com/mak777uh/herness/blob/ce7c64d/docs/PROPOSAL-0001-task-written-bridges.md)).
**Развилка.** (а) реестр проверенных мостов — главный актив харнесса; (б) мосты одноразовы: дешевле сгенерировать и проверить заново, чем хранить; (в) реестр нужен только для **законов/контрактов**, код всегда регенерируется.
**Что нужно.** Рекомендация с критерием измерения (что и когда мерить, чтобы выбрать между «а» и «б» не по вкусу).

#### C3. Кто отвечает за мост, если его сгенерировала модель?

**Дано.** Харнесс самотулится: модель пишет инструменты и мосты под задачи; K10 запрещает инструменту менять политику/реестр/конституцию.
**Что нужно.** Из первых принципов: распределение ответственности (модель-генератор / харнесс-проверщик / владелец-подписант) и минимальный набор артефактов, по которым после инцидента можно ответить «кто и что одобрил» (provenance-цепочка).

#### C4. Должен ли сам мост быть недоверенным?

**Дано.** Сейчас bridge.py выполняется на хосте с токеном провайдера; внешнему помощнику (`net.py`) достаётся allowlist-окружение, namespace и Landlock, а мост сам — нет.
**Развилка.** (а) мост — часть TCB, исполняется с привилегиями, но его байты запечатаны admission; (б) мост тоже исполняется в изоляции (мост внутри микро-VM с единственным outbound); (в) мост делится: policy-половина (TCB) + relay-половина (недоверенная, изолированная).
**Что нужно.** Вариант с ценой и моделью угроз: какие атаки на мост закрывает каждый вариант.

### D. Изоляция и недоверенный код

#### D1. Минимальная достаточная изоляция внешнего помощника?

**Дано.** Реализовано: PID-namespace `unshare -U -p -f --mount-proc` на Linux; restricted-токен Low IL + job kill-on-close на Windows; Landlock-барьер записи (ABI ≥ 3) с единственным разрешённым путём; allowlist окружения; fail-closed при отсутствии механизма. Не покрыто (NC-017/018): token-файл в argv, same-uid `/proc`-доступ на Linux, симлинки/жёсткие ссылки/гонки, чтение и сеть не ограничены, прямые запуски вне моста.
**Развилка.** (а) расширять текущие kernel-механизмы (seccomp, pivot_root, uid-изоляция); (б) поднять уровень: внешнее — всегда в микро-VM; (в) перейти на WASM/песочницу языка исполнения; (г) достаточно текущего уровня для угрозы «внешний помощник пытается прочитать/записать».
**Что нужно.** Ранжирование механизмов по свойству, которое даёт каждый, и минимальная комбинация, закрывающая NC-017/018-классы.

#### D2. Какие классы обхода декларативных замыканий принципиальны?

**Дано.** Замыкание шага — объявление каналов (читает/пишет/сеть/секреты). Известно из NC-018: Landlock ставится после старта интерпретатора; 9p/дескрипторы позволяют писать через заранее открытые fd; симлинки и гонки не покрыты.
**Что нужно.** Полный из первых принципов список классов расхождения «декларация ≠ поведение» (TOCTOU, дескрипторы, косвенные пути, shared-память, side-каналы, уговоры человека) и для каждого: закрывается ли замыканием, изоляцией, доказательством кода — или ничем из этого, и что тогда.

#### D3. Каким должен быть минимальный словарь taint, чтобы граница стала осмысленной?

**Дано.** В K9-модели taint имеет два класса: `secret` и `net`; всё остальное (произвольные секреты, скрытые каналы, соответствие Rust-кода) не покрыто ([`NOT-CLAIMED.md` NC-019](https://github.com/mak777uh/herness/blob/ce7c64d/NOT-CLAIMED.md)).
**Развилка.** (а) расширять алгебру taint (уровни/домены: secret, personal, public, derived); (б) не расширять алгебру, а добавить «уход» в модель (окончательная точка выхода); (в) заменить taint на capability-flow; (г) оставить два класса до появления первого инцидента.
**Что нужно.** Минимальный словарь, при котором T2-класс атаки (композиция безобидных шагов) ловится, и цена выражения этого словаря в Lean и в чекере.

#### D4. Недоверенный текст — это taint или политика?

**Дано.** Ответ внешнего провайдера маркируется `[external_untrusted]` текстом на успехе и на отказе; в NOT-CLAIMED прямо записано: метка текстовая, не политика исполнения; модель может её проигнорировать; prompt-injection через ответ провайдера не покрыт.
**Развилка.** (а) маркировка — достаточный v0, дальше — дисциплина модели; (б) taint должен быть машинным: ответ внешнего не может стать аргументом write/exec-инструмента без явного закона; (в) нужен отдельный закон K12 про недоверенный контент.
**Что нужно.** Первопринципный ответ: как в системе, где потребитель — LLM-агент, сделать «недоверенный текст не управляет инструментами» **обеспечиваемым**, а не дисциплинарным.

### E. Композиция и информационные потоки

#### E1. Какая формальная база для композиции безопасности посила для одного человека?

**Дано.** T2: пошаговой проверки недостаточно; T5/T6: downstream без доказательства делает цепочку недопустимой. Всё — на вырожденной модели «список каналов».
**Развилка.** (а) noninterference/unwinding; (б) композиционный IFC (например, семантика «declassification-free chains»); (в) capability-based reasoning (мониторинг пересечения наборов); (г) никакая теория — мутационные контроли и дифф-тесты как замена.
**Что нужно.** Одна теория, которую один человек может удержать и отразить в Lean за недели, и что она даёт сверх текущего `comp` на списках каналов.

#### E2. Что минимально должно совпасть, чтобы выдать `K9_proven`?

**Дано.** Сейчас `K9_model_checked`: соответствие Rust-кода Lean-модели не покрыто; policy_diff 15/18; chain.py policy-only.
**Развилка.** (а) достаточно «мутационного согласия трёх» (мутант отвергается чекером, даёт контрпример в Lean и отказ в Rust); (б) нужно извлечение модели из кода (extraction/верификация Rust — Kani/RustBelt-класс); (в) нужно свойство «мост порождён из обязательства» (B2-генерация), тогда соответствие структурное.
**Что нужно.** Критерий выдачи `K9_proven`, который не является ни теоретическим идеалом, ни подменой, — и стоимость его достижения по шагам.

#### E3. Как доказывать цепочку длины N?

**Дано.** К9-модель даёт пару-композицию `comp a b` и теоремы T1/T2/T5/T6; чекер требует `proven` у каждого downstream.
**Развилка.** (а) индукция по цепочке (нужен закон «продолжение доказанного сохраняет»); (б) цепочка сводится к пересечению ресурсных наборов; (в) цепочки глубже 2 запрещены v0.
**Что нужно.** Механизм, который масштабируется на N без взрыва обязательств (PROPOSAL-0001: «два моста — три теоремы, пять — уже трудно»).

#### E4. Далеко ли можно продвинуть модель, не упираясь в верификацию Rust?

**Дано.** Граница модели честно объявлена: «проверяются объявленные замыкания, а не поведение кода».
**Развилка.** (а) оставаться на уровне объявлений навсегда — это правильно по цене; (б) поднимать строгость: property-тесты → дифф на живом мосте → извлечение → верификация ядра; (в) верифицировать только policy-ядро моста (не весь код).
**Что нужно.** Где проходит граница «доказывать дальше не стоит», и по какому первопринципному признаку её увидеть (какой класс атак ещё не закрыт на текущей границе и сколько стоит его закрыть).

### F. Экономика доказательств

#### F1. Сколько доказательств достаточно для персонального харнесса?

**Дано.** Конституция делит проверку на уровни: A — доказуемо политикой/моделью, B — доказуемо для кода, C — только измеримо. K9/K11 — не обеспечены; CI гоняет гейты и Rust-тесты, но не Lean и не QEMU.
**Что нужно.** Распределение усилий из первых принципов: для каких законов уровень A окупается, для каких достаточно C, и какие два закона оправдывают уровень B в первую очередь.

#### F2. Мосты одноразовые или накопительные?

**Дано.** C2-развилка выше; повторяемость задач не измерена.
**Что нужно.** Один эксперимент (пре-регистрируемый), который решает «а» или «б» данными, а не мнением, и его порог.

#### F3. Что в этом дизайне — дань традиции, а не первопринципы?

**Дано.** Весь текущий дизайн: Unix-изоляция, allowlist-адреса, HTTP-мост, подписи байтов, Lean-доказательства, JSON-реестры.
**Что нужно.** Список: что выкинули бы, проектируя сегодня с нуля для одного владельца и ИИ-агентов; что оставить; чем заменить выкинутое. Ответ обязан назвать цену каждого выкидывания.

### G. AI-native

#### G1. Что меняет в роли моста дешевизна генерации кода?

**Дано.** Модель пишет код за секунды; перегенерация почти бесплатна; проверка и доверие — дорогие.
**Что нужно.** Из первых принципов: если код — расходный материал, что является активом (законы? доказательства? данные о поведении? репутация канала)? Как должна выглядеть архитектура «код дёшев, доверие дорого» — и чем она отличается от текущего «генерируем код, доказываем, регистрируем»?

#### G2. Что должно быть в протоколе моста для ИИ-потребителя?

**Дано.** Потребитель моста — LLM-агент в комнате; отказы уже кодифицированы (словарь v2, 23 кода; K5 — явный отказ); ответ внешнего маркируется `[external_untrusted]`.
**Развилка.** (а) достаточно машиночитаемых отказов и маркировки; (б) нужен self-describing контракт (мост отдаёт свои законы при подключении); (в) нужен канал «объяснений» (почему отказано — чтобы модель могла скорректировать план без нарушения).
**Что нужно.** Минимальное расширение протокола, которое снижает число повторных нарушений моделью, не ослабляя ни одного закона.

#### G3. Условия, при которых «модель пишет мост + доказательство» безопаснее человека?

**Дано.** R8-развилки про генератор не закрыты; PROPOSAL-0001 предполагает синтез моделью.
**Что нужно.** Первопринципный ответ: при каких инвариантах системы генерация ИИ строго лучше ручного написания (и почему), и какие инварианты обязательны, чтобы это было так.

#### G4. Минимальный механизм доверия «с нуля, сегодня»?

**Дано.** Весь контекст этого документа.
**Что нужно.** Спроектируйте минимальный механизм доверия для «один владелец + N AI-агентов + M внешних сервисов» из первых принципов (не более ~10 элементов), сравните с herness поэлементно: что у herness лишнее, чего не хватает, что у вас дешевле в TCB на порядок.

### H. Перенесённые развилки (мосты-специфичные)

## 6. Формат ответа

По каждому вопросу:

```
### <id вопроса>
**Ответ:** <суть в 3–6 предложениях>
**Развилка:** <выбранная и почему; если ни одна — свой вариант>
**Изменения в репо:** <какие файлы/гейты/пре-регистрации это затрагивает, конкретно>
**Цена:** <время/сложность/TCB/доля провалов>
**Что это не доказывает:** <честная граница>
**Источники:** <открытые вами ссылки; всё остальное — UNVERIFIED>
```

Общие правила: не выдумывать факты о репозитории; не предлагать ослабления гейтов и законов K1–K11 молча; предложение, противоречащее конституции или Q1–Q10, помечать как «поправка конституции»; если вопрос не имеет однозначного ответа — сказать это и дать условие, при котором ответ появится.

## 7. Как ответы будут сверяться

- Каждый ответ сохраняется байт-в-байт с SHA-256 в `docs/research/external/` (метки A–E — порядок вложений владельца).
- Синтез ([`docs/R8-SYNTHESIS.md`](https://github.com/mak777uh/herness/blob/main/docs/R8-SYNTHESIS.md) — образец) различает: **FACT** (проверено чтением/командой с указанием), **FACT-CODE** (следствие чтения кода), **CLAIM** (непроверенное утверждение ответа), **РЕКОМЕНДАЦИЯ** (можно отклонить), **РАЗВИЛКА** (выбор владельца).
- Любое утверждение ответа, противоречащее коду репозитория, проверяется failing-репро, а не спором.
- Совпадение нескольких ответов не считается согласием — только сужением развилки; решения принимает владелец.
