# REQUEST-PROTOCOL — разбор запроса до действия

Владелец говорит на естественном языке. Модель склонна **достроить смысл** и сразу исполнять —
именно так появляются уверенные действия не по адресу. Этот протокол ставит между запросом и
действием обязательный шаг разбора.

## Пять шагов

```
1. Цель одной фразой        — что должно измениться в мире
2. Разложение на утверждения — что запрос утверждает о мире и о желаемом
3. Классификация             — каждое утверждение в одну из четырёх категорий
4. Закрытие неопределённости — вопрос человеку ИЛИ эксперимент
5. Действия                  — исполнить / спросить / измерить / отказать
```

## Четыре категории утверждений

| категория | признак | что с этим делать |
|---|---|---|
| **определено** | смысл единственный, проверяемый | исполнять |
| **не определено** | можно понять двумя способами | спросить владельца, если это про ценности или границы |
| **проверяемо** | спор о факте, а не о смысле | эксперимент, а не мнение |
| **противоречиво** | конфликтует с принципами G1–G3 или с объявленными границами | отказать и назвать конфликт |

Ключевое различие: **вопрос — про ценности и границы, эксперимент — про факты**. Если спор можно
решить прогоном, спрашивать человека нельзя: это перекладывание работы. Если спор про «что для тебя
лучше» — прогон бесполезен.

## Допущения

Всё, что модель решила сама, записывается явно:

```
допущения:
  - «оптимально» понимаю как «дешевле по времени и цене при сохранении границ»
  - источником задач считаю текущий репозиторий
```

Допущение — не факт. Оно живёт с пометкой и проверяется: подтвердилось — становится известным;
опроверглось — записывается в `docs/eliminations.md`.

## Форма разбора

| поле | что содержит | обязательность |
|---|---|---|
| `goal` | цель одной фразой | да |
| `defined` | что понято однозначно | да (может быть пусто) |
| `undefined` | что требует уточнения | да (может быть пусто) |
| `questions` | вопросы владельцу, по одному на неопределённость | каждая неопределённость — вопрос или эксперимент |
| `experiments` | что проверяется прогоном | — |
| `assumptions` | что решено без спроса | — |
| `contradictions` | конфликты с принципами | — |
| `next_actions` | что делаем дальше | да |

Механическая проверка: каждая строка из `undefined` должна иметь вопрос **или** эксперимент.
Иначе разбор неполон — это ловит `hs request`.

## Пример: «сделай оптимальный харнесс»

| категория | содержимое |
|---|---|
| определено | нужен харнесс; он наш; он должен работать |
| не определено | что значит «оптимальный»: скорость, цена, надёжность, автономность |
| проверяемо | какой язык дешевле по итерации; какая ОС держит тулчейны |
| противоречиво | ничего (пока) |
| вопросы | A1: что для тебя «быстрее» |
| эксперименты | E-0001 (базы ОС), E-0002 (язык цикла) |
| допущения | «оптимально» = импакт на единицу времени при сохранении границ |

Так запрос превращается из пожелания в план с проверяемыми частями.

## Когда останавливаться и спрашивать

- неопределённость про **ценности** (что важнее при конфликте);
- неопределённость про **границы** (что можно трогать, что нельзя);
- необратимое действие (деньги, публикация, удаление);
- цена ошибки выше цены вопроса.

В остальных случаях — сначала эксперимент, потом вопрос. Вопрос вместо эксперимента — это
перекладывание работы на владельца.

## Связь с продуктом

Разбор запроса — та же операция, что и границы: **семантика раскладывается в проверяемые смыслы**.
Разница лишь в предмете: там границы человека, здесь границы задачи.


## Где это применимо

Не только к запросам к агенту. Одна и та же операция — отделить определённое от домысленного —
работает везде, где важна определённость:

| область | что раскладывается | пример неопределённости |
|---|---|---|
| **код** | требование до реализации | «сделай быстро» — это про латентность или про сроки? |
| **общение** | смысл сказанного до ответа | «оптимально» — по какому критерию? |
| **задачи** | план до первого шага | «перенеси всё» — что именно входит в «всё»? |
| **решения** | выбор до действия | «лучше» — для кого и при каком конфликте |

## Два режима: чтобы не стать бюрократией

**Быстрый (≈30 секунд).** Три строки, по одной на категорию:

```
понято: <что определено>
неясно: <что домысливаю>  → спрошу / проверю
делаю:  <первый шаг>
```

Достаточно для мелких задач, разговоров и правок.

**Полный.** Контракт `Request` с полями `defined`, `undefined`, `questions`, `experiments`,
`assumptions`, `contradictions`, `next_actions`; проверка — `hs request <файл>`.
Нужен там, где цена ошибки выше цены разбора: необратимые действия, деньги, публикация,
архитектурные решения.

Правило выбора режима: **если отменить действие дёшево — быстрый; если дорого — полный.**

## Пример на текущем разговоре

Владелец: «это применимо ко всему, и к коду, и к общению, и к задачам, где важна определённость».

| категория | содержимое |
|---|---|
| понято | протокол не только для запросов к агенту; нужен универсальный режим |
| неясно → проверить | нужен ли отдельный инструмент для «общения» или достаточно формы |
| делаю | зафиксировать два режима и области применения в документе |

Это и есть применение на практике: одна строка неопределённости, одно действие, без пересказа.
## Что это не даёт

- Гарантии, что классификация верна: она сама может быть ошибочной и должна проверяться.
- Отмены вопросов: часть неопределённости человек закрывает только решением, а не фактом.
- Скорости: разбор стоит времени. Он окупается тем, что не исполняется не тот запрос.
