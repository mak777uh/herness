# DECISION-OS — как устанавливается истина о «правильной ОС»

Дата: 29.10.2026. Это не ADR: здесь не решение, а процедура его получения.
Статус каждого утверждения помечен: **[док]** проверено по документации, **[суждение]** опыт и
рассуждение, **[замер]** требует прогона (E-0001).

## 1. Формальная цель

Выбрать ОС, минимизирующую суммарную цену владения при жёстких ограничениях:

```
цена = время настройки + время простоев + риск невосстановимой поломки
     + стоимость железа + стоимость обслуживания
```

Не «самая быстрая», не «самая лёгкая», не «самая модная» — именно сумма, при условии, что
ограничения ниже выполнены. Ограничение не выполнено → кандидат отбрасывается, каким бы дешёвым
он ни был.

## 2. Жёсткие ограничения (фильтр, не оценка)

| # | ограничение | откуда следует | проверяемость |
|---|---|---|---|
| F1 | glibc-совместимость: Lean/Mathlib, forge, cargo, колёса Python | A3, реальный тулчейн | **[док]** |
| F2 | cgroups v2 и namespaces | A6, квоты и изоляция | **[док]** |
| F3 | снапшоты/поколения и откат | A10, самоизменение | **[док]** |
| F4 | удалённое администрирование без графики | A13, A14 | **[док]** |
| F5 | работа 24/7 без перезагрузок | A15 | **[суждение]** |
| F6 | управление сервисами из кода (API), а не только CLI | ADR-0009 | **[док]** |
| F7 | пригодность для вложенной параллельности | A6 | **[замер]** |

## 3. Кандидаты против фильтра

| ОС | F1 glibc | F2 cgroups | F3 поколения | F4 удалённо | F6 API сервисов | итог |
|---|---|---|---|---|---|---|
| Windows 11 | да | частично (Job Objects) | нет | да | частично | **отсекается** по F3 |
| macOS | да | нет | частично (APFS) | да | частично | **отсекается** по F2 |
| Alpine | **нет** (musl) | да | через LUKS/overlay | да | да | **отсекается** по F1 |
| Buildroot/Yocto | да, но собирать всё | да | своя | да | да | **отсекается** по цене (нет пакетного менеджера) |
| Fedora CoreOS | да | да | да (rpm-ostree) | да | частично | проходит |
| Fedora Silverblue | да | да | да | да | частично | проходит, но десктопный уклон |
| openSUSE MicroOS | да | да | да (btrfs+snapper) | да | да | проходит |
| NixOS | да | да | да (поколения) | да | да | проходит |
| Debian minimal | да | да | **только вручную** (btrfs+snapper) | да | да | проходит условно |
| Ubuntu server minimal | да | да | вручную (btrfs/ZFS) | да | да | проходит условно |

Вывод фильтра: **семейство Linux**, и внутринего два класса — «атомарные из коробки»
(NixOS, MicroOS, Fedora) и «обычные, где поколения надо строить» (Debian, Ubuntu).

## 4. Что решает спор внутри Linux

Три вопроса, и только они:

| вопрос | кто выигрывает | что это докажет |
|---|---|---|
| Сколько ручных шагов до рабочих тулчейнов? | Debian/Ubuntu скорее всего | цена входа |
| Насколько надёжен откат без ручного восстановления? | NixOS/MicroOS | цена ошибки |
| Сколько стоит обучение и поддержка? | Debian/Ubuntu | цена владения |

Мера: E-0001 (время, шаги, падения, откат). Всё, что не измерено там, — **[суждение]**.

## 5. Что уже можно утверждать без замера

1. **[док]** Windows и macOS не проходят фильтр по поколениям и cgroups — это не вкус, а отсутствие
   механизма. Управление ОС (A10) на них недостижимо без виртуализации.
2. **[док]** Alpine отсекается glibc: тулчейны Lean и Foundry — glibc-мир.
3. **[док]** Buildroot отсекается ценой: пакетного менеджера для тулчейнов нет, каждый апдейт — сборка.
4. **[суждение]** Debian minimal — лучшая цена входа и предсказуемость; NixOS — лучший откат и
   воспроизводимость, но дороже в обучении.
5. **[замер]** Что из этого дешевле суммарно — неизвестно. Это и есть E-0001.

## 6. Чего в этом документе нет

- Нет выбора. Выбор появится после E-0001, а не до него.
- Нет установки. Установка — следствие выбора, а не способ его сделать.
- Нет обещания, что победитель окажется удобным: «оптимально» и «приятно» — разные вещи.
