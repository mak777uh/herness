## 1. Короткий вывод

Шесть ответов сходятся в архитектуре следующего слоя: **Lean 4 как статическое ядро,
машиночитаемый `LawRecord-v1` с вычисляемым статусом, один канонический semantic validator,
потоковое чтение через `openat2` от root FD, комната на аппаратной виртуализации, admission
над точными байтами с offline-подписью владельца, производный `active` и генератор,
заблокированный до зелёного ручного среза `head`.**

Но они расходятся в шести местах, которые нельзя «сгладить»: язык канонического валидатора,
точная семантика `file_read_stream`, ускоритель и модель процессов комнаты, механизм
наблюдения эффектов, топология owner-ключа и объём/пороги генератора. Пока эти развилки не
решены владельцем, **нельзя ни писать `file_read_stream`, ни считать срез закрытым**.

Отдельно: R6 подтвердил не только замысел, но и **дефекты текущего кода**, которые нельзя
оставлять «на потом»:

- `head` не имеет разрешающего правила в `policy.json`; `python bin/card_atoms.py --check lab/tools/cards/head.json` даёт `rc=3` (без пути, `--check head`, скрипт отвечает `rc=2` «нет файла» — проверять нужно точный путь);
- в `registry.jsonl` все шесть старых инструментов хранят `"status": "active"`, включая
  `search`, который решением Q8 отвергнут;
- в коде нет проверки admission: `K11_ADMISSION_REQUIRED` есть только как строка словаря;
- `read` делает `resolve_in` → `metadata` → `read_to_string`, то есть проверяет путь отдельно
  от открытия и читает файл целиком;
- `write_beneath` ставит только `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS`. `NO_MAGICLINKS`
  при этом **подразумевается** самим `NO_SYMLINKS` (openat2(2): `RESOLVE_NO_SYMLINKS`
  implies `RESOLVE_NO_MAGICLINKS`), поэтому это не отдельный дефект; реальный пробел —
  отсутствие `NO_XDEV` (проход через точку монтирования);
- `seal` и `netprobe` запускают себя через `Command::new`, хотя карточка обещает
  `process_spawn: false`, а схема — `max_processes: const 1`;
- `resolve_in` всегда проверяет политику как `("read","read")`, независимо от вызывающего
  инструмента.

Это не «мнения внешних моделей»: пункты проверены по коду и перечислены в §3.

## 2. В чём согласны все шесть

1. **Lean 4 — единственное нормативное статическое ядро v0.** TLA+, Alloy, Cedar/Rego не
   вводятся одновременно. Kani — спорное дополнение (B — за, C — против, остальные не
   требуют).
2. **`LawRecord-v1` — машиночитаемая запись, а не проза.** Статус вычисляется из наличия
   доказательства и негативного контроля; `not_proven` не становится зелёным; неизвестный
   закон отвергается; подпись — внешняя оболочка над канонизированным набором записей.
3. **Наблюдение эффектов — измерение, а не доказательство.** Никто не выдаёт
   `observed_code_effects ⊆ card_effects` за математическое доказательство для произвольного
   кода. «Нет событий» не означает «нет нарушений»: слепой/отсутствующий монитор — это
   `unknown`/провал, а не зелёный.
4. **Один канонический semantic validator.** Две независимые семантики не поддерживаются;
   расхождение реализаций — красный тест. Пять ответов выбирают Rust, один (F) — Python;
   это развилка §4.1.
5. **`file_read_stream` читает сырые байты из FD с жёстким потолком.** `max_bytes_read` —
   предел безопасности, `line_count` — предел API; `bytes_read` и `output_bytes` — разные
   величины; `BufReader::take`/`read_to_string` не годятся; `truncated` обязан быть явным.
   Детали различаются (§4.2), но принцип общий.
6. **Чтение — от закреплённого root FD через `openat2`.** Флаги:
   `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS | RESOLVE_NO_XDEV`
   (`NO_MAGICLINKS` уже влечётся `NO_SYMLINKS`, но пишется явно, чтобы не зависеть от
   смены семантики на будущих ядрах);
   `fstat`/`S_ISREG`; fail-closed при отсутствии `openat2`; не-Linux fallback слабее и не
   засчитывается как свидетельство K1.
7. **Комната — `microvm`, без NIC, host mounts, 9p/virtiofs, credentials и лишних устройств.**
   QEMU запускается непривилегированным; TCG — только симуляция; security-run требует
   аппаратного ускорения и доказательства, что ускоритель действительно использован.
8. **Admission подписывает точные байты.** JCS (RFC 8785), domain separation, detached
   Ed25519, SHA-256; привязка к card/source/binary/template/deps/toolchain/policy/room, а не
   к пути; проверка на хосте до запуска; путь и «красивый JSON» не являются идентичностью.
9. **Owner-ключ — offline, вне репозитория, контекста модели и рабочей машины агента.**
   Promoter не имеет приватного материала; подпись — только у владельца; потеря ключа не
   должна давать автоматический путь допуска.
10. **`active` — производный предикат, а не хранимое поле.** Источник истины — append-only
    журнал решений/манифестов; указатель активного кандидата — кэш, который перепроверяется;
    генератор не пишет registry/policy/keys; promoter не подписывает и не расширяет права.
11. **Генератор заблокирован до зелёного ручного `head`.** Нужны semantic validator,
    admission, комната, наблюдение, замороженные до прогона задачи и пороги, held-out набор,
    отсутствие ручных правок кода, 100 % критических контролей и подпись владельца. В v0 —
    только типизированные слоты закрытого шаблона, не свободный Rust.
12. **`policy_checked` ≠ `contract_checked` ≠ `K9_model_checked`; `K9_proven` в v0
    запрещён.** `K11_admitted` — отдельная ступень, привязанная к подписанному манифесту.

## 4. Где расходятся

### 4.1. Канонический semantic validator: Rust или Python

| ответ | позиция |
|---|---|
| A | Rust — единственный; Python только запускает/читает |
| B | Rust в том же крейте; Python — генератор векторов, обязан совпадать побайтово |
| C | Rust-библиотека; Python — тонкий CLI или потребитель общих векторов |
| D | Rust-библиотека/CLI; Python — диагностика, не второй источник разрешения |
| E | Rust-бинарь/модуль; Python вызывает его как подпроцесс |
| F | **Python — канонический** (`bin/card_semantic.py`); Rust принимает validated card + receipt и пересчитывает только digest'ы |

Развилка не косметическая. Если Python канонический, promoter должен доверять
«receipt» от Python-валидатора; если receipt можно подделать или запустить валидатор с
другими правилами, появляется второй путь разрешения. Если Rust канонический, нужен новый
Rust-модуль и дифференциальный корпус с текущим Python-checker, иначе старый и новый
валидаторы разойдутся молча. Пять ответов за Rust, один за Python; **решает владелец**.

### 4.2. `file_read_stream`: шесть несовместимых таблиц

| вопрос | A | B | C | D | E | F |
|---|---|---|---|---|---|---|
| CRLF | LF 1 Б, CRLF 2 Б; терминатор входит в `bytes_read` | `CR` перед `LF` — часть терминатора и снимается | `\r` **остаётся** частью строки, не нормализуется | CRLF — один разделитель, `CR` снимается | CRLF — разделитель, снимается при выдаче | LF; один завершающий `\r` снимается |
| частичная строка при byte cap | не выдавать | при конфликте — отказ, а не «сколько влезло» | не выдавать как полную; `stopped_by` | не выдавать; вернуть `K4_RESOURCE_LIMIT`/partial | **выдаёт обрезанную строку** (`"abcd"`) | не выдавать |
| `truncated` | источник не прочитан полностью | `stop_reason != "eof"` | `stopped_by == byte_limit` | line cap без EOF или byte cap | остались непрочитанные байты | `bytes_read < st_size` или обрезка `output_bytes` |
| byte cap внутри строки | `ok`, `truncated=true` | отказ при конфликте лимитов | `ok`, `stopped_by=byte_limit` | `K4_RESOURCE_LIMIT`/partial | `ok`, частичная строка | `ok`, `lines=[]`, `truncated=true` |
| read-ahead в `bytes_read` | только реально прочитанные байты | **включает** read-ahead | логический счёт до остановки; read-ahead не входит | включает lookahead/read-ahead | `bytes_read = raw_buf`; при line_limit хвост уже прочитанного чанка **не учитывается** — счётчик может быть меньше фактического чтения | сырые байты из FD |
| невалидный UTF-8 | отказ с отдельным кодом | ? | ? | отдельный стабильный код, не `K6_DATA_CLASS_UNKNOWN` | `S1_SCHEMA` | `S1_SCHEMA` как интерим; кода в v2 нет |
| нет файла | ? | ? | ? | ? | ? | gap; интерим `S2_ARTIFACT_MISSING` |

Дополнительно E в `truncated` делает **однобайтовый `read` после исчерпания бюджета**,
чтобы отличить EOF. Это прямо противоречит критерию среза «`bytes_read` не больше
`max_bytes_read`»: такой байт либо не учитывается (тогда счётчик лжёт), либо учитывается
(тогда лимит превышен). E также выдаёт частичную строку как строку, что противоречит
A/D/F и смыслу `line_count`.

**Что нужно зафиксировать до кода:** одну таблицу «вход → `lines`/`bytes_read`/
`truncated`/код» на все граничные случаи, включая ровно-в-лимит, пустой файл, файл без
завершающего `LF`, CRLF, разрез многобайтового UTF-8, отсутствие файла. Без этого
`HEAD-SLICE-R1` нельзя ни реализовать, ни проверить.

### 4.3. Ускоритель и модель процессов комнаты

| ответ | security-run | замечание |
|---|---|---|
| A | WSL2+KVM, если проверка пройдёт; иначе WHPX | `/dev/kvm` сам по себе ничего не доказывает |
| B | WSL2+KVM основной; WHPX вторичный, слабее по host confinement | QEMU под Landlock+seccomp+cgroup |
| C | **WHPX основной**; KVM вторичный | гость сразу под Hyper-V, без вложенности |
| D | WHPX кандидат; KVM — если реально стартует | «WHPC» — опечатка |
| E | WSL2+KVM или WHPX; TCG — симуляция | read-only virtio-blk, virtio-serial |
| F | **WSL2+KVM основной**; WHPX — dev | измерено: `/dev/kvm` есть, QEMU в WSL нет |

Факты машины: QEMU 11.1.0 на Windows поддерживает `whpx` и `tcg`, `microvm` стартует;
WSL2 kernel `6.6.114.1` имеет `/dev/kvm`, но QEMU в WSL не установлен. Это значит, что
«WSL2+KVM» — не готовая среда, а шаг установки; «WHPX» — готовая, но с другим host
confinement. Выбор нельзя делать по вкусу: нужен один security-прогон с доказательством
ускорителя и fail-closed при его отсутствии.

Отдельная развилка — **`max_processes: const 1`**. B заметил: если PID1 — supervisor, а
инструмент — его ребёнок, то процессов два. E обходит это тем, что `pids.max=1` применяется
к cgroup инструмента, а supervisor остаётся снаружи; но схема этого не различает. Нужно
решить, что считает `max_processes`: дерево инструмента или всю комнату.

### 4.4. Наблюдение эффектов

| ответ | механизм | что считается свидетельством |
|---|---|---|
| A | seccomp allowlist + независимый tracer + телеметрия stdout/stderr/FD | комбинация; один канал недостаточен |
| B | seccomp allowlist + отдельный serial-канал «ядро» + audit | инструмент не должен иметь fd на канал наблюдателя |
| C | ptrace/strace + таблица syscall→atom | seccomp-unotify отклонён: указатели subject to TOCTOU |
| D | внешний supervisor с ptrace + deny-by-default seccomp | наблюдение до `exec`, все потоки/дети |
| E | seccomp-unotify + фазовый барьер `HERNESS_TOOL_ACTIVE` | наблюдаются активные syscall-имена; указатели не инспектируются |
| F | инструментирование шаблона + strace в тестах + статический lint | production-слой пока self-report, честно помечен |

Ограничения, которые сужают выбор: в госте без `NET` seccomp-фильтр не ставится
(`Invalid argument`), а `pre_exec` даёт `ENOSYS` — фильтр должен ставить сам процесс
(`harden_self`). Значит «seccomp + независимый канал» в NET-less комнате сразу не работает;
нужен либо `NET=y` без NIC, либо Landlock, либо ptrace/strace. Это решение комнаты, а не
деталь реализации.

### 4.5. Топология owner-ключа

| ответ | схема | может ли recovery выдать допуск |
|---|---|---|
| A | offline recovery root + operational signing key | **да**, recovery делегирует новый operational |
| B | `owner-sign` + `owner-revoke`; восстановления подписи нет | нет; потеря = отзыв + повторный допуск |
| C | активный + холодный запасной | запасной может отозвать и добавить новый — косвенно да |
| D | один offline-ключ + зашифрованные копии; без «универсального recovery» | нет; потеря = ручная переустановка trust anchor |
| E | recovery root + active signing; recovery подписывает **только** ротацию `trusted-keys.json` | косвенно да: может добавить новый active-ключ |
| F | offline Ed25519 + paper/backup; recovery = out-of-band идентичность + re-admission | нет автоматического пути; каждый recovery — событие и повторный допуск |

Это главная развилка K11: recovery, который может добавить новый signing key, — это второй
путь допуска. B прямо называет такой ключ backdoor; A/E считают разделение доменов
достаточным. Нужно выбрать threat model: защищаемся ли мы от компрометации recovery-ключа
или только от потери рабочего.

### 4.7. Приоритет отказов S05

| ответ | порядок |
|---|---|
| B | `K11` > `K6_SECRET_EGRESS` > `K6_DATA_CLASS_UNKNOWN` > `S6_CLOSURE_BREACH` > `K4` > `S1` |
| C | `K11` > `K6` > нарушение scope > `K4` > `S1` |
| E | `K11` > `K6_SECRET_EGRESS` > `K6_DATA_CLASS_UNKNOWN` > `S6` > `K4` > `S1` |
| F | `K11` > `K6_SECRET_EGRESS` > `K6_DATA_CLASS_UNKNOWN` > `K4` > `S6` > `S1` |

Спор — `K4` против `S6` и поведение «вне корня + неизвестный класс». B/E хотят видеть
`K6_DATA_CLASS_UNKNOWN` даже для пути вне корня; F/C — сначала `S6`, потому что вне корня
класс не запрашивается. Нужно зафиксировать не только порядок выдачи, но и порядок
**вычисления**: admission → схема → scope → класс → лимиты, иначе «первичный код» зависит
от случайного порядка `if`.

### 4.8. Мелкие, но обязательные расхождения

- B требует, чтобы сохранённый манифест **уже был** в форме JCS (`stored == JCS(stored)`);
  остальные требуют лишь канонизации перед подписью. Первое сильнее и дешевле в проверке.
- C предлагает SSHSIG (`ssh-keygen -Y sign`) с namespace вместо «голого» Ed25519; это
  отклонение от RFC 8032, его нужно записывать в решении.
- E предлагает `execveat` из sealed `memfd`; F тоже упоминает `execveat`; остальные
  ограничиваются проверкой digest перед запуском. Уровень привязки разный.
- A/B/C/D/E называют разные имена шаблонов (`file_read_stream`, `directory_read_list`,
  `dir_read_entries_v1`, `file_digest_sha256_v1`). Переименование без решения сломает
  ссылки в карточках и тестах.
- F предлагает Python-валидатор и receipt; A/B/C/D/E — Rust. Это та же развилка §4.1, но
  она влияет на TCB promoter'а.

## 5. Что в ответах неверно, неполно или не доказано

1. **C и D не проверяли код по ссылкам.** Их утверждения о репозитории — не свидетельства.
   C прямо говорит: «ссылки не открывал, код не запускал». D не заявляет проверок.
2. **B не читал тела `tool_read_in`/`write_beneath`, policy и registry.** Его вывод о
   TOCTOU и `resource_of` ценен, но часть деталей он достраивал по вызовам. Проверка §3
   подтвердила главное, но не всё.
3. **`resource_of` — не доказанный обход чтения.** Функция действительно превращает
   `/etc/passwd` в `file:/mnt/etc/passwd`, и `policy_allows("read","read", …)` на таком
   ресурсе вернёт `true`. Но `resolve_in` сначала проверяет `starts_with(root)` и отвергает
   путь. Это дефект публичной функции и модели политики, а не работающий escape. Формулировка
   B «политика не-стена» слишком сильна для текущего `resolve_in`.
4. **`resolve_in` — confused deputy, но не повышение прав.** Он всегда проверяет
   `("read","read")`, поэтому `list`/`search`/`seal` проходят первую проверку от имени
   `read`. Это расхождение модели и кода; опасность появится, если `read-allow` расширят или
   уберут, а вызывающие инструменты останутся.
5. **E в S02 нарушает собственный контракт.** Однобайтовый EOF-probe после бюджета и выдача
   частичной строки несовместимы с «`bytes_read <= max_bytes_read`» и «частичная строка не
   выдаётся как полная». Вдобавок при `line_limit` `bytes_read = raw_buf.len()` не включает
   хвост уже прочитанного чанка, поэтому счётчик может быть меньше фактического чтения.
   Нельзя брать E-алгоритм без исправления.
6. **E/ C предлагают механизмы, которые не работают в NET-less госте.** `seccomp-unotify`
   требует seccomp, а seccomp-фильтр в этом ядре зависит от `NET`; `pre_exec` даёт `ENOSYS`.
   Это не их вина (они могли не знать замера), но в комнате v0 это ограничение.
7. **Kani — не консенсус.** B предлагает 3–5 harness'ей, C отвергает Kani как лишнюю
   зависимость; остальные не требуют. Без тел функций и toolchain это не готовый план.
8. **`seccomp-unotify` как наблюдатель указателей опасен.** C прямо ссылается на TOCTOU в
   `seccomp_unotify(2)`. E использует его для имён syscall и фазового барьера, не для
   инспекции указателей; это допустимо только с этой оговоркой.
9. **Ни один ответ не решает K6 для секретов.** Все оставляют v0 fail-closed на
   `public`/`model_visible`; redaction секретов, taint и сетевые мосты не доказаны.
10. **Ни один ответ не является approval.** Шесть текстов — рекомендации. Они не меняют
    конституцию, policy, registry, словарь, схему, пре-регистрацию или код.
11. **«Все ссылки открылись» — заявление F, не наша проверка.** Мы проверили только
    утверждения, перечисленные в §3; остальное — на совести авторов.
12. **Статистика B верна как арифметика, но не как гарантия.** 8/8, 20/20, 24/24 — это
    инженерные гейты; «безопасно на 99 %» из них не следует.

## 6. Что можно делать без нового решения владельца

Уже сделано в этом коммите:

- шесть сырых ответов сохранены байт-в-байт, с размерами и SHA-256;

- этот синтез фиксирует согласие, расхождения и проверенные дефекты.

Можно делать дальше, не меняя конституцию/policy/registry/код:

- добавить в handoff точный список блокеров и следующий порядок;
- подготовить R7-бриф по развилкам §4;
- добавить **падающие** тесты/репро для подтверждённых дефектов (без изменения поведения):
  `resource_of` на пути вне корня, `resolve_in` от имени `list`/`seal`, `head` без policy,

  `HEAD-SLICE-R1`.

Нельзя без решения владельца:

- добавлять `head` в `policy.json` или менять policy/registry;
- менять `tool-card-v1.schema.json`, словарь отказов или пре-регистрацию;
- писать `file_read_stream`, admission, promoter, комнату или генератор;
- объявлять срез закрытым, `K9_proven`, `K11_admitted` или «безопасным»;
- трогать реальный `/mnt`, сеть, мосты, ключи или секреты.

## 7. Развилки для владельца (Q11–Q18)

Это не решения, а вопросы, на которые нужен явный ответ **до** кода. Рекомендация агента
указана, но она не заменяет решение.

| id | вопрос | варианты | рекомендация агента |
|---|---|---|---|
| Q11 | язык канонического semantic validator | Rust (A/B/C/D/E) или Python (F) | Rust в `core-rs`, Python — только генератор векторов/CLI; иначе receipt становится вторым источником разрешения |
| Q12 | точная семантика `file_read_stream` | таблицы A–F различаются | заморозить одну таблицу: `max_bytes_read` абсолютен, лишний байт не читать, частичную строку не выдавать, `truncated` не лжёт, CRLF снимать, UTF-8 — отказ (интерим `S1_SCHEMA` до поправки словаря) |
| Q13 | ускоритель security-run | WSL2+KVM или Windows+WHPX | измерить оба; security-run только с явным `-accel` и доказательством из QEMU/гостя; TCG — `simulation`; выбор — по результату замера, не по вкусу |
| Q14 | что считает `max_processes` | только дерево инструмента или вся комната | считать дерево инструмента; supervisor комнаты — отдельно; иначе `const 1` запрещает собственный PID1 |
| Q15 | механизм наблюдения | ptrace/strace, seccomp-unotify, инструментирование | в тестах — ptrace/strace + wrapper; в комнате — Landlock/seccomp как стена; production-labель `self_reported`; seccomp-unotify только для имён syscall, не указателей |
| Q16 | топология owner-ключа | recovery root (A/E), sign+revoke (B), active+standby (C), single+backup (D/F) | B/D-гибрид: ключ подписи + отдельный revoke-ключ; recovery не выдаёт допуск, потеря = повторный допуск; иначе recovery — второй путь K11 |
| Q17 | объём пилота генератора | 1 шаблон (A/D), 3 (B/C), 4 (E), 12 spec (F) | 1 шаблон `file_read_stream`, 20 функциональных + 20 атак, 100 % критических, 3 повтора, 0 ручных правок; расширять только после успеха |

активировать. Это изменение registry/policy, поэтому без «да» владельца не делается.
