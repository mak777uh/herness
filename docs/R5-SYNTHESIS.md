## 1. Короткий вывод

Оба ответа сходятся в главном: **генератор пока писать нельзя**. Сначала нужен один
read-only вертикальный срез: типизированная карточка → двусторонний checker → чтение
через `openat2` от закреплённого directory FD → минимальная комната → evidence.
Сеть, запись, секреты, `search`, downstream-мосты и автоматический promotion в первый
срез не входят.

Оба ответа также требуют чинить `card_atoms.py` до генератора: пустой `fs.read` не должен
превращаться в право `read /mnt/**`, а конфликт должен проверяться в обе стороны.

Расходятся они в четырёх существенных местах: набор `kind`, судьба `search`, статус TCG
как границы безопасности и строгость K6. Есть и более мелкие расхождения — словарь
отказов, `head`, promotion, метрики.

## 2. В чём оба согласны

1. **Карточка — декларация, а не разрешение.** `kind` не выдаёт capability; отсутствие
   capability в admission/policy означает отказ, даже если карточка объявляет эффект.
2. **Пустой массив — это «нет эффекта», а не wildcard.** Отсутствующее обязательное поле —
   ошибка схемы. Синтез `/mnt/**` из пустого `read` запрещён.
3. **Запрет сильнее разрешения.** Пересечение `allow` и `deny` — конфликт, а не «последнее
   правило выигрывает».
4. **Статика и динамика нужны вместе.** Статическая проверка — включение множеств
   авторитетов (`child ⊆ parent`); динамическая — наблюдение трасс/сисколов. Ни одна из
   них по отдельности не доказывает поведение произвольного Rust-кода.
5. **Четырёхсторонняя монотонность:**
   `observed_code_effects ⊆ card_effects ⊆ approved_capabilities ⊆ room_ceiling`,
   плюс `policy_allow_for_tool == card_effects` для v0 (лишнее разрешение — orphan grant)
   и `card_effects ∩ policy_deny = ∅`.
6. **`head` обязан читать не больше объявленного.** Обе стороны требуют `max_bytes_read`
   и потоковое чтение; «прочитать файл целиком и обрезать» — не выполнение контракта.
7. **Чтение — через `openat2` от root FD.** Не `canonicalize → проверка → повторное
   открытие по строке пути`. `write_beneath` уже использует `openat2` — это прецедент.
8. **K6 в v0 не решается регулярками.** Оба ответа признают, что классификация и redaction
   ненадёжны; оба ограничивают v0. B жёстче: только доверенный fixture-манифест
   `model_visible`, `unknown` — отказ.
9. **K9 и K11 не обеспечены.** Downstream-мосты в v0 отключены; `policy_checked` — не
   `K9_proven`. Admission иностранного артефакта — отдельный подписанный манифест.
10. **WSL — только разработка.** Комнату и границу безопасности нельзя выдавать за WSL.
11. **Генератор отделён от promotion.** Генератор пишет только candidate/staging; менять
    active registry/approval может только отдельный promoter после проверки, а approval —
    владелец.
12. **Автоматического approval в v0 нет.** AI-ревьюер может объяснять diff, но не голосовать
    и не подписывать.
13. **Новые коды отказа — поправка словаря, а не самодеятельность агента.** Переиспользовать
    `S1_SCHEMA` или `S6_CLOSURE_BREACH` для K4/K6/K11 нельзя.
14. **Один срез — один шаблон.** Никакого freeform, произвольных путей, команд, динамической
    загрузки кода и «универсального observe».

## 3. Где расходятся

### 3.1. Набор `kind` (D01)

| | A | B |
|---|---|---|
| набор | `observe`, `transform`, `staged_write`, `bridge_request` | `file_read`, `directory_read`, `file_write`, `digest`, `bridge_request` |
| логика | классы эффектов; `read/search/head` — шаблоны внутри `observe` | файловые операции; `head` — режим `file_read` |
| `search` | входит в `observe` с лимитами | reject в первом срезе |
| риск | `observe` становится «мусорным ведром» | пять kind всё равно могут быть слишком широкими |

**Рекомендация агента:** для v0 — набор B, потому что он ближе к текущим шести инструментам,
не прячет `search` внутри `observe` и позволяет явно отвергнуть `search` в первом срезе.
Это не решение владельца и не действующий enum; см. Q1.

### 3.2. `search` в первом срезе

A допускает `search` как `observe` с `max_files`/`max_depth`. B отвергает: это композиция
`directory_read ∘ file_read`, большой вывод и K6-taint, а K9 не обеспечен.

**Рекомендация:** B. `search` остаётся выключенным до отдельного admission и taint-модели.
Текущий Rust `search` к тому же читает файлы целиком и имеет TOCTOU-окно.

### 3.3. QEMU и TCG

A: «TCG или KVM, без user mounts» — считает TCG допустимой комнатой.
B: TCG — non-virtualization use case; QEMU не обещает guest isolation; для security-утверждения
нужны KVM/HVF и поддерживаемый machine type.

**Проверено нами:** документация QEMU прямо говорит, что non-virtualization use case (TCG)
не должен полагаться на QEMU для guest isolation или каких-либо security guarantees;
для virtualization use case нужны KVM/HVF и machine type из списка (`microvm`, `q35`, …).
Источник: [QEMU Security](https://www.qemu.org/docs/master/system/security.html), прочитан
16.11.2026.

**Рекомендация:** B. Пока не измерено, какой ускоритель реально доступен, любой прогон на TCG
называется симуляцией, а не границей безопасности. Это вопрос Q5.

### 3.4. K6

A: taint by source + canary-маркеры; `observe` может читать `unknown`, если объявлен
`K6_SECRET_LEAK` или используется `SecretHandle`.
B: только доверенная классификация `public`/`model_visible`; `unknown`/`secret` — отказ;
никаких реальных секретов и handle в v0; canary — тест, а не граница.

**Рекомендация:** B. Canary-маркер не является границей безопасности и не должен быть
условием допуска. `SecretHandle` в v0 не реализуется. Это вопрос Q6.

### 3.5. Коды отказа

A использует `S6_CLOSURE_BREACH` для превышения лимита и `S1_SCHEMA` для классов данных.
B справедливо замечает: точных кодов для K4/K6/K11 в `lab/refusal-codes.json` нет;
переименование ситуаций в чужие коды маскирует отказ.

**Рекомендация:** B. До поправки словаря использовать только существующие коды, а
непокрытые ситуации называть статусом `uncovered`/`unknown` без кода. Это вопрос Q3.
Предлагаемые B коды (`K4_RESOURCE_LIMIT`, `K6_DATA_CLASS_UNKNOWN`, `K6_SECRET_EGRESS`,
`K11_ADMISSION_REQUIRED`) — только предложение.

### 3.6. `head` и потоковое чтение

A: `BufReader::take(limit)`. B: не полагаться на read-ahead `BufReader`; использовать
собственный ограниченный цикл чтения от FD, отдельно считать `bytes_read`, не смешивать
`max_bytes_read` с `output_bytes`.

**Рекомендация:** B. `BufReader::take` может читать больше, чем отдаёт; для контракта нужен
измеримый счётчик. Это часть C03.

### 3.7. Promotion и K10

A: отдельные Unix-пользователи `gen`, `prom`, `root`; генератор — чистая функция.
B: генератор и checker — untrusted workers в карантине; promoter — host-side процесс;
owner подписывает detached-подписью; active pointer меняется атомарно; guest-права не
являются границей для K10.

**Рекомендация:** B как более полная модель; Unix-разделение A полезно как
defense-in-depth, но недостаточно: root в guest и скомпрометированный promoter ломают
всю схему. Это вопрос Q7.

### 3.8. Метрики

A не даёт порогов. B даёт scorecard: 100 % критических негативных контролей, ≥ 18/20
общего понимания, 100 % чувствительности критических мутаций, ≥ 95 % функциональных
пилотных задач, детерминизм и лимиты.

**Рекомендация:** принять scorecard B как **черновик** для пре-регистрации пилота, не как
закон. 20 задач не доказывают безопасность; это инженерный гейт. Это вопрос Q9.

## 4. Ошибки и риски в самих ответах

- **A, Lean `compose`:** комментарий говорит «`deny_fs := union` — пересечение запретов».
  Объединение запретов — это не пересечение. Код с `union` консервативен (запрет, если
  запрещает любая сторона), но комментарий вводит в заблуждение; формулировку нельзя
  переносить в конституцию без исправления.
- **A, K6:** одновременно `unknown = deny` и «`observe` может читать `unknown` с canary».
  Это противоречие; canary не является границей.
- **A, коды:** `S6_CLOSURE_BREACH` для лимита и `S1_SCHEMA` для класса данных — подмена
  смысла кода; словарь этого не разрешает.
- **A, C02:** фраза «синтетический `netprobe` с пустым `fs.read` теперь даёт OK статически»
  верна только при условии, что пустой `read` не порождает атомов. Если checker всё ещё
  синтезирует `/mnt/**`, это не OK. Проверять надо не формулировку, а тест.
- **B, строгое равенство:** `policy_allow_for_tool == card_effects` полезно для v0, но
  сравнивать нужно **эффекты**, а не все атомы (лимиты, обязанности отказа и негативные
  обязанности не являются capability). Иначе checker будет требовать policy-правило на
  «обязанность отказа».
- **B, схема:** `tool-card-v1` — большая схема с новыми кодами отказа. Она не становится
  действующей от того, что лежит в ответе; это draft до approval владельца.
- **B, TCG:** вывод правильный, но он опирается на внешнюю документацию; перед
  security-утверждением нужно проверить фактическую версию QEMU, machine type и ускоритель
  командой, а не предполагать.
- **Оба:** ни один ответ не является доказательством безопасности; это рекомендации.
  Полные тексты — в [`docs/research/external/`](research/external/README.md).

## 5. Что проверено нами, а не принято на слово

| проверка | команда/источник | результат |
|---|---|---|
| ложное зелёное `card_atoms` | `python bin/card_atoms.py --derive/--check` на синтетической карточке `netprobe` | воспроизведено в R5 §3; пустой `fs.read` даёт право `read /mnt/**`, `--check` говорит `ok`, rc=0 |
| JCS-векторы B | `python -c` + `hashlib.sha256` по пяти строкам | все пять SHA-256 совпали с таблицей B |
| QEMU TCG | [QEMU Security](https://www.qemu.org/docs/master/system/security.html) | TCG — non-virtualization use case; QEMU не обещает guest isolation; для virtualization нужны KVM/HVF и поддерживаемый machine type |
| TOCTOU `read/search` | чтение `core-rs/src/loopmod.rs` | `resolve_in` проверяет путь, затем `std::fs::read_to_string` открывает его заново; окно статически видно, эксплуатация не воспроизводилась |
| `head` целиком | `core-rs/src/loopmod.rs`, `tool_read_in` | файл читается целиком, затем обрезается; обещание карточки не обеспечено |
| `tool_card.py --render` | `bin/tool_card.py` | `closure.net` не выводится; хвост R3 C44 остаётся |

Эти проверки не доказывают, что Rust-код можно безопасно исполнять; они фиксируют дефекты
проверяющей стороны.

## 6. Что агент может сделать без нового решения владельца

Это не законы и не capability. Это починка приборов и подготовка черновиков.

1. **Починить `card_atoms.py`:**
   - убрать синтез `read /mnt/**`;
   - пустой массив — ноль атомов;
   - выводить положительные атомы для объявленных `write` и `net`, а не только для `read`;
   - запрет записи при пустом `write` — универсальный (`**`), а не «всё, кроме `/mnt/work/**`»;
   - двусторонний `conflicts()`: card→policy deny и policy allow→card;
   - `--check` возвращает не 0, если есть `uncovered`; `uncovered` — не «зелёный»;
   - регрессионный тест на синтетический `netprobe`, `/mnt2` vs `/mnt`, allow без card,
     card без allow, deny overlap.
2. **Сохранить сырые ответы и сводку** в репозитории, чтобы следующий агент не додумывал.
3. **Подготовить draft `tool-card-v1`** отдельным файлом, но не делать его действующим
   валидатором до approval владельца.
4. **Подготовить пре-регистрацию первого среза** (`head`, синтетический `model_visible`
   fixture, без сети/записи/секретов) — но не запускать генератор.
5. **Не менять** конституцию, policy, registry, approval, словарь отказов и гейты.

## 8. Предлагаемый первый вертикальный срез (черновик, не пре-регистрация)

- `kind: file_read`, один шаблон `file_read_stream`.
- Вход — один неизменяемый синтетический файл с классом `model_visible`, без реального
  `/mnt` владельца.
- Выход — `lines`, `truncated`, `bytes_read`; `max_bytes_read` — жёсткий лимит.
- Чтение — `openat2` от root FD, `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS |
  RESOLVE_NO_MAGICLINKS | RESOLVE_NO_XDEV`, затем `fstat` и чтение только из FD.
- Комната — без сети, без host mounts, без SSH/Git/API-ключей; QEMU-процесс
  непривилегированный; TCG, если нет KVM/HVF, помечается как симуляция.
- Evidence — card/source/binary/template/toolchain/policy/room digests, trace digest,
  счётчики, negative controls.
- Kill criteria: любой критический negative control принят; checker зелёный при
  отсутствующей телеметрии; `head` читает больше `max_bytes_read`; TCG выдан за
  security boundary; генератор может писать в protected path.

Этот срез — предложение. Порог и вход фиксируются отдельной пре-регистрацией после
ответов владельца на Q1–Q10.

## 9. Что этот документ не доказывает

- Что A или B правы.
- Что выбранный `kind`, схема или алгебра полны.
- Что `openat2`/QEMU/Landlock обеспечивают безопасность на этой машине.
- Что K6/K9/K11 можно считать обеспеченными после починки checker.
- Что генератор можно писать сразу после этого документа.
- Что 20 пилотных задач или 100 % на конечном наборе дают общую безопасность.
