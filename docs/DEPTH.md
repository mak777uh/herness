# DEPTH — насколько глубоко делать самому

Справочник решений (`PROBLEMS.md`) отвечает на вопрос «какие бывают подходы». Этот документ —
про вторую ось, без которой первый неполон: **на какой ступени владения мы стоим и почему именно
на ней.**

## Зачем вторая ось

«Взять NixOS» и «написать свою ОС вокруг чужого ядра» — не два продукта, а две ступени одной
лестницы. Пока лестница не названа, любой выбор выглядит как «взяли, потому что проще», хотя может
быть «взяли, потому что дальше дороже, а выигрыш не проверен».

Владелец сформулировал это так: **«писать ОС самому, потом — писать ОС самому вокруг чужого ядра»**.
Спешки нет: важна оптимальность, а не скорость. Значит лестница должна быть явной, а не подразумеваемой.

## Лестница

| ступень | что | цена | риск |
|---|---|---|---|
| **D0** | взять готовое как есть | 0 | чужая воля: сломают обновлением |
| **D1** | настроить (конфиг, политики) | дни | настройка не переживёт обновление |
| **D2** | обернуть (свой адаптер/плагин поверх) | недели | живём на чужом API |
| **D3** | собрать своё из чужих компонентов | месяцы | сборка — тоже зависимость |
| **D4** | своё ядро, чужие периферии | месяцы–годы | один человек против экосистемы |
| **D5** | всё целиком своё | годы | срок жизни проекта |

**Это не «чем глубже, тем лучше».** D5 для поиска — это ферма и годы; D5 для ОС — драйверы и
поддержка железа. Глубина оправдана только тем, что покупает, а не сама по себе.

## Пример: операционная система

| ступень | что значит |
|---|---|
| D0 | Ubuntu как есть (сейчас в WSL) |
| D1 | конфиг NixOS + flake: версии зафиксированы файлом |
| D2 | свой слой поверх чужой ОС: профиль, плагины, обвязка |
| D3 | своя сборка дистрибутива из nixpkgs: свой набор пакетов, инсталлятор, профиль |
| **D4** | **своя ОС вокруг чужого ядра**: свой userland, init, пакетный менеджер, обновления с откатом |
| D5 | своё ядро или unikernel под наши задачи |

D4 достижим для одного человека: userland, пакетный менеджер и откат — это код, а ядро — чужая
стабильная работа. D5 — уже про драйверы и годы, и выигрыша у нас не просматривается.

## Где мы сейчас

| класс | ступень | шаг вперёд |
|---|---|---|
| ОС | **D1** (NixOS выбран, не установлен) | D2: свой слой поверх; D4 — долгая цель |
| Сеть и поиск | **D2** (свой `fetch`) | D3: свой агрегатор; D4: свой индекс по нужным источникам |
| Ядро харнесса | **D3** (свой цикл, журнал, свидетельства) | D4: своё ядро без чужого рантайма |
| Безопасность | **D1** (deny-лист, отказ) | D2: модель действий; D3: песочница |
| Память | **D2** (журнал + артефакты) | D3: event sourcing, повтор с места |
| Модели | **D1** (своя обёртка) | D2: свой слой выбора/кэша; D3: локальный инференс |

## Правила

1. **Каждое решение называет ступень.** «Берём NixOS» — это D1, а не «просто берём». Без номера
   решение неполно.
2. **Шаг вглубь требует причины и цены.** Не «хочу своё», а «D1 не даёт X, D4 даёт, стоит N месяцев».
3. **Глубина считается по классу, а не по проекту.** Можно писать своё ядро харнесса и брать чужой
   пакетный менеджер — это нормально, если названо.
4. **Глубина не отменяет проверку.** Своё на D4 может быть хуже чужого на D0; это выясняется замером,
   а не статусом «мы написали сами».
5. **Время не аргумент против.** Год на D4 — нормально, если он покупает то, чего нет на D1.

## Чего этот документ не даёт

- Не говорит, какая ступень «правильная»: это решается под класс задач.
- Не оценивает наши силы: «один человек может D4» — гипотеза, а не измерение.
- Не отменяет зависимостей: на D3–D4 их меньше, но не ноль.
