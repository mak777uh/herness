## 2. Плановые этапы 1.6 и 2.1: дефекты подтверждены построчно

### 2.1. Этап 1.6 — «приёмка только читает» сейчас неверно

`core-rs/accept-run.ps1:186` (извлечение журнала из образа после прогона):

```powershell
... e2fsck -fy .../acc.img >/dev/null 2>&1; mount -o loop .../acc.img /tmp/acc && cp ...
```

Три нарушения заявленного «read-only» в одной строке:

1. **`e2fsck -fy` чинит свидетельство на месте** — флаг `-y` отвечает «да» на все вопросы починки. Это запись в образ-улику, а не чтение.
2. **`mount -o loop` без `ro`** — монтирование на запись; даже без e2fsck ядро может обновить суперблок/журнал ext4.
3. **Код возврата e2fsck выброшен** (`>/dev/null 2>&1;`) — починка могла провалиться, и это никак не видно.

Тот же паттерн повторяется в `core-rs/crash-resume.ps1:85`. При этом `docs/ADR-0049` (строки 92–94) утверждает: «Проверка не меняет свидетельство: образ после e2fsck монтируется только для копирования» — **текст ADR противоречит реализации**.

**Важный нюанс для правки (иначе наивный фикс сломает приёмку):** QEMU убивается жёстко (`$process.Kill()`), поэтому ext4 в образе почти всегда «грязная». Наивное `mount -o ro,noload` на грязной ФС может отдать **устаревший** журнал (незакоммиченные транзакции не накатываются) — приёмка начнёт читать вчерашние события и молча врать. Правильная форма:

- SHA-256 исходного образа **до** и **после** всей процедуры; несовпало → UNKNOWN/FAIL;
- извлечение журнала — **с копии** образа (`cp` → e2fsck/монтирование уже копии; исходник не трогаем вообще);
- либо чистый экспорт журнала из гостя до убийства QEMU (гость сам делает sync и отдаёт файл через мост) — тогда e2fsck не нужен вовсе;
- применить к **обоим** скриптам и поправить текст ADR-0049 отдельной записью.

### 2.2. Этап 2.1 — kind не покрыт контрольной суммой

`core-rs/src/journal.rs:89–106`, `append()`:

```rust
body: len(u32) + seq(u64)          // 12 байт
crc = SHA256(body ++ payload)[0..4] // хеш считается БЕЗ kind
body.push(kind.byte());             // kind дописывается ПОСЛЕ хеша
```

`walk()` хеширует `bytes[pos..pos+12] ++ payload` — байт kind в хеш не входит. Следствие: **подмена Data(1) ↔ Commit(2) не детектируется**. Это не теоретический риск: именно маркер commit отделяет «заявлено» от «подтверждено», и битый kind меняет смысл записи при зелёной CRC. (Замечание: «CRC» здесь — усечённый SHA-256, 4 байта; имя вводит в заблуждение, но это отдельная косметика.)

**Второй, смежный дефект там же:** `Journal::open` делает seek в конец и берёт `seq = report().records`. При открытии журнала с оборванным хвостом (torn tail) новые записи дописываются **поверх** мусора и «хоронят» старые записи. Путь `run_task_resume` (`loopmod.rs:1364–1393`) оборванный хвост корректно обрезает, а durable-open с `start=None` — нет. Поведение должно быть fail-closed: либо обрезка хвоста с событием quarantine, либо отказ открытия.

**Нюанс правки:** перенос kind внутрь хеша меняет формат записи → это версия HSJ1 → HSJ2, то есть **отдельный ADR** (что делать со старыми журналами: отвергать или мигрировать) + негативный тест (перевернуть байт kind Data↔Commit → walk обязан отвергнуть), который до фикса красный, после — зелёный. По правилу репозитория: пре-регистрация с порогом ДО прогона.

### N6. SSRF-фильтр: литеральный обход через 198.18/15 + окно DNS-rebinding

`bin/net_policy.py:90–91`:

```python
if ip in ipaddress.ip_network("198.18.0.0/15"):
    return   # разрешено БЕЗУСЛОВНО
```

Исключение добавлено под F-0082 (DNS этой машины возвращает 198.19.x для всех доменов), но оно разрешает и **литеральный URL** `http://198.18.0.1/` на любой сети, где перехвата нет, — то есть дыра в фильтре на ровном месте. Правка: исключение 198.18/15 применять только к результату резолва при подтверждённом перехвате (не к литералам), резолв один раз, connect к зафиксированному IP с повторной проверкой. Негативные тесты: литерал 198.18.0.1 обязан получать отказ; симуляция rebinding.

### P1. Плановые этапы — с нюансами из §2

7. **Этап 1.6 (read-only приёмка):** SHA-256 оригинала до/после; извлечение журнала с копии (или чистый экспорт из гостя); несовпадение хеша → UNKNOWN/FAIL; оба скрипта (`accept-run.ps1`, `crash-resume.ps1`); правка текста ADR-0049 отдельной записью. *Пре-регистрация:* порог = хеш равен И журнал парсится; негативный контроль = заведомо грязный образ, оригинал обязан остаться байт-в-байт неизменным. *Приёмка:* негативный тест красный до фикса, зелёный после; e2fsck больше не вызывается на оригинале нигде (`grep e2fsck core-rs/*.ps1` — только по копии).

Затем 3×N04 подряд для проверки флака; гипотезу fsync проверять только после улик. *Приёмка:* искусственно проваленный прогон оставляет журнал+лог; три прогона N04 дают записанный вердикт (стабилен/флакает) с артефактами.

## 6. Что этот обзор НЕ доказывает

- **Не запускалась комната QEMU** (ни один живой прогон задачи): выводы о поведении гостя, флаке N04 и guestfwd — из кода и карточек, не из нового наблюдения.
- **813 тестов VecDHT не перепрогонялись:** числа 143/813 взяты из сообщения коммита `505edd2` (и удалённого блока METRICS); их актуальность на текущем HEAD не подтверждена этим обзором.
- **Lean собран вживую (обновлено после замечания владельца):** `lake build` красный ровно по F-0080; позитивные модули зелёные, негативные контроли отвергнуты как задумано, аксиомы шести теорем чистые. Чего сборка НЕ доказывает: соответствие Lean-модели Rust-коду (граница самого прибора: «доказано свойство модели политики, а не соответствие Rust-кода модели»), работу моста H-0180 и CI-обвязку — она по-прежнему отсутствует.
- **Одна машина:** выводы о DNS-перехвате 198.18/15 привязаны к этому хосту; литеральный обход (N6) — свойство кода, но его эксплуатация на других сетях не измерялась.
- **Обзор только читал:** ни один фикс не применён, ни один гейт не изменён; все «приёмки» выше — критерии для будущей работы, а не выполненные проверки.
- **Зелёные гейты ≠ отсутствие дефектов** (NC-005): 32 гейта и 16 проб ловят только то, для чего написан детектор; находки N1–N11 — прямое тому подтверждение.

## 7. Расшифровка меток (простыми словами)

| Метка | Что значит |
|---|---|
| **F-xxxx** | «Находка/отказ» — карточка зафиксированного дефекта или честного отказа (например, F-0084: канал не поднимается, этап закрыт отказом). Отрицательный результат хранится как результат. |
| **E-xxxx** | Эксперимент: сначала пре-регистрация (что меряем, порог), потом прогон, потом вердикт. |
| **H-xxxx** | Гипотеза — проверяемое предположение с фальсификатором (чем её можно опровергнуть). |
| **C-xxxx** | Утверждение — строка в CLAIMS.md со свидетельством и командой проверки; число без команды результатом не считается. |
| **ADR-xxxx** | Запись решения: что решили, почему, какие альтернативы отвергли. Смена порога/формата — только через ADR. |
| **R1** (в SSRF-R1 и т.п.) | Раунд 1 пре-регистрации эксперимента. |
| **NC-xxx** | NOT-CLAIMED: явный список того, чего мы НЕ утверждаем (защита от перечитывания документа как обещания). |
| **PASS / FAIL / UNKNOWN** | Вердикты приёмки: принято / отказано / данных недостаточно (UNKNOWN — честный третий исход, не «почти PASS»). |
| **HSJ1** | Формат журнала событий ядра (заголовок len+seq+crc+kind); этап 2.1 потребует версию HSJ2. |
