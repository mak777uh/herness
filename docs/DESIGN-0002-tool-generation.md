# DESIGN-0002: автогенерация инструментов и мостов, удобная модели

**Дата:** 16.11.2026. **Статус:** проект. **Основание:** «харнесс пишется от задач» + просьба
сделать автогенерацию безопаснее и прозрачнее, чем в Unharnessed, и понятнее ИИ-модели.
**Связано:** `PROPOSAL-0001-task-written-bridges.md`, `lab/tools/registry.jsonl`,
`lab/tools/contracts.json`, `lab/tools/policy.json`, `bin/closure_probe.py`.

---

## 1. Что уже есть (и чего не хватает)

| артефакт инструмента | где | кто пишет сейчас |
|---|---|---|
| деонтические атомы (право/обязанность, кто, что, условия) | `lab/tools/contracts.json` | человек |
| правила политики (allow/deny, уровень, «почему») | `lab/tools/policy.json` | человек |
| запись реестра (контракт, вход/выход, замыкание, примеры, среда) | `lab/tools/registry.jsonl` | `bin/build_registry.py` из кода |
| тело инструмента | `core-rs/src/loopmod.rs` | человек |
| проверка соответствия кода замыканию | `bin/closure_probe.py` | есть |
| проба гейта (подложенный дефект) | `bin/gate_probe.py` | есть |

**Не хватает трёх вещей:** (1) карточки инструмента — компактного описания, которое читает модель;
(2) генератора, который из карточки делает остальные пять артефактов; (3) лестницы проверок, которая
ведёт от «черновик» до «active» и останавливается на первом красном с точным следующим действием.

---

## 2. Принцип: контракт — источник истины, код — производное

Модель **не пишет Rust**. Модель пишет карточку — JSON с объявленным поведением. Харнесс из неё
делает: атомы контракта, правила политики, запись реестра, скелет тела с уже вставленной проверкой
замыкания, пробу и фикстуры. Тело заполняется **слотами** (что читать, что вернуть, чем обрезать);
свободный Rust — отдельный режим `--freeform`, и он проходит ту же лестницу.

Почему так, а не «пусть модель пишет код»:

- **Диффы читаемы.** Сгенерированный файл отличается от предыдущего версией карточки, а не стилем.
- **Замыкание нельзя расширить по неосторожности.** Карточка объявляет `fs/net/time/mem/bytes`;
  генератор отказывается, если объявленное шире того, что разрешено комнате.
- **Код выбрасываем.** Проверенный контракт важнее реализации: сменили реализацию — карточка и
  доказательства остались, лестница перезапускается.
- **Модели проще.** Один вход (карточка) вместо пяти файлов и знания внутренностей `loopmod.rs`.

## 3. Карточка инструмента (то, что видит модель)

```json
{
  "id": "head",
  "purpose": "вернуть первые N строк файла, не давая прочитать файл целиком",
  "inputs":  {"path": "файл внутри /mnt", "n": "целое 1..200, по умолчанию 10"},
  "outputs": {"lines": "строки с номерами", "truncated": "файл длиннее выдачи"},
  "closure": {"fs": {"read": ["/mnt/**"], "write": []}, "net": [], "time_ms": 100, "memory_mb": 4, "output_bytes": 8192},
  "refusals": ["PATH_OUTSIDE_ROOM", "INVALID_ARGUMENT"],
  "examples": [
    {"args": {"path": "/mnt/CLAIMS.md", "n": 3}, "expect": "первая строка содержит «1: »"},
    {"args": {"path": "/mnt/CLAIMS.md", "n": 0}, "expect": "отказ INVALID_ARGUMENT"},
    {"args": {"path": "/etc/passwd", "n": 3}, "expect": "отказ PATH_OUTSIDE_ROOM"}
  ]
}
```

Правила карточки (проверяются, а не подразумеваются):

1. `closure.fs.read` ⊆ монтирований комнаты (`/mnt/**`); `closure.net` пуст, если инструмент не сетевой.
2. Минимум три примера: норма, граница, **отказ**. Пример без отказа — карточка не принимается.
3. Коды отказа — только из `lab/refusal-codes.json`; новый код = отдельное решение, не побочный эффект.
4. `purpose` — одно предложение, без «быстро/удобно/мощно»: это не проверяемо.

Карточка — это же и **подсказка модели при вызове**: `hs.py tools card head` печатает её сжато
(~300 токенов) вместо чтения реестра и исходников.

## 4. Лестница проверок (с четырьмя исходами)

Каждая ступень печатает `passed | failed | void | not applicable` (терминология взята у marfagenez:
`void` — прибор не различил, `not applicable` — вопрос не стоит).

| ступень | что проверяет | чем |
|---|---|---|
| 1. schema | карточка полна, коды отказа из словаря, примеры трёх видов | `bin/tool_card.py --check` |
| 2. closure | объявленное замыкание не шире комнаты | тот же валидатор + `lab/room.json` |
| 3. policy | правила deny-first, у каждого `why`, нет неявных разрешений | `bin/policy.py --check` |
| 4. compile | скелет и вставленные слоты компилируются | `cargo test --lib` |
| 5. closure-probe | тело не выходит за замыкание | `bin/closure_probe.py` |
| 6. negative | проба с подложенным дефектом ловится | `bin/gate_probe.py --only <id>` |
| 7. examples | три примера дают объявленный результат | `bin/tool_examples.py` |
| 8. registry | запись в реестре несёт контракт, замыкание, примеры, хеш среды | `bin/build_registry.py` |

Ступени 1–3 и 8 идут без сборки → работают в CI. 4–7 — на машине с Rust/комнатой.

Правило остановки: **первый `failed` останавливает лестницу**, печатает причину и `next: <команда>`.
Модель не должна догадываться, что чинить: каждая строка отказа заканчивается действием.

## 5. Мосты — та же схема, другая лестница

Мост описывается карточкой того же вида плюс:

```json
{
  "kind": "bridge",
  "between": ["cell-a", "cell-b"],
  "laws": ["output_is_function_of_input", "no_read_outside_root", "no_net"],
  "proof": {"model": "proofs/Proofs/BridgeGen/<id>.lean", "negative": "proofs/Proofs/BridgeGen/<id>Negative.lean"}
}
```

Лестница моста: `schema → laws ⊆ словарь законов → Lean-модель собирается → аксиомы стандартные →
негативный контроль падает → policy_diff совпадает на фикстурах → регистрация`.

Словарь законов **закрытый** (как коды отказа): `output_is_function_of_input`, `no_read_outside_root`,
`no_net`, `no_write_outside_root`, `token_never_in_output`. Новый закон — отдельное решение с ADR.
Это защита от «композиция взрывает обязательства»: законы композируются механически, потому что их
конечный список.

## 6. Почему модели будет проще (конкретно)

| что мешает модели сейчас | что делаем |
|---|---|
| пять файлов в разных форматах | одна карточка JSON; остальное генерируется |
| «почему отказали» — в тексте гейта | каждая ступень печатает `passed/failed/void/NA` + `next:` |
| нужно знать внутренности `loopmod.rs` | скелет с уже вставленной проверкой замыкания и слотами `TODO(slot)` |
| нет примеров «как правильно» | две золотые карточки: `read` (read-only) и `seal` (read+write+hash) |
| вызов инструмента требует чтения реестра | `hs.py tools card <id>` — 300 токенов, ровно нужное |
| непонятно, что уже есть | `hs.py tools list` — одна строка на инструмент: id, контракт, замыкание |

Ещё два правила, которые снижают цену ошибки:

- **Карточка проверяется до генерации.** Невалидная карточка не создаёт файлов — модель получает
  список замечаний и ничего не ломает.
- **Генерация по умолчанию в `--dry-run`.** Печать плана (какие файлы, какие правила) без записи;
  запись — явным `--write`. Это дешевле, чем откатывать.

## 7. Безопасность и прозрачность

1. **Замыкание не расширяется.** Валидатор сравнивает объявленное с монтированиями комнаты и
   с политикой; расширение — отказ, а не предупреждение.
2. **Deny-first.** Для каждого действия, которого нет в карточке, генерируется `deny` с `why`.
   Отсутствие правила — не разрешение.
3. **Защищённые пути только через генератор.** `lab/tools/policy.json`, `contracts.json`,
   `registry.jsonl` — защищённые пути (`check_autonomy`); ручная правка требует записи в
   `docs/decision-log.md`, генератор пишет её сам.
4. **Шапка происхождения.** Каждый сгенерированный файл начинается с:
   `generated from card <id>@<hash> by toolgen 0.1.0; ladder: schema,closure,policy`.
   Подделать происхождение труднее, чем забыть его.
5. **След решения.** `hs.py tools why <id>` печатает: карточка → правила политики → вердикты проб.
   Это то, чего нет в Unharnessed: там «почему инструмент такой» — вопрос к промпту.

## 8. Первый срез (одна вертикаль)

**Инструмент:** `head` — первые N строк файла, read-only, два кода отказа.

**Что делаем:**
1. `bin/tool_card.py` — схема, валидация, рендер карточки, проверка замыкания против комнаты.
2. `bin/new_tool.py` — из карточки: правила политики (черновик), скелет Rust со слотами и проверкой
   замыкания, проба, фикстуры; `--dry-run` по умолчанию.
3. Тесты: карточка без отказа не проходит; расширение замыкания отвергается; неизвестный код отказа
   отвергается; валидная карточка печатает карточку ≤ 400 токенов.

**Критерий среза:** генератор на карточке `head` создаёт пять файлов в `--dry-run` и ноль файлов при
невалидной карточке; лестница 1–3 зелёная без сборки; ступени 4–7 объявлены как `not applicable`
до появления тела.

**Чего срез не делает:** не пишет тело за модель, не запускает cargo, не трогает `loopmod.rs`.

---

## 9. Что может убить идею

- **Слоты окажутся тесными.** Если половина инструментов требует свободной логики, генератор станет
  тормозом. Мерить: доля инструментов, уложившихся в слоты.
- **Лестница длиннее, чем выгода.** Восемь ступеней на инструмент — это дорого; для мелких
  инструментов часть ступеней должна быть `not applicable` по объявлению, а не по забывчивости.
- **Реестр разойдётся с кодом.** Лечится тем же, чем `policy_sync`: запись в реестре строится из
  кода, а не пишется руками (`build_registry.py` уже так делает).

## 10. Границы

- Это проект, а не решение: ADR появится после первого среза, если срез пройдёт.
- Свободный Rust (`--freeform`) в первом срезе не поддерживается вообще — сначала слоты.
- Мосты в этом срезе только описаны схемой; их генератор — следующий шаг после `PROPOSAL-0001`.
