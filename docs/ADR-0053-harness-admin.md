# ADR-0053. Админ харнесса: отдельный канал, который держит сам харнесс

**Дата:** 01.11.2026. **Состояние:** предложено владельцем, принято к реализации. **Основание:** роль,
которую я выполняю сейчас, находится снаружи; её надо перенести внутрь — но сначала описать.

## 1. Проблема

Сейчас улучшения харнесса появляются так: владелец присылает ссылки и вопросы, я разбираю, решаю,
внедряю. Всё это живёт в одной переписке. Последствия:

- знания о харнессе сосредоточены в одном разговоре, а не в системе;
- находка из другого проекта (например, «шаг тратится на перечитывание») не доходит до харнесса,
  пока владелец не перескажет;
- формат отдачи, правила и приоритеты держатся на памяти (сегодня это уже дважды ломалось).

## 2. Решение: роль «админ харнесса» как отдельный канал

Админ — это отдельная постоянная сессия (канал), чья задача — **сам харнесс**: его качество, правила,
склады, гейты, приоритеты и приём находок от других проектов.

Что админ получает на вход:

| вход | откуда | формат |
|---|---|---|
| находка проекта («застрял там-то», «работает так-то») | другие проекты/сессии | `lab/admin-inbox/<дата>-<слаг>.md` по шаблону |
| вопрос владельца | чат владельца | свободный |
| аудит харнесса | `bin/hs.py selfaudit` | вычисленный отчёт |
| провал гейта/теста | CI, прогоны | вывод команды |

Что админ делает на выходе:

1. **разбирает находку** по циклу §5 `docs/TOP-REVIEW.md` (склад → вопрос → разбор → решение →
   гипотеза → внедрение с контролем);
2. **ведёт склады**: `research/*-INDEX.md`, `lab/adoptions.json`, `lab/owner-preferences.json`;
3. **держит гейты**: следит, чтобы у новых проверок был отрицательный контроль;
4. **обновляет правила** для остальных проектов (что теперь обязательно);
5. **докладывает владельцу** коротко и файлом, а не текстом в чат.

## 3. Границы полномочий (важно)

Админ **может** без спроса: править код харнесса, гейты, тесты, склады, документы; запускать прогоны
в рамках бюджета; заводить гипотезы и отказы.

Админ **не может** без владельца: публиковать наружу; менять физику мира (ядро, состав комнаты);
удалять канонические образы; менять зарегистрированные гипотезы после их проверки; расширять
поверхность моста; менять сами правила автономии.

Это то же разделение, что в `lab/autonomy-rules.json`; админ ему подчиняется наравне с остальными.

## 4. Почему это улучшит работу всех

- находка перестаёт зависеть от того, пересказал ли её владелец: она идёт в inbox по шаблону;
- решение по находке фиксируется в складе решений и действует **для всех** проектов;
- правило без `how`/`check` не принимается (уже гейт), значит улучшение доходит до практики;
- склады становятся общими: `bin/shelf.py search` ищет по всем источникам и решениям сразу.

## 5. Минимальная реализация (первый шаг)

1. `lab/admin-inbox/` — очередь находок с шаблоном (сделано вместе с этим ADR).
2. Проверка формата находки: обязательные поля (что случилось, где, что предлагаю, чем проверю).
3. Правило ответа админа: каждая находка получает статус `принято / отклонено / отложено` с
   причиной и ссылкой на запись в `lab/adoptions.json`.
4. Позже: админ запускается как отдельная сессия харнесса с профилем `admin` и теми же гейтами.

## 6. Что это НЕ решает

- не даёт админу внешних полномочий и не отменяет «ничего наружу без да»;
- не заменяет аудит: админ читает вычисленный отчёт, а не «своё мнение о себе»;
- не гарантирует качество решений: решения по-прежнему проверяются отрицательным контролем.

## 7. Как поймём, что работает

| признак | проверка |
|---|---|
| находки доходят | в inbox появляются записи из других проектов, не только от владельца |
| находки не теряются | каждая запись имеет статус; аудит WARN, если есть записи без статуса |
| правила доходят до практики | новые правила имеют `how` и `check`; гейт «решения» зелёный |
| админ не «сам себе судья» | его собственные изменения проходят те же гейты и аудит |
