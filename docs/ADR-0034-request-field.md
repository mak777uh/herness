# ADR-0034 — Поле запроса: определено / выводится / не определено, и чем закрывается

Дата: 30.10.2026. Статус: **предложено** (не принято, не проверено).
Основано на двух наших репозиториях: `lexspec` (как текст раскладывается на нормы) и `flowguard-spec`
(как из этого получается софт).

## Что взято у lexspec

| механизм lexspec | что переносим |
|---|---|
| `kind: "norm" \| "clause" \| "scenario"` | у части запроса есть **тип**: требование / ограничение / вопрос |
| §4 Hohfeld: восемь позиций | у части запроса есть **модальность**: разрешено / обязательно / запрещено (у нас есть `core/hohfeld.py`) |
| §7 conflict policy | что делать, если две части противоречат |
| **§8 coverage and escapes** | у каждой части есть **покрытие**: что она закрывает и чем закрывается, если не закрыта |
| §9 verdicts (`REFUSED`/`CHECKED`/`CHECKED_ANCHORED`) | у части есть вердикт, а не «вроде разобрались» |
| §10 refusal codes (`S2_HASH_MISMATCH` и др.) с «лечением» | отказ — это код с предписанным действием, а не текст |

Главное, чего у нас не было: **escape** — явное «эта часть не закрыта, и вот канал».

## Что взято у flowguard-spec

| механизм | что переносим |
|---|---|
| «inside a **declared closure**» | у запроса есть объявленная граница: что входит, что нет |
| «if the band is `thin`, the verifier **will refuse a strong verdict**» | сильное утверждение запрещено, если данных мало — порог, а не настроение |
| acceptance thresholds / **kill criteria** | условия остановки записываются заранее, «оптимизировать» их нельзя |
| `check-claims.py`: каждое утверждение типизировано, каждый артефакт прослеживаем | это уже наш `CLAIMS.md`, подтверждение подхода |
| «one command, from schema dump to a verdict» | критерий зрелости цепочки: посторонний воспроизводит одной командой |

## Предложение: поле запроса

На каждый запрос строим структуру из пяти частей:

```json
{
  "closure": "что входит в задачу; что явно вне — и это не обещание",
  "fixed":    [{"part": "…", "source": "сказано в запросе"}],
  "derived":  [{"part": "…", "by": "инструмент|решение", "which": "grep|fetch|ADR-0031"}],
  "open":     [{"part": "…", "channel": "user|experiment|search|peer|refuse", "why": "…"}],
  "conflicts":[{"between": ["part1", "part2"], "policy": "как разрешаем"}],
  "verdict":  "EXECUTE|OPTIONS|CLARIFY|SEARCH|ASK_PEER|REFUSE"
}
```

**Правило:** запрос нельзя выполнять, пока в `open` есть часть с каналом `user` или `refuse`. И наоборот:
если `open` пуст, а `verdict` = `CLARIFY` — это ошибка маршрутизации, а не осторожность.

### Наши типы ответа уже совпадают с каналами

| канал закрытия | наш тип (`core/reply.py`) |
|---|---|
| всё в `fixed` и `derived` | `EXECUTE` |
| выбор из вариантов | `OPTIONS` |
| у пользователя | `CLARIFY` |
| поиском | `SEARCH` |
| у соседа/другой модели | `ASK_PEER` |
| вне объявленной границы | `REFUSE` |

То есть новые сущности не нужны: нужна **запись**, почему выбран тип, и что осталось открытым.

## Что это даёт на практике

1. **Не задаём вопрос, если он уже закрыт инструментом.** Часть `open` с каналом `search`, у которой
   есть `fetch` — закрывается сама. Сейчас мы это решаем «на глаз».
2. **Не выполняем, если открыто у пользователя.** Явное правило вместо вежливости.
3. **Видно, куда ведут инструменты.** `derived` перечисляет, чем именно закрывается: `grep`, `fetch`,
   `ADR`. Это и есть «поле инструментов и решений», о котором говорил владелец.
4. **Противоречие — отдельная часть, а не сюрприз.** Две части запроса, требующие разного, попадают в
   `conflicts` с политикой, а не выясняются в середине работы.

## Кристаллизация цепочки в софт

Цепочку можно превратить в код (ADR-0023), когда выполнены **все** условия:

| # | условие | откуда |
|---|---|---|
| 1 | объявлена `closure` | flowguard |
| 2 | у каждой части есть вердикт или код отказа с лечением | lexspec |
| 3 | все `open` закрыты или имеют детерминированный канал | новое |
| 4 | цепочка воспроизводится **одной командой** посторонним | flowguard (T2) |
| 5 | повторялась ≥ порога из ADR-0023 | наш замер |

Если хотя бы одного нет — это процедура, а не код. «Скорость моделей растёт» не отменяет условия 4:
быстрый код, который нельзя воспроизвести, — это быстрый шум.

## Что нужно проверить, чтобы это стало решением

1. Собрать поле вручную на 10 наших реальных запросах: сколько частей `fixed`/`derived`/`open`, сколько
   раз `verdict` разошёлся бы с текущим поведением.
2. Проверить правило «`open` у пользователя ⇒ не выполняем» на случаях, где мы всё-таки выполнили.
3. Ввести один код отказа с лечением (например, `S2_HASH_MISMATCH`-аналог) и посмотреть, помогает ли.

## Границы

- Это **предложение**, а не принятое решение: ADR-0034 не меняет поведение харнесса.
- Механизмы lexspec и flowguard прочитаны по документам; код не запускался.
- Поле запроса не решает, **как** модель понимает запрос: оно лишь фиксирует результат понимания в
  проверяемой форме.
