# ADR-0022 — Маршрутизация: правила сейчас, классификатор потом

Дата: 29.10.2026. Статус: принято. Дополняет ADR-0020 и ADR-0021.

## Развилка, которую надо решить первой

Мы смешивали два разных предсказания:

| что предсказываем | откуда метка | чем полезна |
|---|---|---|
| **тип задачи** (разведка, аудит, правка…) | журналы: какие инструменты и шаги были | выбор набора инструментов |
| **уровень** (L0…L2) | **только эксперимент**: прогнать на разных уровнях и увидеть, где хватило | выбор строгости |

Из журналов уровень не выводится: агент всегда пользуется инструментами, даже когда задача
закрылась бы без них. Поведение говорит «что делали», а не «что было достаточно».

Отсюда решение: **метки уровня берём из экспериментов, метки типа — из журналов.**

## Решение

| что | сейчас | потом |
|---|---|---|
| выбор уровня | **правила в коде** (прозрачные, отлаживаемые) | классификатор, если правила провалятся |
| определение типа | правила + журналы для валидации | классификатор типов (ADR-0021) |
| «всегда L1» | **контрольный участник**, а не забытый вариант | то же |

Порядок: **правила → замер промахов → и только по промахам классификатор**. Не наоборот: обучать
модель, не зная, где правила ошибаются, значит не иметь с чем сравнивать.

## Правила выбора уровня (черновик)

| признак (наблюдаемый) | уровень |
|---|---|
| нет действий, только ответ | L0 |
| нужен факт из файлов или сети | L1 |
| результат должен пережить разговор: отчёт, аудит, публикация наружу | L2 |
| действие необратимо: деньги, публикация, удаление | L2 + подтверждение человека |
| задача длиннее одного прогона, нужна передача между узлами | L3 (позже) |

Правила намеренно грубые: их ценность — в прозрачности и в том, что их промахи видно.

## Как мерить промахи правил

1. Взять 30 задач из журналов, по 5 на тип.
2. Прогнать каждую на уровне, который назначили правила, и на уровень ниже.
3. Зафиксировать: хватило ли, чем закончилось, сколько стоило.
4. Промах правила = «назначили L2, хватило L1» (перестраховка) или «назначили L1, не хватило» (недобор).

Метрика: доля промахов каждого рода. Недобор опаснее перестраховки: он даёт ложный результат.

## Когда вводить классификатор

Только если выполнено всё:

1. на 30 задачах доля **недобора** ≥10 % — правила пропускают риск;
2. есть корпус ≥100 размеченных типов (ADR-0021);
3. классификатор обгоняет правила на том же корпусе.

Иначе правила остаются: они дешевле, объяснимы и не требуют модели.

## Что это не доказывает

Что журналы дают достаточно меток типа. Что 30 задач хватит, чтобы увидеть редкие промахи. Что
правила не окажутся хуже классификатора просто из-за грубости.

## Замер: правила почти не отличаются от «всегда L1»

На 58 реальных запросах из журналов (`python bin/hs.py plan --compare`):

| исход | запросов |
|---|---|
| правила не распознали → L1 | 48 |
| правила дали ровно L1 | 6 |
| правила подняли выше L1 | 4 |
| правила опустили ниже L1 | 0 |
| **отличаются от L1** | **6,9 %** |

Вывод: «всегда L1» — сильная базовая линия. Таблица уровней даёт выигрыш не более чем на 7 %
запросов, и это **потолок**, а не измеренная польза.

## Уточнение решения

Правила сохраняем **только как повышение по риску** (необратимые действия: деньги, публикация,
удаление), потому что там цена ошибки несопоставима со стоимостью журнала. Понижение до L0 из
правил убираем: на реальных запросах оно ни разу не сработало и требует уверенности в намерении,
которой у правил нет.

Итого: **по умолчанию L1; повышение — по риску; понижение — по желанию владельца, а не по правилу.**

## Что добавили после веера пяти моделей (29.10.2026)

Проверены первоисточники: When2Tool (arXiv 2605.09252), REFLEX/Jev (2609.26532), CASEL (2610.36570).
Сводка — `research/DIGEST-routing.md`. Три изменения в замере и в устройстве L2:

1. **Контрольный срез без инструментов.** В замер добавляются задачи, где инструмент не нужен:
   иначе «всегда L1» выглядит хорошо именно на них, и перестраховка не видна.
2. **Предел инструментов на шаг — не больше 7.** Выше 4–10 выбор деградирует (подтверждено работами).
3. **Счётчик шагов — главная метрика стоимости.** Число шагов объясняет цену сильнее, чем токены.

И уточнение про L2: это не «задача целиком в строгом режиме», а решение **на каждый вызов** —
direct / verify / sandbox / clarify / approve / abstain (меню из CASEL). Уровень задаёт рамку,
режим выбирается по последствиям конкретного вызова.
