## 0. Проект в одном экране

`herness` — харнесс, который должен **безопасно генерировать собственные
инструменты**. У него есть:

- **первая комната** (room zero) — защищённый корень доверия: конституция K1–K11,
  ключи, политика, реестр, допуск;
- **инструменты** — сначала шесть native (уже внутри), затем сгенерированные;
- **карточка инструмента** — декларация вида, входов/выходов, эффектов, лимитов,
  отказов, provenance; карточка не является доказательством поведения;
- **admission** — подписанный владельцем манифест, привязывающий права к точным
  байтам card/source/binary/template/deps/toolchain/policy/room;
- **promoter** — отдельный host-side процесс, который проверяет и продвигает
  candidate; он не получает голос владельца;
- **комната** — QEMU/KVM-гость без сети, host mounts и лишних устройств, с
  наблюдением за поведением;
- **мосты** — единственный способ выйти наружу; мост дальше может иметь свои
  правила, если не нарушает конституцию.

Текущая стадия: **до генератора**. Есть шесть native-инструментов, черновик
`tool-card-v1`, открытая пре-регистрация среза `head`, измерения QEMU/seccomp и
пять ответов R7. Ни одна сгенерированная карточка ещё не допущена; Rust-срез
`file_read_stream` не написан; admission в коде не проверяется.

**Что считается успехом v0:** один сгенерированный read-only инструмент
`file_read` проходит card → policy → room → observation → owner admission, и
отчёт честно отделяет свидетельство от доказательства. **Не** успех:
«модель написала код, он запустился».

## 1. Конституция: рамка, которую нельзя молча менять

Полный текст: [`docs/CONSTITUTION-v0-2026-11-16.md`](https://github.com/mak777uh/herness/blob/c63f3b8f8968ccf0fc7d3b03ae8c03f1e527519f/docs/CONSTITUTION-v0-2026-11-16.md).

| id | имя | смысл в одном предложении |
|---|---|---|
| K1 | `no_read_outside_root` | читать можно только внутри объявленного корня; выход — отказ |
| K2 | `no_write_outside_root` | писать можно только внутри объявленного корня; выход — отказ |
| K3 | `no_net_except_declared` | сеть только к объявленному мосту; прямого выхода нет |
| K4 | `bounded_resources` | время, память, вывод, процессы, открытые fd — ограничены и измеряются |
| K5 | `explicit_refusal` | отказ явный, с кодом; молчаливый пропуск запрещён |
| K6 | `no_secret_outside_protected_space` | секрет не выходит за защищённое пространство; v0 fail-closed |
| K7 | `deterministic_output` | при тех же входах и окружении — тот же вывод |
| K8 | `provenance` | у результата есть прослеживаемое происхождение |
| K9 | `composition_preserves` | композиция сохраняет K1–K11; без доказательства — отказ |
| K10 | `no_self_modification` | инструмент не меняет политику, реестр, ключи, конституцию |
| K11 | `admission_to_protected_space` | чужой код входит в защищённое пространство только по допуску |

**Важное правило про native.** Конституция говорит прямо: «Для
native-инструмента K11 не применяется (они уже в системе), но K1–K10
применяются» (строки 94–95; там же §211). Это не лазейка: native-инструменты
остаются недоверенными в смысле проверки поведения, но отдельный admission-вход
для них не требуется. Любое предложение «применить K11 к native» — поправка к
конституции, а не деталь реестра.

**Четыре уровня (дизайн, не конституция).** Для допуска используется
монотонность:

```
observed_code_effects ⊆ card_effects ⊆ approved_capabilities ⊆ room_ceiling
policy_allow_for_tool == card_effects
card_effects ∩ policy_deny = ∅
```

Пустые массивы означают «нет эффекта», а не wildcard. Запрет сильнее
разрешения; кто не назван — тот не может.

## 4. Что показал R7: согласие и развилки

Синтез: [`docs/R7-SYNTHESIS.md`](https://github.com/mak777uh/herness/blob/c63f3b8f8968ccf0fc7d3b03ae8c03f1e527519f/docs/R7-SYNTHESIS.md).
Сырые ответы: [`docs/research/external/README.md`](https://github.com/mak777uh/herness/blob/c63f3b8f8968ccf0fc7d3b03ae8c03f1e527519f/docs/research/external/README.md).

Пять ответов (A, B, C, D, E) сходятся в следующем:

1. канон семантики — Rust; Python не выдаёт допуск;
2. `file_read_stream` читает сырые байты с жёстким потолком; без
   `BufReader::take`/`read_to_string`; EOF-зонд сверх бюджета запрещён; частичная
   строка не выдаётся; `truncated`/`stop_reason` обязательны;
3. комната — WSL2 + KVM, `microvm`, без сети и host mounts; TCG — только
   симуляция; один `-accel kvm` без fallback;
4. наблюдение — измерение, а не доказательство; «нет событий» — не зелёный;
   self-report инструмента не считается независимым;
5. owner-ключ подписывает admission; recovery не подписывает admission;
6. `active` — производный предикат, журнал append-only; генератор пишет только
   candidate; registry пишет только promoter;
7. admission привязан к точным байтам (JCS, домен, digest), проверяется на хосте
   до запуска;
8. генератор — только после зелёного ручного `head`; held-out и пороги
   замораживаются до прогона; авто-approval нет;
9. `K9_proven` в v0 запрещён; `K11_admitted` ≠ «безопасен»;
10. при нескольких нарушениях вычисляются все, выдаётся один primary; K11
    первым; для пути вне корня класс данных не запрашивается.

Расходятся: runtime-роль валидатора; точная таблица S02 (EOF, счётчики,
граница, CRLF, `output_cap`); механизм seccomp и модель процессов; механизм
наблюдения и уровень притязания; топология ключа и recovery; судьба legacy-шести
и `search`; объём пилота; приоритет отказов; формат статусов; детали манифеста.

## 5. Вопросы

### R8-Q1. Канон карточки и runtime-проверка (F01)

**Зачем.** От этого зависит, что именно проверяет promoter, что считается
`active` и можно ли подменить карточку после допуска.

**Дано.** `tool_card.py`/`card_atoms.py` работают со старым форматом; новая схема
`tool-card-v1` — draft; draft с нулевыми provenance digest проходит форму; в
Rust нет семантического валидатора карточки. Пять ответов R7 выбрали Rust-канон,
но разошлись в runtime-роли: полная семантика при загрузке (C), проверка admission
(A), только digest-привязка (E), доверие подписанному манифесту (D), не
фиксировано (B).

**Развилка.**

- (a) Rust-валидатор только при генерации/приёме; runtime доверяет подписанному
  манифесту и проверяет только digest.
- (b) Rust-валидатор при приёме **и** при каждой загрузке карточки (runtime
  revalidation).
- (c) Rust-валидатор при приёме; runtime проверяет только то, что digest
  card/binary/template совпадает с admission.
- (d) отдельный «тонкий» runtime-валидатор для подмножества инвариантов (каких
  именно — назови), полная семантика — на хосте.

**Что нужно.**

1. Выбери вариант и назови **точный список правил сверх JSON Schema** (ID
   правила, что запрещает, положительный и отрицательный пример). Покрой как
   минимум: непустой scope по kind; запрет wildcard/`..`/NUL/абсолютных
   сегментов; `process_spawn=false`; `max_bytes_read` ≤ потолка; допустимые
   data classes; коды отказов только из словаря; `examples` с ok и refusal;
   `provenance` с ненулевыми digest; `kind ↔ template ↔ effects`; `output_bytes`
   vs `max_bytes_read`.
2. Опиши, что происходит при **подмене файла карточки после допуска**: кто и на
   каком шаге это обнаруживает, какой код отказа, что видит модель.
3. Опиши, как Python остаётся ненормативным (роль, что он не может разрешить).
4. Предложи форму и размер конformance-корпуса (векторы + мутанты), достаточного
   для v0, и критерий, при котором корпус считается недостаточным.

**Проверка.** Карточка с лишним `fs_write` должна быть отвергнута; карточка с
чужим `binary_digest` — отвергнута; ручная правка карточки после допуска не

3. Новые коды: для UTF-8, missing, type (directory/FIFO/device), output overflow,
   search skip. Для каждого — имя, смысл, где используется. Если достаточно
   detail-поля — скажи, почему код не нужен. Если нужна поправка словаря —
   назови версию и правило.
4. Что видит модель в каждом из 14 случаев R8-Q2; какой код primary.
5. Как порядок взаимодействует с `K5` (явный отказ) и `K6` (не выдавать
   содержимое). Приведи пример, где неверный порядок маскирует утечку.

**Проверка.** Для каждого кода есть положительный и отрицательный тест; порядок
не зависит от реализации; `search` skip не выглядит как «0 найдено» без
оговорки.

### R8-Q9. Лестница статусов и две оси (F04)

**Зачем.** Статус — язык отчётов и гейтов. Если смешать свидетельство и
полномочие, `K11_admitted` начнёт означать «безопасен».

**Дано.** R7: 4 ступени (D: `schema_valid → policy_checked → slice_passed →
admitted`), 5 (B: `card_valid → policy_checked → room_run_passed →
observed_within_card → K11_admitted`), 6 (A: `declared → schema_validated →
semantic_validated → policy_checked → K11_admitted → runtime_observed`; E:
`declared → schema_checked → policy_checked → contract_checked →
runtime_checked → K11_admitted`), или две оси (C: evidence + authority). Все
запрещают `K9_proven`; все говорят, что `K11_admitted` ≠ «безопасен».

**Что нужно.**

1. Выбери представление: лестница или две оси. Если лестница — точные имена,
   порядок, что каждая ступень **утверждает** и **не утверждает**.
2. Кто вычисляет статус, из каких артефактов, где он хранится (или всегда
   вычисляется). Что сбрасывает ступени при изменении digest/policy/room.
3. Может ли карточка быть `admitted` без runtime? Может ли `runtime_checked`
   быть без admission? Ответь для каждого варианта.
4. Как в отчёте выглядит «доказано / наблюдено / допущено / неизвестно»;
   приведи пример одной строки.
5. Как запрещённый `K9_proven` не просачивается через синонимы
   (`composition_verified`, `proven`, `safe`). Предложи проверку формулировок.

**Проверка.** По схеме можно автоматически отличить «допущен» от «проверен»;
никакая комбинация статусов не даёт «K9 доказан».

### R8-Q10. Admission-манифест: точные байты и проверка (A01)

**Зачем.** Подпись не тех байтов или проверка пути вместо fd обесценивает
admission. Сейчас кода нет; решение определяет схему и verifier.

**Дано.** Нужны JCS (RFC 8785), домен, SHA-256, detached-подпись, exact-byte
binding, host-side promoter, offline owner, anti-replay. R7 расходится в полях,
домене, формате подписи, trust anchor, Linux/Windows TOCTOU. `seal`/`netprobe`
сейчас сами запускают себя через `Command::new`, хотя карточка обещает
`process_spawn: false`.

**Что нужно.**

1. Полный список полей манифеста с типами и обязательностью: tool id, card
   digest, source digest, binary digest, template digest, deps, toolchain, policy
   digest, room profile digest, schema digest, key id, epoch, seq, issued_at,
   expires_at, prev digest, approvals, evidence. Что **не** входит и почему.
2. Что именно подписывается: JCS байты, домен, namespace, hash. Покажи
   псевдокод `sign` и `verify` без библиотеки-специфики; назови, где хранится
   канонический JSON и как проверяется `stored == JCS`.
3. Как promoter проверяет манифест до запуска: порядок шагов, что делает при
   расхождении, какой код, что логирует. Как runtime проверяет, что запускает
   именно подписанные байты.
4. Linux TOCTOU: FD/`execveat`/`memfd`/`F_SEAL_*` — выбери и объясни, что
   закрывает окно, а что остаётся. Windows: handle + hash + ACL или отказ от
   исполнения; назови остаточное окно.
5. Анти-откат: epoch/seq/prev/revocation; кто пишет состояние; что происходит
   при копии каталога и откате часов.
6. Что делать с `seal`/`netprobe`, которые сами запускают процесс: считать
   `process_spawn: true` и менять схему, переписать их в процессе, или исключить
   из v0? Ответь явно.

**Проверка.** Манифест с изменённым одним байтом card не проходит; манифест,
подписанный не тем доменом, не проходит; запуск по пути вместо fd/handle не
считается доказанным.

### R8-Q11. Независимые дефекты и порядок починки (AUDIT)

**Зачем.** Часть дефектов не зависит от развилок и может быть починена раньше.
Нужен приоритет, минимальные диффы и тесты, без ослабления гейтов.

**Дано.** Проверенные дефекты:

- Rust `POLICY` 14 vs `policy.json` 19; пять `implied` deny с `!` не
  реализованы; `resource_matches` не понимает `!`.
- `read`: карточка 8192, код 24 KiB; `read_to_string` после `metadata` —
  TOCTOU и чтение целиком.
- `write`: `O_TRUNC` противоречит Q1 create-new/no-overwrite; нет `resolve_in`;
  policy проверяется на ненормализованном пути.
- `search`: молчаливый пропуск нечитаемых файлов при подсчёте `scanned`.
- `head`: две карточки (legacy и draft), `card_atoms` проверяет только legacy.
- `max_processes` не проверяется runtime; `seal`/`netprobe` сами запускают
  процесс; `run_tool_g` не проверяет admission.
- `write_beneath` без `NO_XDEV`; `NO_MAGICLINKS` не нужен явно.

**Что нужно.**

1. Какой источник истины для policy: `policy.json`, Rust `POLICY`, или
   генерация одного из другого? Что делать с `!` и `implied`? Как проверить, что
   deny не стали мёртвыми?
2. Приоритет починки: что раньше — policy drift, `O_TRUNC`, `MAX_READ`,
   `search` skip, две карточки, `max_processes`, self-exec, admission? Почему.
3. Для каждого пункта — минимальный дифф (файл/функция/поведение), тест,
   негативный контроль и риск регрессии. Без «переписать всё».
4. Какие ещё дефекты ты видишь в снимке, которых нет в списке? Дай путь,
   строку, воспроизведение и ожидаемый код. Не выдавай догадку за факт.
5. Что из этого **нельзя** чинить до решения Q11–Q18, потому что закрепит
   неверную семантику?

**Проверка.** Каждый дифф можно применить отдельно; ни один не ослабляет
существующий гейт; у каждого есть тест, который падает до и проходит после.

## 6. Формат ответа

Для каждого вопроса — блок:

```
## R8-QN
DECISION: <один вариант или точная конструкция>
COMMITMENTS: <что именно фиксируем: поля, коды, команды, формулы>
REJECTED: <что отвергнуто и почему>
EVIDENCE: <файл:строка/прогон/man-страница; что проверено, что нет>
RESIDUAL RISK: <что остаётся и как это обнаружится>
UNVERIFIED: <что не открывал/не запускал>
```

Требования:

- помечай `FACT` (проверено), `ASSUMPTION` (не проверено), `RECOMMENDATION`
  (совет); не смешивай;
- для таблиц — заполняй все ячейки, не оставляй «зависит» без условия;
- для команд — одна команда, а не фрагменты; placeholders в `<...>`;
- для кодов — имя из словаря v2 или явное предложение новой версии;
- ссылки — на commit `c63f3b8`, а не на `main`;
- если вариант требует поправки конституции или решения владельца — скажи это
  отдельной строкой `OWNER_DECISION_REQUIRED`;
- не предлагай ослаблять порог, гейт или пре-регистрацию; если считаешь порог
  неверным — предложи новый **до** данных, с обоснованием;
- не утверждай `K9_proven` и не используй его синонимы;
- не запрашивай секреты, ключи, токены и не предлагай действий с сетью.

**Объём.** До ~400 слов на вопрос, не считая таблиц и кода. Если вопрос
требует больше — вынеси детали в приложение, но решение должно быть в блоке.
