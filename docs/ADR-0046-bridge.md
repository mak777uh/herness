# ADR-0046. Мост выхода: свой минимальный, потому что готовый держит ключ в чужой цепочке

**Статус:** принято 31.10.2026. Закрывает выбор B1/B2 в пользу **B2** и решает «свой мост или
готовый шлюз» в пользу **своего**.

## Что проверено по первичным источникам (не по пересказу)

| факт | источник | чем подтверждено |
|---|---|---|
| LiteLLM скомпрометирован: 21.10.2026 в Docker и PyPI уехал `v1.107.0` со скомпилированным вредоносным кодом, который крадёт учётные данные; жил ~2 часа; подпись cosign перевыпускали | собственный блог вендора | тело страницы, `evidence/objects/74a0a32d…` |
| Codex: HTTP-прокси `127.0.0.1:3128`, SOCKS5 `127.0.0.1:8081`, на Windows диапазоны 3128–3159 и 8081–8112 | README `codex-rs/network-proxy` | тело, `evidence/objects/3f804967…` |
| Agent Router (бывш. Envoy AI Gateway) существует, Apache-2.0, «open source control plane… powered by Envoy», OpenAI-совместимый | README проекта | тело, `evidence/objects/a08d6fe0…` |

Три прохода по P23 разошлись в выводах («готового нет» / «LiteLLM подходит» / «Agent Router
перспективнее»), но в фактах сошлись: **все готовые кандидаты требуют Docker/WSL на Windows, имеют
свежий CVE или статус RC/beta, а главное — они держат ключ провайдера**. У LiteLLM это уже
закончилось компрометацией релиза.

## Решение

**B2 + свой мост.** Комната говорит по HTTP с `127.0.0.1:<порт>`; мост на хосте проверяет локальный
токен, подставляет ключ провайдера и уходит по HTTPS.

Реализация: `bin/bridge.py` (~200 строк, только стандартная библиотека).

Почему свой, а не готовый:

1. **Ключ.** Мост — единственный компонент, который держит ключ. Готовый шлюз тянет чужую цепочку
   поставки ровно туда, где лежит ключ; у LiteLLM это уже сработало как инцидент.
2. **Ноль криптографии своего кода.** TLS делает стандартная библиотека хоста. Мы не пишем ни
   шифрование, ни разбор сертификатов — только пересылку JSON.
3. **Форма проста.** Один провайдер, один клиент: `POST /v1/...` с токеном → `POST` провайдеру с
   ключом. Всё остальное (бюджеты, виртуальные ключи, БД) нам не нужно, а именно оно и приносит
   CVE.
4. **Обратимость.** Мост — это endpoint. Если позже понадобится готовый шлюз, он встаёт на то же
   место без изменения комнаты.

## Обязательства, которые из этого следуют

- **DNS не нужен**: мост задан адресом, комната не резолвит имена — проблема C-0145 не возникает.
- **Fail-closed**: нет моста — нет модели. Комната не имеет прямого маршрута наружу (правило C-0141
  и отсутствие DNS это обеспечивают).
- **Журнал без содержимого**: по образцу аудита Codex — решение и адрес да, тела и заголовки нет.
- **Токен клиента** — не аутентификация ради красоты: loopback сам по себе не защищает, если к
  порту может постучаться другой процесс.

## Что мост проверяет (и это проверено тестами)

7 тестов: без токена — 401 и провайдер не тронут; с токеном — 200 и провайдер видит **настоящий**
ключ, а не локальный; путь вне `/v1` — 404 без пересылки; в журнале нет ни тела, ни ключа, ни
токена; отпечаток токена есть; без `HS_BRIDGE_KEY` мост не стартует; `http://` upstream отвергается.

## Чего это не решает

- Мост не заменяет политику: он не ограничивает модель и не считает деньги. Если понадобится —
  это отдельный слой, и его надо будет делать явно.
- Модель ответа по-прежнему не проверяется: мост — транспорт, а не свидетельство.

## Границы

- Замеры: только тесты моста. Ни один готовый шлюз **не устанавливался** — сравнение идёт по
  документации и инциденту, а не по опыту эксплуатации.
- «Agent Router перспективнее» — мнение одного из проходов, не проверенное; в ADR он остаётся
  альтернативой, а не рекомендацией.


## Проверено вживую (C-0148)

Комната (QEMU, наше ядро 6.18.60 с сетью) → мост на хосте → заглушка провайдера:

```
цикл: шагов 0, вызовов 0, событий 3, журнал 4 записей, коммитов 1, статус done, порядок ok
модель: 23 байт, начало: DONE проверено
журнал моста: {"status": 200, "bytes_in": 68, "bytes_out": 201, "token": "373526ea1ee1"}
```

То есть весь путь работает, а в журнале моста нет ни тела, ни ключа — только отпечаток токена и
размеры.

## Что этим снимается

Три цены B1, которые я считал неизбежными, исчезли:

| цена B1 | почему исчезла |
|---|---|
| +1,24 МБ на rustls | TLS заканчивается на мосту; в комнате plain HTTP |
| C-тулчейн под musl для `aws-lc` | крипто в комнату не едет вовсе |
| DNS (C-0145: падает под запретом UDP) | комната знает мост по адресу и имён не резолвит |


## Провайдер подключён (C-0149, C-0150)

Подписка opencode go, модель `deepseek-v4.1-flash`. Что выяснилось по факту, а не по документации:

| попытка | результат |
|---|---|
| zen `/v1/models` | 200, 37 моделей (в том числе `deepseek-v4.1-flash`) |
| zen `/v1/chat/completions`, платная модель | **402 Insufficient account funds** |
| zen, `-free` модель | **429 FreeUsageLimitError**: бесплатные модели только в клиенте OpenCode |
| go `/inference/go/openai/v1/chat/completions` без сессии | **400 MissingSessionID** |
| то же с `x-opencode-session` и браузерным UA | **200**, ответ модели за 1,7–3,6 с, `billing_source=go`, `cost 0` |

Значит мост обязан добавлять `x-opencode-session` (новый UUID на запрос) и браузерный User-Agent —
иначе провайдер отвечает до модели. Это записано в `bin/bridge.py` с пояснением, зачем.

Ключ лежит вне репозитория (`C:/111/env/secrets/`, отпечаток `d76a933a121c`); в комнату он не
попадает — она знает только локальный токен моста.

## Первый настоящий прогон в комнате (C-0150)

```
цикл: шагов 1, вызовов 1, событий 7, журнал 8 записей, коммитов 1, статус done, порядок ok
модель: 77 байт, начало: DONE seal ok d105fb5d1c0ce17b09f25aba9e0
```

Модель сама выбрала `TOOL seal /method.md`, инструмент исполнился в комнате под песочницей, затем
модель закончила `DONE` с хешем печати. Это первый случай, когда цикл в гостевой системе **думал
снаружи, а действовал внутри**.
