## Что стоит добавить: по приоритету

### 1. Session types — проверка последовательности вызовов инструментов

**Почему нам:** у нас есть протокол `TOOL` / `DONE` / `BLOCKED` / `NO-WORK`. Сейчас он
проверяется **разбором строки**, но не проверяется **последовательность**.

**Что это даёт:** запрет недопустимых переходов до исполнения. Например:
- `DONE` не может быть первым шагом (нечего завершать);
- `TOOL` после `DONE` — ошибка;
- `BLOCKED` без причины — ошибка.

**Цена:** дни. Модель — конечный автомат из 4 состояний, доказательство в Lean.

**Что докажем:** «из любого состояния достижимо `DONE` или `BLOCKED`, и `DONE` не может быть
первым».

### 2. Assume-Guarantee — независимая проверка частей

**Почему нам:** у нас три уровня (политика, посредник, замыкание). Сейчас они проверяются
**вместе**. Assume-Guarantee позволяет проверять **каждый отдельно** с предположениями о других.

**Что это даёт:** если политика изменилась, не надо перепроверять замыкание — достаточно проверить,
что предположение выполнено.

**Цена:** недели. Нужно формализовать предположения.

**Что докажем:** «если посредник выполнил свою гарантию, а политика — свою, то система безопасна».

### 3. Hyperproperties — независимость результата от секрета

**Почему нам:** у нас есть токен моста и ключ провайдера. Надо доказать, что **токен не влияет на
наблюдаемый вывод**.

**Что это даёт:** формальное доказательство, что ключ не утекает через ответ.

**Цена:** недели. Нужна модель двух исполнений с разными секретами.

**Что докажем:** «два исполнения с разными токенами дают одинаковый ответ».

### 4. Kani — bounded model checking для Rust

**Почему нам:** наш код на Rust. Kani проверяет переполнения, panic, `unsafe`.

**Что это даёт:** находит ошибки, которые тесты не ловят.

**Цена:** дни (установка + прогон). Но **ограничен глубиной** для циклов.

**Что проверим:** `resolve_in`, `policy_allows`, `resource_matches` — нет ли panic на граничных
входах.

### 5. Runtime verification — проверка трассы против свойства

**Почему нам:** у нас есть журнал. Можно проверять его против **временного свойства**.

**Что это даёт:** «агент не может объявить успех без опоры» — проверяется на живой трассе.

**Цена:** дни. Свойство — LTL-формула, проверка — по журналу.

**Что проверим:** «если `DONE`, то перед ним был `claim/anchored`».

### 6. Bisimulation — эквивалентность старой и новой реализации

**Почему нам:** мы меняем код (например, `HISTORY_MAX` 12→6). Надо доказать, что поведение
не изменилось там, где не должно.

**Цена:** недели.

**Что докажем:** «посредник до и после правки ведёт себя одинаково на всех входах».

## Что НЕ стоит брать

| метод | почему |
|---|---|
| **Rocq, Isabelle, Agda** | у нас уже Lean; второй доказатель — двойная работа без выигрыша |
| **F\*** | нужен для криптографии, у нас её нет |
| **Dafny, SPARK, Frama-C** | для C и Ada; у нас Rust |
| **TLA+, Alloy** | для распределённых систем; у нас одна комната |
| **PRISM, UppAal** | вероятности и сроки; у нас детерминированная комната |
| **separation logic** | для ручного управления памятью; у нас Rust с borrow checker |
| **neural network verification** | у нас нет своей модели |
| **cryptographic proof assistants** | у нас нет своей криптографии |

## Главное из предупреждения

> «Формальная верификация не означает "программа корректна во всех смыслах". Она доказывает
> соответствие **именно той спецификации**, которую вы формализовали; ошибки, пробелы или неверные
> допущения в самой спецификации остаются вне доказательства.»

**Это то же, что мы записали в `docs/VERIFICATION-SPEC.md`:** доказано свойство модели, а не
соответствие кода модели.

**И то же, что говорит книга (стр. 268):** описание — не описываемое.
