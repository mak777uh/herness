# План изменений: что делать дальше и почему

**Дата:** 08.11.2026. **Основание:** полный анализ репозитория (`research/outputs/repo-analysis.txt`),
76 блоков инсайтов по книге (`research/book/INSIGHTS.md`) и из первых принципов.

## Что есть сейчас

| | |
|---|---|
| **части** | 4 репозитория, 2072 файла, 37 МБ, 1152 коммита |
| **код** | Rust 4270 строк, Python 19288 строк |
| **проверки** | 30 проб и аудитов, 51 тест Rust, 12 теорем Lean |
| **данные** | 280 утверждений, 69 отказов, 17 правил политики, 19 кодов отказа |

## Что показал анализ: три настоящих проблемы

### 1. Python в 4,5 раза больше Rust — и это не код продукта

**19288 строк Python против 4270 строк Rust.** Но Python — это **проверки**, а не продукт.
Продукт — Rust. Проверки разрослись до размера, при котором их самих надо проверять.

**Принцип из книги:** «улучшение — чаще удаление». Через отрицание приходят к положительному.

**Что делать:** найти проверки, которые дублируют друг друга или не находят ничего нового.
Удалить. Оставить те, которые ловят то, чего не ловят другие.

### 2. Агент работает в образе, а не в факте

**`HISTORY_MAX` уменьшен с 12 до 6, но `LAST_RESULT` остался 4000 символов.**

Из книги (стр. 351, 257): **образ создаётся при невнимательности**, и **контекст — это образ**.
Агент видит не результат, а его обрезанную часть — и достраивает образ.

**Что делать:** проверить, что обрезка до 4000 символов не режет нужное. Если режет — увеличить
или отдавать по частям. Это **прямая причина 6 провалов чтения из 10**.

### 3. Ноль внешних пользователей — это отсутствие ядра

Из книги (стр. 13–14): **новое не возникает из массы любопытных, а из нескольких, кто идёт до
конца**.

**Что делать:** найти одного человека. Это меняет оценку по рубрике полезности сильнее, чем
что-либо ещё.

## План: пять шагов, по порядку

### Шаг 1. Починить чтение (самое слабое место)

**Почему первым:** чтение провалилось **6 из 10** — самый частый тип задачи.

**Что делать:**
1. Проверить, что `read` отдаёт нужное место. Сейчас `MAX_READ = 8 КиБ` — возможно, мало.
2. Проверить, что `LAST_RESULT = 4000` символов не режет ответ.
3. Прогнать серию из 20 задач чтения и сравнить с 4 из 10.

**Критерий успеха:** чтение ≥ 7 из 10.

### Шаг 2. Сократить проверки

**Почему вторым:** 19288 строк проверок — это груз, а не сила.

**Что делать:**
1. Составить список всех проверок и того, **что каждая ловит**.
2. Найти дубли: две проверки, ловящие одно и то же.
3. Удалить дубли. Оставить те, которые ловят уникальное.

**Критерий успеха:** число строк Python уменьшилось, число пойманных дефектов не уменьшилось.

### Шаг 3. Прогнать аудит гейтов на «видит или защищает»

**Почему третьим:** из книги (стр. 394) — **гейт, который ищет безопасности, будет поддерживать
беспорядок**.

**Что делать:**
1. Вопрос добавлен в `gate_audit.py`. Прогнать.
2. Найти гейты, которые защищают себя.
3. Для каждого: усилить или убрать.

**Критерий успеха:** ни один гейт не защищает себя.

### Шаг 4. Доказать отношения между частями

**Почему четвёртым:** это ваша формулировка — **части взаимозаменяемы, если отношения доказаны**.

**Что делать:**
1. Определить **контракт части**: что часть обязана объявить (входы, выходы, границы, доказательства).
2. Определить **мост между частями**: как две части соединяются.
3. Доказать в Lean: **если пулы законов несовместимы, мост не соединяется**.

**Критерий успеха:** три теоремы о мосте между частями.

### Шаг 5. Найти одного внешнего пользователя

**Почему последним:** без шагов 1–4 нечего показывать.

**Что делать:**
1. Собрать пакет: README, ограничения, архив.
2. Найти одного человека с реальной задачей.
3. Пройти с ним до конца одной задачи.

**Критерий успеха:** один человек, который сказал «это сработало» или «это не сработало, и вот
почему».

## Будущее: P2P-поиск в сети

**Отдельный Rust-модуль в харнессе** (`core-rs/src/p2p/`): семантические эскизы, маршрутизация
с бюджетом lookup'ов, anchor-комитеты. Основание — ресёрч семантической маршрутизации
(SemDHT, Semord, Semantica) и то, что уже есть в `VecDHT` (грубый квантователь, 64 шарда).

**Подробно:** `docs/P2P-SEARCH-MODULE.md`.

**Не сейчас.** У нас ноль внешних пользователей и одна комната. Это для сети, которой ещё нет.

## Чего НЕ делать

**Не добавлять новые проверки, пока не сократили старые.** Иначе груз растёт.

**Не доказывать больше теорем, пока не починили чтение.** Доказательства не помогут, если
механизм не решает задачи.

**Не расширять архитектуру.** Три уровня достаточны.

## Чего мы не знаем

**Почему чтение проваливается.** Может быть, `MAX_READ` мал. Может быть, модель не находит место.
Может быть, задача сформулирована так, что модель не понимает. **Это надо выяснить на шаге 1.**

**Работает ли механизм на реальных задачах.** Ноль пользователей — ноль данных.

**Нужны ли части вообще.** Может быть, `flowguard-spec`, `lexspec`, `nomos` — это груз, а не
помощь. Это выяснится на шаге 4.
